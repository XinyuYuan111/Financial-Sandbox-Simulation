版本：0.2  
状态：Framework Alpha 实现基线  
日期：2026-07-23  
适用对象：后端、前端、测试、数据适配和 Agent 实现 Agent  

本文件将 `加密金融平行市场沙盒_基础设施设计方案_v0.1.docx` 与 `grilling-decisions.md` 中已接受的决策编译为可实施规范。它不是最终产品 MVP 方案，也不承诺真实金融因果归因。

## 0. 规范使用方式

### 0.1 决策优先级

发生冲突时按以下顺序解释：

1. 本 v0.2 中标记为 `MUST` 或 `CONTRACT` 的条款。
2. `grilling-decisions.md` 中用户已接受或已澄清的最终边界。
3. 本 v0.2 中标记为 `DEFAULT` 的默认参数。
4. v0.1 中未被后续决策覆盖的内容。

v0.1 中关于完整可执行链 fork、实时因果归因、PostgreSQL/Redis/S3 默认依赖、正常 Quick Start 静默使用 Fixture、实时 LLM 重执行一致性和初始产品演示问题的表述，不再作为 Framework Alpha 的实现依据。

### 0.2 规范词

- `MUST`：架构契约，违反即拒绝启动、提交或验收失败。
- `SHOULD`：默认实现，只有有证据的工程原因才能偏离，并必须记录 ADR。
- `DEFAULT`：可修改的版本化默认值，不是永久架构不变量。
- `BENCHMARK`：通过实测校准的性能或容量配置，不得伪装成固定保证。
- `DEFERRED`：当前不实现，不得以隐式方式进入 Framework Alpha。

### 0.3 目标里程碑

Framework Alpha 要证明一个本地、可配置、可保存、可回放、可分叉的离散事件市场世界能够闭环运行。最终产品 MVP 的用户、场景、价值主张和产品验收另立文档，不阻塞本文实现。

## 1. 技术选型结论

### 1.1 推荐语言

**权威后端和仿真内核统一使用 Python 3.12+；浏览器前端使用 TypeScript。**

推荐组合：

| 层 | 语言/组件 | 选择理由 |
| --- | --- | --- |
| 仿真内核、领域模块、适配器 | Python 3.12+ | LLM、数据处理和测试生态完整；事件队列与 200 个 Agent 的本地调度不是首要瓶颈；便于快速迭代契约 |
| API、SSE 和控制面 | Python + FastAPI | 与内核同语言，避免跨语言 DTO 和序列化边界；异步 I/O 适合 LLM 和 Provider 等待 |
| Schema 和运行时校验 | Python + Pydantic | 对 Action、Observation、Event 和配置做严格结构校验；可生成 JSON Schema |
| 数值与账本 | Python 整数定点表示 | 金融数量不使用二进制浮点；核心运算使用最小单位整数和显式舍入 |
| 本地存储 | SQLite WAL + Python sqlite3 或 SQLAlchemy Core | 一键本地运行、单权威写者和快照查询足够；不引入默认数据库集群 |
| 浏览器 | TypeScript + React | 适合时间线、订单簿、Agent View 和回放投影；浏览器不运行权威仿真 |
| 测试 | Python pytest + TypeScript 测试 | 内核契约与前端投影分别验证；Golden Fixture 以规范化 JSON 比较 |

### 1.2 为什么暂不使用 Rust、Go 或微服务

仿真正确性主要依赖事件顺序、资产守恒、分支隔离、LLM 语义隔离和可回放存档。当前性能瓶颈预计来自 LLM Provider 和 HolderDataProvider 的 I/O，而不是 CLOB 的本地匹配。引入第二种后端语言或分布式消息系统会增加 Schema、事务、故障和调试边界，但不会提高 Framework Alpha 的可验证性。

若 BENCHMARK 证明某个纯计算热点确实成为瓶颈，才允许把一个经过接口隔离的模块提取为 Rust 扩展；提取前必须有基准、等价性测试和回退实现。不得预先将内核拆成多语言或微服务。

### 1.3 语言层面的硬约束

- 仿真权威状态只能由 Python 服务端修改。
- 浏览器、LLM 和 Provider 不能直接写账本、订单簿、MemoryStore 或 SQLite。
- 核心金融数值禁止 `float`；价格、数量、余额、手续费使用整数最小单位。
- asyncio 只用于 I/O 等待和控制面并发；同一分支的世界提交仍由单写者顺序完成。
- 任何外部数据必须先转成版本化内部 Schema，再进入仿真。

## 2. 总体架构

### 2.1 运行拓扑

Framework Alpha 采用**模块化单体**：一个 Python 进程包含控制面、仿真平面、存储和适配器；前端由同源 API 提供静态资源。逻辑模块彼此通过 Python 接口和类型化事件通信，但不拆成独立部署服务。

```text
Browser / React
       |
       | REST commands + SSE projections
       v
Python Application
  Control Plane
    config / preview / run control / import-export
  Simulation Plane
    Kernel -> Event Store -> State Projectors
             |                 |
             v                 v
       World Modules       Query Projections
    ledger / CLOB / info / social / chain snapshot
             |
             v
       Agent Runtime
    observation / memory / belief / planner / reactive
             |
             v
       LLM and data adapters
       (external I/O only)
       |
       v
 SQLite WAL + content-addressed blobs
```

### 2.2 模块所有权

| 模块 | 拥有的可变状态 | 允许的输入 | 禁止事项 |
| --- | --- | --- | --- |
| Kernel | 虚拟时钟、事件队列、分支生命周期、写入租约 | 已校验 Domain Event、控制命令 | 直接调用 LLM、直接改浏览器状态 |
| Event Store | append-only 事件、事件哈希链 | Kernel 的原子提交 | 修改历史事件、接受未校验 payload |
| Ledger | 账户、余额、锁定、记账分录 | 合法结算事件、显式 mint/burn/fee 事件 | 通过背景流凭空增发资产 |
| CLOB | 订单、队列、成交、盘口 | 合法订单动作、结算回调 | 绕过 Ledger 直接改变余额 |
| Information/Social | 信息对象、派生内容、送达和关系事件 | 发布、转发、私聊、协议动作 | 直接改变 Agent 信念或记忆 |
| Observation | 每次实际送达和筛选后的观察包 | 权限、订阅、注意力、世界投影 | 读取未授权全局状态 |
| MemoryService | Agent 可访问记忆、容量和修订状态 | MemoryWriteProposal、MemoryRevisionProposal | 接受任意自然语言直写 |
| BeliefService | Agent 当前信念和竞争假设 | BeliefUpdateProposal | 用全局真值自动纠正 Agent |
| Agent Runtime | 策略状态、认知预算、运行上下文 | ObservationPacket、事件触发器 | 修改世界状态或共享其他 Agent 上下文 |
| Archive | 保存的事实、配置、checkpoint 和 blob | Quiescing 后的稳定状态 | 打包秘密凭证或可执行内容 |

任何模块如需改变另一个模块拥有的状态，必须提交 Action 或生成 Domain Event，由状态所有者应用。

### 2.3 不可变与可变数据

- 不可变：事件、原始外部输入、ObservationPacket、LLM 请求/响应记录、MemoryEntry、信息派生链、Archive manifest。
- 可变投影：当前订单簿、账户余额、Agent 当前预算、可访问记忆索引、BeliefState、UI 聚合指标。
- 可变投影丢失后必须能从事件或 checkpoint 恢复；投影不是权威事实源。

## 4. 核心领域契约

### 4.1 时间

- `sim_time_us`：虚拟时间，整数微秒；只由 Kernel 推进。
- `wall_time_utc`：现实时间，仅用于日志、Provider 记录和运维诊断，不参与世界排序。
- `playback_cursor`：前端回放位置，不改变仿真状态。
- 现实 LLM 返回速度不得改变 `sim_time_us`。等待 Provider 时，Kernel 可以暂停该 Agent 的决策，但不将现实等待自动转成世界时间。

### 4.2 数值

资产数量使用最小单位整数：

```text
Quantity = integer >= 0
PriceTicks = integer >= 0
Money = integer in quote smallest unit
```

每个市场在配置中声明 `base_scale`、`quote_scale` 和 `price_tick`。成交价格和手续费按显式舍入规则计算，舍入余数进入指定费用或残差账户。禁止使用 `float` 余额、数量或价格；JSON 中使用整数或字符串化整数，不使用二进制浮点。

### 4.3 EventEnvelope

每个权威事件至少包含：

```json
{
  "event_id": "evt_opaque",
  "run_id": "run_opaque",
  "branch_id": "branch_opaque",
  "branch_seq": 42,
  "sim_time_us": 120000000,
  "priority": 40,
  "tie_break_key": "agent_001:action_008",
  "event_type": "TradeSettled",
  "source_id": "clob_local",
  "target_ids": ["agent_001", "agent_002"],
  "payload": {},
  "parent_event_ids": ["evt_order_1", "evt_order_2"],
  "observation_id": "obs_17",
  "action_id": "act_18",
  "correlation_id": "corr_19",
  "visibility": "analyst_only",
  "rng_stream": "market.matching",
  "rng_draw_index": 7,
  "schema_version": "event.v0.2",
  "prev_event_hash": "sha256:...",
  "event_hash": "sha256:..."
}
```

`branch_seq` 是同一分支的权威顺序。`parent_event_ids` 记录机械血缘，不构成一般性因果证明。事件必须在校验、状态应用、持久化和投影更新完成后才对外可见。

### 4.4 ActionContract

Action 只能由 Agent Runtime、BackgroundFlowGenerator 或用户控制面提交：

```json
{
  "action_id": "act_opaque",
  "agent_id": "agent_001",
  "branch_id": "branch_opaque",
  "submitted_sim_time_us": 120000000,
  "action_type": "SubmitOrder",
  "payload": {},
  "expected_execution_time_us": 120080000,
  "validity_window_us": 500000,
  "parent_observation_id": "obs_17",
  "client_command_id": "cmd_idempotent",
  "schema_version": "action.v0.2"
}
```

动作管线固定为：Schema 校验 -> Agent/Capability 权限校验 -> 余额和资源校验 -> 市场/协议校验 -> 生成执行事件。任何失败都生成 `ActionRejected`，不得静默丢弃。

### 4.5 ObservationPacket

ObservationPacket 保存 Agent 当时实际使用的观察，不在回放时重新计算：

```json
{
  "observation_id": "obs_17",
  "agent_id": "agent_001",
  "branch_id": "branch_opaque",
  "sim_time_us": 120000000,
  "world_version": 42,
  "market_view": {},
  "portfolio_view": {},
  "information_items": [],
  "private_messages": [],
  "chain_view": {},
  "missing_fields": [],
  "observation_delays": {},
  "provenance": [],
  "attention_decisions": [],
  "schema_version": "observation.v0.2"
}
```

### 4.6 Checkpoint 与 Archive

Checkpoint 必须能恢复同版本运行所需的完整内部状态：事件游标、事件队列、账本、订单簿、Background Market Sector、Agent Components、Observation 可访问状态、MemoryStore、BeliefState、CognitiveBudget、LLM 请求结算结果、命名 RNG 状态、配置解析结果和运行时版本。

Archive 是应用级 `.sandbox` 格式，不是数据库备份：

```text
manifest.json
  schema_version
  runtime_version
  run_id / root_branch_id
  included_branches[]
  file_hashes[]
config/resolved_scenario.json
events/branch_<id>.jsonl.zst
checkpoints/<id>.json.zst
blobs/sha256/<hash>
llm/replay_records.jsonl
inputs/chain_snapshot.json
inputs/holder_provider_report.json
projections/optional/
```

Archive 不包含 API Key、钱包私钥或其他秘密。导入先进入隔离 staging，执行资源限制、Schema 校验、路径校验和哈希校验；禁止自动执行 Archive 中的脚本或插件。

## 5. 仿真内核

### 5.1 单写者原则

同一分支在任一时刻只有一个权威提交者。LLM、Provider、前端和未来的多 Worker 可以并发等待或准备输入，但最终事件批次必须回到分支写入租约中顺序提交。

### 5.2 事件提交周期

```text
1. 从事件队列取最小 (sim_time_us, priority, tie_break_key)
2. 读取当前 branch state version
3. 执行事件处理器，产生候选 Domain Events
4. 校验事件 Schema、权限、资产守恒和 branch version
5. 在同一 SQLite 事务内：
   a. append EventEnvelope
   b. apply authoritative projections
   c. update branch cursor and hashes
   d. enqueue derived events
   e. update throttled UI projections
6. 提交事务后再向 SSE 和 Agent Runtime 发布结果
```

事务失败时整批回滚；客户端使用 `client_command_id` 重试时必须幂等。不能先推送 UI 再提交权威状态。

### 5.3 事件排序

默认优先级顺序：

1. 系统、链和控制事件。
2. 市场成交与结算。
3. 保证金检查和清算。
4. 信息发布、送达和关系事件。
5. Observation 更新。
6. Agent 决策与反应。
7. 新动作提交和调度。

同一虚拟时刻、同一优先级按稳定 `tie_break_key` 排序。`tie_break_key` 必须与现实 Provider 返回顺序无关。背景流不能在 `sim_time_us = 0` 的开盘屏障前推进市场或让显式 Agent 失去第一次观察机会。

### 5.4 随机性

使用命名随机流，例如 `market.background`, `agent.<id>.persona`, `agent.<id>.attention`。每个流记录 seed、版本、消费位置和用途。分支默认继承分叉点的流状态；重新播种必须是显式干预。禁止单一全局 RNG 让无关模块互相消耗随机数。

### 5.5 分支状态机

```text
Created -> Initializing -> Ready -> Running
Running -> Paused -> Running
Running -> Quiescing -> Checkpointed
Checkpointed -> Forking -> Ready
Running/Paused -> Completed
任何阶段 -> Failed
```

历史只读。续跑、用户修改或干预均从 checkpoint 创建新分支。多个分支可以逻辑并存，但不得共享可变状态、命名随机流或缓存；可以共享不可变 blob。

## 6. 持久化与恢复

### 6.1 SQLite 组织

启用 WAL、外键约束和参数化 SQL。建议表：

```text
runs
branches
branch_leases
events
event_parents
snapshots
agents
wallets
ledger_accounts
ledger_postings
orders
trades
information_items
information_derivations
relationships
observations
memory_entries
belief_states
llm_requests
llm_responses
commands
projection_cursors
archive_files
```

事件和大对象可以分段压缩到 content-addressed blob；SQLite 只保存 hash、长度、媒体类型和归属。任何可变行都必须带 `branch_id` 和 `state_version`，跨分支查询必须显式指定分支。

### 6.2 保存

用户保存、自动 checkpoint 和分叉使用同一机制。保存命令使分支进入 `Quiescing`：停止发起新 LLM 请求，等待已发请求成功、失败或超时，提交其结果或降级事件，排空当前事件边界，再生成 checkpoint。不能把 Python Future 写入 Archive，也不能加载后无记录地重发请求。

完整实验保存要求所有保留分支分别 Quiescing 并通过事件链、状态和 blob hash 校验。部分 Archive 可以作为故障诊断产物，但不得标记为可续跑完整实验。

### 6.3 磁盘压力

Archive、权威事件和用户保存历史不得静默删除。系统应使用 JSONL 分段压缩、重复 blob 内容寻址、投影重建和可配置 checkpoint 频率降低空间增长。空间不足时：

1. 停止新建 Archive、分叉或需要持久化的运行。
2. 保留已有权威历史和用户保存点。
3. 给出可解释的容量诊断和清理建议。
4. 允许用户显式删除非权威缓存或导出后清理，但不能隐式删除历史。

## 7. 初始化与外部链数据

### 7.1 正常 Quick Start 的输入

用户必须选择受支持的外部链和目标 Token。正常模式还要求实时 LLM Provider 预检通过。市场、Agent、Persona、信息、注意力和预算等其余字段由版本化默认值补齐。Fixture、Replay、规则 Agent 只能用于显式标记的测试、Golden、故障演示或历史回放模式。

链 Provider 失败时不得静默使用 Fixture、旧缓存或另一条链的数据。备用 Provider 只能在预配置、同链、同一最新最终确认区块且数据来源完整可披露时切换；一次初始化不得拼接多个 Provider 的 Holder 结果。

### 7.2 分阶段初始化

```text
Draft Config
  -> Resolve Defaults
  -> Provider Preflight
  -> Load Latest Finalized Block
  -> Resolve Holder Coverage and Special Buckets
  -> Synthesize Portfolios and USDx
  -> Build Background Accounts and Initial Book
  -> Validate Invariants
  -> Resolved Initial State Preview
  -> Atomic Commit to Ready
```

任何必需字段都必须有显式值或版本化默认值。失败只能停在 staging；半初始化世界不得进入 `Ready`。

### 7.3 HolderDataProvider 输出

Provider 结果至少包含：chain id、block height、block hash、provider id、retrieved at、token metadata、地址数、余额合计、覆盖率、特殊地址分类、分类置信度、原始输入 hash 和限制说明。部分覆盖可以进入正常 Quick Start，但必须明确标记 `partial`；未覆盖供给进入已记账 Background Market Sector，不得伪装成完整 Holder 集合。

交易所托管、桥、协议、LP 和合约地址先进入来源桶，例如 `CustodiedSupply`、`BridgeSupply`、`ProtocolSupply`、`LockedTreasury`。分类不确定时保守处理，不创建现实身份数字孪生，也不把聚合地址解释为单个巨鲸。

### 7.4 合成 Portfolio 与供给约束

真实地址只提供余额分位、活动、交易规模、集中度等初始状态特征。显式 Agent 使用 seeded 分层抽样和匿名合成 Portfolio，不复制真实身份、意图或全部资产。

所有 Token、USDx、费用账户、锁仓、销毁和背景储备必须在初始化时记账并满足守恒：

```text
total_token_supply
  = active_agent_token
  + active_background_token
  + inactive_reserve_token
  + locked_or_protocol_token
  + burned_token
```

默认显式 Agent 为 200 个独立个体：180 个普通市场参与者、8 个资本型参与者、6 个流动性提供者、1 个资产发行方、5 个信息参与者。用户可以修改数量和比例，但启动前必须通过 LLM、内存、事件和磁盘容量预检，不得静默缩减。

显式活跃资产的默认资金初始化档位：普通参与者 7.5%，资本型参与者 50%，流动性提供者 30%，资产发行方 10%，信息参与者 2.5%。这些是互不重复的 `funding_profile`，不是互斥硬类型；`role_tags` 可以多选，Capability、Persona、Components 和派生行为标签分别表达不同维度。普通参与者可占绝大多数人数，但只占显式 Agent 活跃净值约 5%-10%。

活跃净值使用：

```text
active_portfolio_value
  = usdx + tradable_token_amount * initial_mid_price
```

锁仓、未解锁 Treasury、非活跃背景储备和协议约束余额不进入分母。Token 与 USDx 必须分别校验，不能只校验折算净值。

### 7.5 USDx 与初始盘口

目标资产的初始价格是独立的 `initial_mid_price`，可以来自 default、manual、seeded_random 或冻结的 market snapshot；启动后不再同步外部价格。

```text
local_active_float_value
  = local_active_tradable_token_amount * initial_mid_price
active_usdx_supply
  = local_active_float_value * quote_coverage_ratio
total_usdx_supply
  = active_usdx_supply + inactive_usdx_reserve
```

非活跃 USDx 在初始化时记账，但不能下单，也不计入初始购买力；后续只能通过事件从储备账户转入背景活跃账户，不能静默增发。

初始订单簿由 Background Market Sector 独占，并由已记账资产支持。盘口深度按活跃资本和目标基准冲击反推；默认校准到一次受保护巨鲸卖出约造成 3%-5% 价格冲击。`sim_time_us = 0` 的开盘屏障完成后，显式 Agent 才能自主挂单、吃单或撤单。初始盘口所有权不等于 70/30 活跃资本比例。

## 8. 市场世界

### 8.1 Ledger

Ledger 采用账户和分录模型。每次转账、成交、费用、锁定、解锁、mint、burn 和背景激活都形成可审计 posting；分录必须满足资产守恒和账户余额非负约束。钱包由一个 Agent 控制者拥有；Framework Alpha 不支持共享钱包、多签或控制权转移。

### 8.2 CLOB

Framework Alpha 只实现一个本地现货 CLOB、一个目标 Token 和一个合成 USDx 报价资产。最小动作：`SubmitLimitOrder`、`SubmitProtectedMarketOrder`、`CancelOrder`、`ReplaceOrder`。支持部分成交、价格时间优先、订单有效期、Maker/Taker 手续费、处理延迟和深度统计。

市价单必须包含保护条件，例如最大滑点、最差价格或最大成交金额；超过保护条件时部分成交或拒绝，不允许无限滑点。匹配先生成成交事实，再由 Ledger 结算；任何结算失败都使事件批次回滚。

### 8.3 Background Market Sector

背景流是已记账环境参与者，不是无限资产生成器。它可以产生普通限价单、市价单、撤单和预配置参与激活事件，但所有动作都走相同 Action、CLOB 和 Ledger 管线。资产耗尽是正常状态；不得静默补资、强行稳定价格或在显式 Agent 第一次观察前推进市场。

`ParticipationPolicy` 只能从允许的非活跃来源桶转移已记账资产，记录来源、数量、触发条件、剩余储备和事件 hash。Q110 的 70/30 只约束初始化和环境主动注入，不约束运行期合法交易造成的财富变化。

## 9. 信息、社会关系与观察

### 9.1 信息对象

事实状态和语言表述分离。同一底层事实可以有不同 `rendered_content`、可信度和情绪强度。原始 InformationItem 不可变；转发、改写和泄露创建派生对象并保留 `derived_from_info_id`，不修改原对象。

至少实现 PublicFeed、OfficialAnnouncement、TradingTerminal 和一个 PrivateChannel；私聊必须有明确送达事件。`Delivered`、`Viewed`、`Believed`、`ActedUpon` 是不同事件，不能合并。

### 9.2 权限与注意力

ObservationService 依次执行：权限 -> 送达 -> 渠道过滤 -> 延迟 -> AttentionProfile -> CognitiveProfile -> Memory/Belief 流程。后层不能扩大前层的可见范围。真实性不向 Agent 暴露；Agent 只能看到内容、来源字段和允许的可信度线索。

AttentionProfile 分三层：不可变基础偏好、运行中可消耗的注意力预算、带来源和有效期的临时 modifier。动态重新分配必须受容量约束并事件化。Agent View 读取已保存的实际 ObservationPacket，不能从全局状态事后伪造。

### 9.3 社会关系

Relationship 记录主体之间的关系类型、主观信任、公开影响力输入、私有频道和协议引用。信任属于某个 Agent 的 BeliefState，不建立全局权威 trust 真值。联盟、承诺、支付和违约必须通过显式社会事件；内核不替 Agent 强制履约，除非协议本身定义了可执行结算规则。

## 10. Agent Runtime、LLM、记忆与信念

### 10.1 Entity-Component 模型

Agent 是可插拔实体，不建立大量硬编码子类。最小组件：Portfolio、WalletControl、MarketAccess、InformationAccess、Communication、Strategy、Memory、Personality、Latency、RiskConstraint、CognitiveProfile、AttentionProfile 和 CapabilitySet。

`funding_profile` 只记录互不重复的初始化资金来源；`role_tags` 可多选；Persona 表示倾向而非保证行为；Capability 表示硬权限；Components 表示功能组合；运行后的行为类别从事件派生。Capability 的授予和撤销可事件化，但 Framework Alpha 不支持自由转让或再授权。

### 10.2 决策闭环

```text
World Event
  -> Permission and Delivery
  -> Attention Selection
  -> ObservationPacket persisted
  -> Agent Runtime trigger
  -> optional Memory Search
  -> optional LLM Strategic Planner
  -> deterministic Reactive Controller
  -> Action validation
  -> scheduled execution event
  -> world facts and next observation
```

LLM 生成目标、立场、条件策略和解释，不生成任意代码，也不一次性生成未来 30 分钟逐秒动作。高频挂单、撤单和执行速度由 Reactive Controller 和市场规则处理。

### 10.3 CognitiveProfile 与预算

每个 Agent 保存不可变 `base_cognitive_profile`，例如上下文容量、每个窗口最大规划次数、记忆检索上限、信息处理容量和复杂事件阈值。运行时另存 `cognitive_budget_state`，记录当前可消耗和可重置额度。疲劳、压力、工具和用户干预使用事件化 `cognitive_modifiers`，不能覆盖基础 Profile。

ProviderBudget 是控制面成本限制，不能反向修改 Agent 的 CognitiveProfile。容量不足时按预检结果拒绝启动或走已声明降级路径，不能暗中降低某些 Agent 的认知预算。

### 10.4 LLM Gateway

Gateway 负责 Provider Adapter、预检、并发池、超时、重试、熔断、Schema 校验、成本记录、Replay 和降级。一个 API 配置可以服务多个 Agent，但每个请求必须有独立 Agent ID、独立上下文、独立请求记录和独立响应归属。传输层允许批处理，语义层禁止共享 Prompt、Memory 或决策。

Provider 返回顺序不能决定虚拟事件顺序。LLM 失败、超时或预算耗尽时，必须生成可回放的失败/降级事件，并使用旧策略、Reactive Controller 或预配置 Replay；正常 Quick Start 启动前 Provider 预检失败不得静默转为测试模式。

### 10.5 MemoryStore

LLM 和控制器只能提交 `MemoryWriteProposal` 或 `MemoryRevisionProposal`。MemoryService 校验来源 Observation/Information/Event、权限、Schema、重复项和容量后生成事件。MemoryEntry 不可变；合并、摘要、替换和遗忘全部事件化。

容量不足时优先合并语义重复项，再按显著性、近期使用、当前目标相关性、置信度、来源多样性和有效期淘汰。Agent 可以主动查询自己的当前可访问记忆，但查询受 CognitiveBudget 限制；失败只返回未找到或部分召回，不暴露从未观察、已遗忘、查询不匹配或预算不足的内部原因。

### 10.6 BeliefState

BeliefState 独立于 MemoryStore，至少包含 `subject`、`predicate`、`object/value`、`confidence`、`evidence_memory_ids`、`updated_at`、受限 `stated_reason` 和 `belief_set_id`。Agent 或控制器提交 `BeliefUpdateProposal`，BeliefService 只校验引用记忆当前可访问、Schema 和权限；内核不以全局事实替 Agent 纠错。

多个竞争假设可以并存。只有显式声明为完整、互斥、穷尽的集合才归一化为 1；否则每个置信度独立在 `[0,1]`。`confidence` 是 Agent 的主观确信程度，不是客观概率，也不能跨 Agent 直接求平均。

支撑记忆被遗忘后，信念可以保留；证据引用只供 Analyst View 审计，不得让 Agent 通过 ID、BeliefState 或 Archive 恢复已遗忘内容。信念变化必须形成显式事件；`stated_reason` 受长度限制，不能成为第二个无限记忆库。

## 11. 配置体验与控制面

### 11.1 三层配置

- Quick Start：用户选择外部链、目标 Token、LLM Provider 和少量市场选项；其他字段使用版本化默认值。
- Customize：按市场、Agent、信息、预算和保存策略展开常用选项。
- Advanced：编辑完整 Schema，但系统仍负责默认补齐、类型校验和不变量校验。

初始化预览必须展示实际 Provider、最终确认区块、Holder 覆盖率、资产来源桶、Agent 数量、Token/USDx 分配、初始价格、盘口深度、警告、容量估计和所有自动合成/缩放结果。无警告时才能一键进入 Ready。

### 11.2 控制命令

控制命令必须有 `client_command_id`、目标 run/branch、操作者会话和幂等结果。最小集合：`create_scenario`、`resolve_preview`、`start`、`pause`、`save`、`fork`、`inject_intervention`、`replay`、`export_archive`、`import_archive`、`delete_cache`。运行中直接改状态不允许；用户干预必须变成 Action 或 Control Event。

### 11.3 API 基线

| 方法 | 路径 | 语义 |
| --- | --- | --- |
| POST | `/api/v1/scenarios` | 创建 Draft Scenario |
| POST | `/api/v1/scenarios/{id}/resolve` | 解析默认、Provider 和 Resolved Initial State Preview |
| POST | `/api/v1/runs` | 从已确认 Preview 原子创建 Run 和 root Branch |
| GET | `/api/v1/runs/{id}` | 查询运行状态和版本 |
| POST | `/api/v1/branches/{id}/commands` | 提交幂等控制命令 |
| GET | `/api/v1/branches/{id}/state` | 查询指定 cursor 的投影 |
| GET | `/api/v1/branches/{id}/events` | 分页查询权威事件，不默认全量推送 |
| GET | `/api/v1/branches/{id}/stream` | SSE 推送节流后的投影和显著事件 |
| POST | `/api/v1/branches/{id}/fork` | 从 checkpoint 创建只读历史的新分支 |
| POST | `/api/v1/archives/export` | Quiescing 后导出 `.sandbox` |
| POST | `/api/v1/archives/import` | 隔离 staging、校验后导入 |

错误响应必须包含稳定 `error_code`、可读 message、字段路径、是否可重试和关联 command ID。断线恢复使用 `branch_id + cursor`，不能依赖长连接永不中断。

### 11.4 前端视图

最小 UI：Scenario Builder、Resolved Initial State Preview、Market Timeline、Microstructure、Information Map、Agent View、Parallel Worlds、Archive/Replay。实时和历史回放使用同一 projection model；实时只是在最新 cursor 上自动跟随。

SSE 只推送投影、显著事件和进度，完整原始事件通过分页查询获取。前端永远不把聚合指标当作权威事实，也不直接访问密钥、LLM、链节点或 SQLite。

## 12. 安全与故障边界

- 本地 API 默认只监听 loopback，使用本地会话令牌和同源策略；远程模式必须显式开启。
- Archive 不含秘密；Provider 凭证只来自运行环境 Secret Store。
- LLM 输出只能是受 Schema 约束的策略、记忆提案、信念提案或 Action，不执行任意代码。
- Archive 导入必须限制压缩展开大小、文件数量、JSON 深度、字符串长度和资源引用。
- 外部 Provider 失败必须可见、可诊断、可回放；不得静默改数据源、改模式或终止分支。
- 崩溃恢复从最后一个已提交事件边界和 checkpoint 开始；半提交事务由 SQLite 回滚。
- 单分支写入租约、幂等命令和 branch version 检查共同防止重复提交和双 Worker 写入。

## 13. 性能、容量与存储策略

性能数字使用版本化 `BenchmarkProfile`，包含参考硬件、Python 版本、Agent 数量、事件率、LLM 并发、Holder 数据规模、Archive 大小和测量方法。不要把尚未实测的事件数、内存峰值或磁盘阈值写成永久承诺。

启动前预检至少估算：

- Agent 总数、待处理请求数和实际 in-flight LLM 数。
- 每个 Agent 的上下文、记忆、Observation 和事件存储。
- CLOB 订单数、背景流频率和事件队列增长。
- SQLite 文件、压缩日志、checkpoint 和 blob 空间。
- Provider 速率、超时和成本预算。

存储优化优先使用 JSONL 分段、压缩、内容寻址、事件与投影分离、按 branch 分区和可配置 checkpoint 频率。不要通过丢弃权威事件、合并 Agent 语义状态或静默减少事件来“优化”。

## 14. 实施路线

### Phase 0：契约和工具链

交付 Event、Action、Observation、Scenario、Snapshot、Archive 的 Pydantic 模型、JSON Schema、错误码、定点数值工具、命名 RNG 和 SQLite WAL 初始化。写结构校验测试。

### Phase 1：内核和持久化

实现单写者 Kernel、事件排序、事件原子提交、分支状态机、命名随机流、checkpoint、branch 和从事件恢复投影。先用固定 fixture，不接外部 Provider。

### Phase 2：Ledger 与 CLOB

实现账户、分录、锁定、结算、手续费、限价单、受保护市价单、部分成交、撤单、订单有效期和背景流。完成资产守恒、价格时间优先和无限滑点拒绝测试。

### Phase 3：初始化与观察

实现分阶段初始化、默认解析、Resolved Initial State Preview、HolderDataProvider 接口、合成 Portfolio、USDx 守恒、权限、注意力和 ObservationPacket 持久化。

### Phase 4：Agent Runtime

实现 Rule Agent、Reactive Controller、CognitiveProfile、MemoryService、BeliefService、Capability 校验和 Agent View。先用 Replay Adapter 验证闭环，再接实时 LLM。

### Phase 5：LLM Gateway 与控制面

实现 Provider 预检、独立请求上下文、受限并发池、批处理传输、超时/降级、成本记录、Quiescing 和幂等控制命令。

### Phase 6：API、SSE 和前端

实现 Scenario Builder、初始化预览、Market Timeline、Microstructure、Information Map、Agent View、Parallel Worlds 和统一 replay cursor。完成断线恢复和投影非权威测试。

### Phase 7：Archive、实证校准和交付

实现 `.sandbox` 导入导出、哈希校验、完整分支树保存、磁盘压力策略、Benchmark Profile、Golden Fixture 和端到端验收报告。

## 15. 测试与验收

### 15.1 必须通过的断言

| 类别 | 断言 |
| --- | --- |
| 数值 | 相同输入下定点计算、舍入和费用结果稳定；禁止浮点进入账本 |
| 时间 | 改变现实 LLM 返回延迟不改变已提交的虚拟事件顺序 |
| 事件 | 事件只追加不修改；每个事件有 branch_seq、schema hash 和可验证血缘 |
| 资产 | 除显式 mint、burn、fee 外 Token/USDx 分别守恒 |
| 权限 | Agent 无法观察未授权信息、其他 Agent 记忆或权威 Archive |
| 观察 | Agent View 使用历史 ObservationPacket，不从全局状态重建 |
| 记忆 | 记忆容量、遗忘、修订和主动检索均事件化且受 CognitiveBudget 约束 |
| 信念 | 竞争信念可并存；主观 confidence 不被解释为客观概率；遗忘不恢复证据 |
| 分支 | 分叉前状态和事件完全一致；分叉后可变状态、随机流和缓存隔离 |
| 保存 | Quiescing 后 Archive 可校验、可回放；历史和用户保存点不静默删除 |
| 初始化 | 必要字段完整解析；链失败不静默回退；Preview 与实际启动输入一致 |
| LLM | 每个 Agent 请求、上下文、响应和预算独立；批处理不改变语义归属 |
| UI | SSE 只推送投影；断线用 cursor 恢复；前端不拥有权威状态 |
| Golden | 固定 fixture、Replay 和 seed 下，内核事件内容和关键投影达到预期 |

### 15.2 确定性范围

必须确定：定点数值、事件排序、Ledger、CLOB、权限、Observation 过滤、命名 RNG、Replay、固定 Fixture 和 Archive 回放。实时 LLM 重新执行不承诺得到同一路径；其输入、输出、超时和降级必须被保存，以便精确回看当时发生过什么。

### 15.3 Framework Alpha 完成条件

Framework Alpha 只有在以下条件全部通过后完成：

1. 一个目标 Token、USDx、本地 CLOB 和合成世界可从 Resolved Initial State 启动。
2. 至少一组 Rule Agent 和一组 Replay Agent 能完成观察、决策、下单、成交、信息传播和回放闭环。
3. 一个 checkpoint 可以创建两个隔离分支，并注入不同干预。
4. Analyst View 和 Agent View 能在同一时间轴回看。
5. `.sandbox` 能保存完整根树、导入校验并在同版本恢复。
6. Golden Fixture、契约测试、资产守恒和分支隔离测试通过。
7. 正常 Quick Start 的链 Provider 和实时 LLM 预检失败时明确阻止启动，不会静默换模式。

## 16. 明确暂缓

以下内容不进入 Framework Alpha，除非另有正式 ADR：

- 最终产品 MVP 的金融问题、用户价值和场景验收。
- 完整可执行链 fork、智能合约执行、AMM、永续合约、跨链桥和 MEV。
- 多链、多资产、多市场和真实稳定币持仓关联。

## 17. 实施 Agent 的工作规则

1. 先读本文件，再读 `grilling-decisions.md`；不得只按 v0.1 实现。
2. 新增领域状态前，先确认它是否已有明确所有者；避免为同一概念创建第二套真值。
3. 新增事件前，先定义 Schema、来源、可见性、父事件、幂等键和投影影响。
4. 新增默认值时标记 `DEFAULT` 并写入版本化 preset；不得把默认值硬编码成架构不变量。
5. 新增外部调用时，定义预检、超时、失败事件、重试和回放记录；不得静默回退。
6. 新增并发时，保留分支单写者和虚拟顺序；现实完成顺序不能成为世界顺序。
7. 新增前端状态时，明确它是投影还是权威状态；权威状态只能来自服务端事件/查询。
8. 任何偏离本规范的实现先写 ADR 和测试，再修改代码；不要用实现方便掩盖契约冲突。

## 附录 B：第一批实现的最小垂直切片

第一批代码不应试图实现全部世界。推荐切片如下：

```text
固定 Scenario Fixture
  -> InitialStateResolved
  -> 一个 Branch
  -> 两个 Rule Agent + 一个 BackgroundFlowGenerator
  -> ObservationPacket
  -> SubmitLimitOrder / CancelOrder
  -> CLOB match
  -> Ledger settlement
  -> TradeSettled + next Observation
  -> Checkpoint
  -> Fork Branch A/B
  -> Replay Analyst View / Agent View
```

这条切片通过后，再逐步替换实时 HolderDataProvider、实时 LLM 和更复杂的信息、社会模块。这样可以在最小实体集合上验证整个架构，而不是同时制造多个互相耦合的半成品系统。
