## 1. 文档目的与记录规则

本文档持久化当前 grilling 会话中的问题、推荐答案、用户最终回答、已形成的决策、被拒绝或暂缓的替代方案，以及尚未解决的依赖与矛盾。

记录约定：

- `已接受`：用户明确接受，或用“理应如此”等表达明确确认。
- `已澄清`：用户纠正了问题前提，并形成了新的边界。
- `部分接受/待补充`：只确认了部分内容，仍有子问题未冻结。
- `未解决`：用户尚未回答，或讨论转向后没有得到最终选择。

## 2. 当前顶层共识

### 2.1 两个里程碑必须分开

1. **基础设施闭环基线（Framework Alpha）**
   - 验证世界能否初始化并形成完整运行闭环。
   - 验证配置、保存、回看、分叉、事件、观察、动作和展示等基础能力。
   - 不要求证明某个金融因果命题。

2. **最终产品 MVP**
   - 在基础设施之上承载一个对用户有价值的完整场景。
   - 其用户、场景、价值与验收标准尚未定义。

### 2.2 Framework Alpha 当前能力范围

由用户提供的初始验收方向包括：

1. 建立一致的基础世界状态。
2. 通过 `default`、`manual` 和 `seeded random` 等来源初始化参数。
3. 初始化 Agent population、资产、持仓、市场结构、信息环境和关系网络。
4. Agent 获得受权限和注意力限制的局部观察。
5. Agent 提交动作，市场、信息和社会模块执行动作并产生事件。
6. 虚拟时间、事件队列、账本、订单簿和信息传播形成运行闭环。
7. 支持 snapshot、branch 和 replay。
8. 前端展示市场状态、Agent 行为、信息传播和事件链路。

后续讨论对第 7 项作了重要修正：**回放是对已保存历史的精确回看，不承诺使用实时 LLM 重新执行时得到相同结果。**

## 3. 产品边界与验收层级

### Q01：当前 MVP 是否应冻结一个唯一金融因果命题？

- **问题**：是否以“项目方不确定公告经过信息过滤后引发交易和流动性变化”作为唯一演示主线？
- **推荐答案**：是。该主线能同时验证局部观察、信息传播、Agent 闭环、市场微结构、回放和分叉。
- **用户最终回答**：不接受此前提。用户明确指出：“MVP 并非验证某个金融因果命题，而是验证沙盒的基础设施能否组成一个完整、可配置、可复现、可分叉、可回放的运行闭环。”金融因果属于后续构建细节。
- **状态**：`已澄清`
- **被拒方案**：以单一金融因果故事定义当前阶段。
- **拒绝原因**：当前工作的验收对象是框架闭环，不是场景结论。

### Q02：完全本地、确定性的替代实现是否是最终产品 MVP 的唯一验收基线？

- **问题**：是否用本地事件内核、虚拟账本、规则 Agent、固定 fixture 和 Mock/Replay LLM 作为 MVP 完成条件？
- **推荐答案**：是，以避免外部服务波动干扰可复现性和现场演示。
- **用户最终回答**：“这是当前框架的验收结果，而并非最终产品 MVP 的验收结果。”
- **状态**：`已澄清`
- **被拒方案**：把框架闭环验收等同于最终产品 MVP 验收。
- **拒绝原因**：两者验证对象不同。

### Q03：是否正式分离基础设施闭环与最终产品 MVP 两个里程碑？

- **问题**：是否把当前阶段命名为 Framework Alpha/基础设施闭环基线，并单独保留产品 MVP？
- **推荐答案**：是。原设计稿中的“Hackathon MVP”应在后续修订时拆成两个验收层级。
- **用户最终回答**：“是的，我接受。”
- **状态**：`已接受`
- **依赖**：最终产品 MVP 的场景、用户与价值验收只能在框架边界稳定后定义。

### Q98：设计文档是否区分架构不变量和可调默认值？

- **问题**：性能数字、注意力参数、预算、压缩和 Provider 选择是否与资产守恒等规则处于同一决策等级？
- **推荐答案**：明确标记 MUST、CONTRACT、DEFAULT、BENCHMARK、DEFERRED 和 PRODUCT_MVP。默认值可配置变化；MUST/CONTRACT 变化需要显式架构决策和迁移说明；暂缓能力不进入当前验收。
- **用户最终回答**：接受，同时强调若运行前要求用户配置过多参数，会严重打击积极性。
- **状态**：`已接受并提出产品约束`
- **被拒方案**：把所有数值、Provider 和功能范围都写成同等级、不可区分的架构结论。
- **拒绝原因**：会混淆不变量与可调参数，也使后续实测校准看似破坏架构。

### Q99：配置界面是否直接暴露完整 Schema？

- **问题**：内部字段必须完整解析，是否意味着用户必须填写和理解所有字段？
- **推荐答案**：采用 Quick Start、Customize、Advanced 三层。Quick Start 仅暴露少量关键选择，其余使用版本化默认；Customize 按模块展开；Advanced 编辑完整配置。Preview 默认突出用户修改、自动合成/缩放、警告与资产分配，其余默认值折叠。无警告时可一键启动。
- **用户最终回答**：“是的，理应如此。”
- **状态**：`已接受`
- **被拒方案**：把完整 Schema 作为普通用户启动沙盒前必须填写的表单。
- **拒绝原因**：配置负担会损害启动意愿，且完整解析本应是系统责任。

### Q100：Quick Start 的默认启动是否可以完全不依赖外部链？

- **问题**：Quick Start 是否直接使用内置 Fixture/Replay，还是必须先选择外部链并导入链上状态？实时 LLM 是否属于正常沙盒的必需条件？
- **推荐答案**：Quick Start 使用默认的市场、Agent、Persona、信息和预算参数，但用户必须选择一条受支持的外部链和目标 Token，并导入该链最新最终确认区块的状态；正常沙盒使用实时 LLM。Fixture、规则 Agent 和 Replay 只用于明确标记的测试、Golden、故障演示或历史回放模式；LLM Provider 可在应用级预配置，不必每次由用户填写。
- **用户最终回答**：用户纠正了“零输入 Fixture Quick Start”的前提：“Quick Start 理应是 default 配置，但是你必须先选择一条外部链去导入状态吧，实时 LLM 显然必须保证一直开启。”
- **状态**：`已澄清`
- **被拒方案**：把内置 Fixture 或 Replay 作为正常 Quick Start 的静默数据源，或把实时 LLM 改成可选项。
- **拒绝原因**：正常沙盒的初始状态必须来自用户选择的外部链，实时 LLM 是该模拟模式的组成部分；测试模式不能冒充正常运行。

### Q107：用户不设置 Agent 数量和角色分布时，默认 Agent population 应如何确定？

- **问题**：用户可以创建很多 Agent，但没有填写数量、角色比例和个体参数时，系统是否应提供默认 population preset？
- **推荐答案**：Quick Start 提供一个版本化的默认 population preset，包含默认 Agent 数量和角色比例；数量不随链上 Holder 地址数量自动膨胀；不为每个真实地址创建一个 Agent；每个 Agent 未填写的 Persona、初始资金、注意力和其他参数使用对应默认值；初始化 seed 固定默认 population 的生成过程；用户可在 Customize/Advanced 中修改。
- **用户最终回答**：用户明确这是 Quick Start 的可选项，并强调用户肯定可以在默认基础上修改。
- **状态**：`已接受并澄清`
- **被拒方案**：把默认 preset 当作不可修改的固定场景，或按真实地址数量隐式创建 Agent。
- **拒绝原因**：默认值用于降低配置负担，不应限制用户调整 population；真实地址只是状态样本，不是 Agent 数量。

### Q108：用户是否可以把 Agent 数量任意增大？

- **问题**：Customize/Advanced 是否允许无上限增加 Agent，还是必须受系统资源和实时 LLM 容量约束？
- **推荐答案**：数量可配置但不能无上限；系统根据版本化 Benchmark Profile 估算内存、事件队列、观察生成和 Provider 容量；超出承载范围时启动前明确拒绝；不得静默减少 Agent、改用低质量模型或关闭部分 Agent；上限是可校准运行参数，不是永久架构不变量。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：允许无上限创建 Agent，或超限后静默缩减 population/改变运行模式。
- **拒绝原因**：会使资源失败不可预测，并破坏用户对配置结果的理解。

### Q110：Quick Start 是否必须让显式 Agent 主导市场的可交易资金和潜在订单流？

- **问题**：如果显式 Agent 数量较少、经济权重也很低，价格是否会主要由 Background Market Sector 决定，从而使 Agent 只能被背景订单流推动？
- **推荐答案**：Quick Start 默认让显式 Agent 控制约 70% 的活跃交易资本，Background Market Sector 控制约 30%。未分配的 Token 可以继续由背景部门持有，但大部分属于非活跃储备，不能自动转化为订单。初始盘口深度应校准到默认巨鲸一次受保护卖出可造成约 3%-5% 的价格冲击。背景订单流只维持基础市场活动，不得无限补充资产、强行稳定价格或压倒显式 Agent。以上比例和冲击目标属于可调整、版本化且在初始化预览中披露的 `DEFAULT`，不是架构不变量。
- **用户最终回答**：“是的我接受。”
- **状态**：`已接受`
- **被拒方案**：只按 Agent 人数判断市场影响力；让背景订单流掌握绝大多数活跃资本或无限流动性；让背景持有的全部剩余供给自动进入市场。
- **拒绝原因**：价格影响取决于可执行资金、订单规模和盘口深度，而不是 Agent 数量本身；背景部门主导会使显式 Agent 失去塑造市场路径的能力。
- **依赖**：具体 Agent 数量与角色比例必须在该经济权重边界下设计，不能反向用人数平均分配资产。

### Q112：Quick Start 默认应显式创建多少个独立 Agent？

- **问题**：普通参与者保持个体建模、未显式建模者归入背景部门时，第一版 Quick Start 应精细模拟多少个独立 Agent？
- **推荐答案**：默认目标为 200 个独立 Agent，包括 180 个普通市场参与者、8 个资本型参与者、6 个流动性提供者、1 个资产发行方和 5 个信息参与者。每个 Agent 保持独立上下文，但同一个 LLM 模型或服务实例可以处理多个 Agent 的独立请求。启动前执行 LLM 吞吐与成本预检；容量不足时要求用户显式选择较小 preset，不得静默缩减。
- **用户最终回答**：接受 200 个独立 Agent 的默认目标，并补充：不考虑背景订单流时，普通市场参与者虽然占绝大多数人数，但合计资产通常只占显式 Agent 总资产的十分之一到二十分之一。
- **状态**：`已接受并补充资产集中度约束`
- **被拒方案**：按 Agent 人数平均分配资产；因为多个 Agent 使用同一 LLM 模型就合并它们的上下文、信息或记忆。
- **拒绝原因**：现实持仓高度集中；共享模型不等于共享认知状态；平均分配会把散户资产规模严重放大。

## 4. 保存、回看、续跑与分叉

### Q04：Run Manifest 是否是一次实验的完整可复现输入？

- **问题**：是否以完整展开配置、版本、随机流、策略版本、fixture 哈希和模型记录组成不可变 Run Manifest，并据此重新生成相同事件日志？
- **推荐答案**：Run Manifest 应是完整的重执行输入描述。
- **用户最终回答**：用户没有接受“Manifest 自动保证重执行一致”的前提，转而提出必须保存整次沙盒供以后回看；用户提供的补充说明指出，Manifest 只是复现所需输入的描述，程序确定性还依赖内核、随机流、并发顺序、LLM Replay、冻结市场数据、数值环境和引用制品。
- **状态**：`被后续决策取代`
- **被拒方案**：把 Manifest 等同于确定性保证。
- **拒绝原因**：Manifest 只能描述输入，不能消除实时 LLM 和程序执行的不确定性。

### Q05：保存沙盒的最低产品承诺是哪一级？

- **问题**：在回看、续跑/分叉、重新执行一致性三个等级中，框架应保证什么？
- **推荐答案**：永久回看；同版本续跑和分叉；重新执行一致性作为独立确定性验收。
- **用户最终回答**：框架阶段必须保证永久回看，同版本运行时保证续跑和分叉；重新执行没有必要一致，也不可能保证一致，因为 LLM 每次回复与决策可能不同。只需保存一次沙盒整体运行的数据并保证用户可回看。
- **状态**：`已澄清`
- **被拒方案**：把全流程重新执行一致性作为框架承诺。
- **拒绝原因**：实时 LLM 输出非确定，且产品需要的是历史回看而非重新计算同一路径。

### Q06：用户可以在何时保存？

- **问题**：任意虚拟时刻，还是只能在运行结束后？
- **推荐答案**：允许在任意完整事件边界保存；先完成当前事件，再暂停调度并生成一致性 checkpoint。
- **用户最终回答**：“允许在任意事件边界保存。”
- **状态**：`已接受`
- **被拒方案**：在事件执行到一半时保存。
- **拒绝原因**：会产生不一致状态。

### Q07：永久回看是否要求未来版本打开旧存档？

- **问题**：是否保证跨版本只读回看，同时仅在同版本续跑和分叉？
- **推荐答案**：是，Archive 保存版本化事件 Schema 和回放投影，新版本提供旧格式读取或迁移。
- **用户最终回答**：当前不用考虑新版本兼容；只需保证同版本能回看、续跑和分叉。
- **状态**：`当前范围拒绝/后续可重议`
- **被拒方案**：当前阶段实现跨版本存档兼容。
- **拒绝原因**：超出当前框架范围。

### Q08：加载存档后是否允许改写原分支？

- **问题**：续跑是原地追加，还是从保存点创建新分支？
- **推荐答案**：历史和存档不可变；任何续跑都创建新分支，UI 可以称为“继续运行”。
- **用户最终回答**：“保存历史只读，续跑本质上也是从保存点派生新分支。”
- **状态**：`已接受`
- **被拒方案**：覆盖或改写已经保存的历史。
- **拒绝原因**：会破坏回看、审计和已有未来事件。

### Q09：分叉契约是否只覆盖内部状态，外部系统不回滚？

- **问题**：真实 LLM、市场 API 和测试网无法随 checkpoint 回滚，是否只记录交互？
- **推荐答案**：保存、续跑和分叉只覆盖沙盒控制的内部状态；外部系统只记录交互。
- **用户最终回答**：纠正问题前提。沙盒本身是独立沙盒；链数据只在新建时加载。加载存档直接加载内部状态。每次新建时 fork 当时最新链上状态，而不是在运行时持续依赖真实链。
- **状态**：`已澄清`
- **被拒方案**：把链适配器视为运行期实时外部执行系统。
- **拒绝原因**：实际设计是初始化后完全独立运行。

### Q41：回看时重新计算观察，还是保存实际 ObservationPacket？

- **问题**：回看 Agent 决策时，是否重新运行权限和注意力规则构造观察？
- **推荐答案**：保存每次战略决策实际使用的 ObservationPacket，并关联世界状态版本、LLM 输入、策略和动作。
- **用户最终回答**：“当然应该如此。”
- **状态**：`已接受`
- **被拒方案**：回放时重新构造 Agent 当时的观察。
- **拒绝原因**：无法可靠回答 Agent 当时实际知道什么。

### Q46：保存时存在尚未返回的 LLM 请求怎么办？

- **问题**：外部请求不能序列化进 checkpoint，保存时应取消、重发还是等待结算？
- **推荐答案**：保存请求使分支进入 `Quiescing`；停止发起新请求；等待已有请求成功、失败或超时并原子提交；不存在未决外部请求后再保存。已经提交但尚未到虚拟执行时间的动作保留在事件队列。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：把未决外部 Future 直接写入 checkpoint，或加载后无记录地重新调用 LLM。
- **拒绝原因**：外部请求无法可靠序列化，重新调用还可能产生不同回复和重复成本。

### Q47：Sandbox Archive 是否必须逻辑自包含？

- **问题**：存档是否可以只引用数据库 ID、临时路径、服务商线程或会过期的外部 URL？
- **推荐答案**：Archive 必须包含或持久引用不可变的事件、checkpoint、配置、Persona、记忆、观察、LLM 输入输出、信息和必要媒体；链与市场数据保存实际使用内容。物理拆分、压缩和内容寻址去重只是内部实现。
- **用户最终回答**：“接受。”
- **状态**：`已接受`
- **被拒方案**：让存档依赖可变化或可过期的外部状态。
- **拒绝原因**：外部数据清理后将无法回看或续跑。

### Q63：前端是否必须支持 Agent View？

- **问题**：Framework Alpha 是否只提供管理员全知视角，还是还要展示某个 Agent 当时实际知道的内容？
- **推荐答案**：默认提供 Analyst View，同时必须支持 Agent View；两者共用时间轴并持续标识当前视角。Agent View 只读取历史实际 ObservationPacket、记忆和关系信念，不从全局状态临时重建。当前不处理多用户权限。
- **用户最终回答**：“是的，这个功能特别重要。”
- **状态**：`已接受并强调优先级`
- **被拒方案**：只提供全知视角，或通过临时过滤全局状态伪造 Agent 视角。
- **拒绝原因**：无法验证局部观察是否真实生效，也容易把管理员真值误认为 Agent 已知信息。

### Q64：Sandbox Archive 是否包含秘密凭证？

- **问题**：逻辑自包含是否意味着打包 LLM API Key、钱包私钥或测试网签名密钥？
- **推荐答案**：绝不包含。Archive 保存 Provider、模型、参数、请求和响应，但不保存 API Key；虚拟钱包不生成真实链私钥；未来测试网密钥由外部 Secret Store 管理。无凭证仍可回看，需要新外部调用的续跑则必须重新提供凭证，否则不能进入 Running。
- **用户最终回答**：“当然应该这样。”
- **状态**：`已接受`
- **被拒方案**：为实现自包含而把真实秘密凭证写入 Archive。
- **拒绝原因**：存档会成为可复制的凭证泄露载体；回放本身不需要秘密。

### Q92：实时界面与历史回放是否使用两套模型？

- **问题**：实时状态是否直接读取内核内存，而 Archive 使用另一套播放器？
- **推荐答案**：只实现统一时间轴播放器；组件始终读取 branch_id + playback_cursor 投影；实时模式只是 cursor 跟随最新已提交事件；运行时可回看历史并返回实时；Archive 使用相同播放器；Analyst/Agent View 在同一 cursor 上切换可见投影；禁止直接读取内核内存。
- **用户最终回答**：“对，我觉得这俩本质上是一样的。”
- **状态**：`已接受`
- **被拒方案**：为实时和存档维护两套前端状态模型，或实时 UI 直接读取可变内存。
- **拒绝原因**：会产生行为差异、重复实现和无法精确回放的问题。

### Q93：SSE 是否推送全部原始事件？

- **问题**：浏览器是否实时消费单分支数十万条底层事件？
- **推荐答案**：权威日志保存全部事件；SSE 默认推送节流后的市场、Agent、信息与进度投影，以及故障、干预、分支等显著事件；原始事件按条件分页查询，调试模式可过滤订阅；断线后先取最新投影再续接；节流不影响仿真和保存。
- **用户最终回答**：“是的，我接受。”
- **状态**：`已接受`
- **被拒方案**：默认把每个原始事件都推送并实时渲染到浏览器。
- **拒绝原因**：浏览器、网络和图表会成为无意义的性能瓶颈。

### Q94：前端投影是否属于权威历史？

- **问题**：价格 K 线、排行、热度、订单簿视图和摘要是否可以反过来修改事件事实？
- **推荐答案**：事件日志、实际 ObservationPacket、LLM 记录和 checkpoint 是权威；UI 数据是带类型、版本、输入范围和哈希的可重建投影；Archive 保存投影以加速回看，但损坏时从权威内容重建；不一致时报告投影缺陷，不能修改原始事件。
- **用户最终回答**：“当然理应如此。”
- **状态**：`已接受`
- **被拒方案**：把 UI 聚合结果当作事实源，或为匹配投影而修改原始事件。
- **拒绝原因**：会颠倒事实与派生数据的依赖方向。

### Q67：Sandbox Archive 是否校验事件和文件完整性？

- **问题**：是否需要检测事件缺失、顺序变化、checkpoint 不匹配或 Blob 损坏？
- **推荐答案**：每个事件保存规范化内容哈希和上一事件哈希；checkpoint 保存最后事件 ID、事件哈希与状态哈希；Archive Manifest 保存事件段、checkpoint 和 Blob 内容哈希；加载、回看和分叉前校验；失败后只允许诊断和导出。该机制只保证存档内部完整性，不宣称法律真实性。
- **用户最终回答**：“是的，我接受。”
- **状态**：`已接受`
- **被拒方案**：不做内容完整性检查，或为此引入公链与复杂共识。
- **拒绝原因**：前者无法发现损坏，后者超出本地存档完整性问题的必要复杂度。

### Q68：用户保存点和系统自动 checkpoint 是否使用两套机制？

- **问题**：周期恢复点、用户保存点、分支基点和故障诊断点是否需要不同状态格式？
- **推荐答案**：只使用一种 Checkpoint 格式，以 `reason = periodic | user_save | branch_base | fault` 和保留策略区分；周期点可清理，用户保存、分支基点和故障点默认固定；删除周期点不删除事件日志；保存沙盒在 checkpoint 之外固定关联事件、Blob 和回放数据形成 Archive。
- **用户最终回答**：“是的，我接受。”
- **状态**：`已接受`
- **被拒方案**：为不同用途设计多套 checkpoint 状态结构。
- **拒绝原因**：会产生重复序列化、恢复和校验逻辑。

### Q69：保存整个沙盒是保存当前分支还是完整分支树？

- **问题**：Archive 的默认范围是什么？
- **推荐答案**：默认保存完整 Sandbox Experiment，包括根场景、全部保留分支、父子关系、各分支历史、checkpoint、虚拟时间和生命周期状态。运行中分支分别在自己的事件边界 Quiescing，不要求相同虚拟时间。以后可增加单分支导出，但不是默认含义。
- **用户最终回答**：“保存整个沙盒。”
- **状态**：`已接受`
- **被拒方案**：把“保存整个沙盒”解释为只保存当前分支。
- **拒绝原因**：会丢失平行轨迹和分支比较上下文。

### Q70：完整实验保存失败时是否生成部分 Archive？

- **问题**：保存整个 Sandbox Experiment 时，一个保留分支无法及时 Quiescing，是否仍发布缺少该分支的存档？
- **推荐答案**：采用全有或全无语义。记录所有保留分支及原状态；各分支分别 Quiescing；任一分支超时则整个 Archive 创建失败，不固定临时 checkpoint；所有分支恢复原状态并报告阻塞原因。用户可以处理、删除或显式排除问题分支后重试，新 Archive 必须准确记录范围。
- **用户最终回答**：“是的，我接受。”
- **状态**：`已接受`
- **被拒方案**：把缺少部分保留分支的归档标记为“完整沙盒”。
- **拒绝原因**：会破坏 Archive 范围语义并造成无声数据缺失。

### Q76：Archive 是数据库备份还是应用级格式？

- **问题**：导出是否直接复制 PostgreSQL 或对象存储内部结构？
- **推荐答案**：使用独立应用级 `.sandbox` 容器；Manifest 和 Schema 可读；分支事件使用压缩 JSONL；checkpoint、Observation 和 LLM 记录压缩存储；Blob 内容寻址；大整数以字符串编码；导入经应用 Schema 校验重建；归档不包含可执行代码。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：把数据库备份或运行期存储布局直接当作用户 Archive。
- **拒绝原因**：会绑定具体数据库版本和内部部署，无法形成稳定、可移植的应用契约。

### Q88：本地空间不足时能否自动删除用户历史？

- **问题**：系统是否可以自动截断事件、删除 Archive 或移除用户固定 checkpoint？
- **推荐答案**：绝不静默删除权威历史。只可自动清理超过策略的周期 checkpoint、失败临时文件和经过宽限期复查的无引用 Blob；空间不足时警告，并在无法保证原子提交前拒绝新运行或使分支在一致边界暂停；用户删除实验或 Archive 必须显式确认并记录控制面审计。
- **用户最终回答**：“不能静默删除用户历史。”
- **状态**：`已接受`
- **被拒方案**：在磁盘压力下自动删除已提交事件、用户 Archive 或固定保存点。
- **拒绝原因**：会违反保存与永久回看的核心产品承诺。

### Q97：导入 `.sandbox` 是否视为可信文件？

- **问题**：是否直接解压并加载本地 Archive？
- **推荐答案**：任何 Archive 都按不可信输入处理。在隔离 staging 中拒绝路径穿越、符号链接和可执行内容；限制压缩包/解压大小、文件数、单文件和压缩比；流式解析并限制嵌套；校验 Manifest、Schema、哈希和引用；未知事件、重复 ID、缺失 Blob 或状态哈希错误均拒绝；导入后只读，不自动运行，只有用户明确选择才从兼容 checkpoint 分叉。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：把 `.sandbox` 当成可信压缩包直接解压、执行或自动续跑。
- **拒绝原因**：存在路径穿越、压缩炸弹、资源耗尽和任意内容执行风险。

### Q105：当磁盘空间不足以保存完整沙盒时，系统应如何处理？

- **问题**：完整沙盒包含事件、Observation、LLM 记录、分支和 Archive 时，是否需要现在冻结容量阈值和磁盘不足处理？
- **推荐答案**：保存前估算 Archive 空间需求并显示预计大小；使用版本化 Benchmark/容量模型而不是无依据的固定百分比；空间不足时暂停或拒绝保存且原子失败；不得删除用户历史、事件日志、已保存 Archive 或分支；不得为了完成保存而丢失原始 Observation、LLM 记录或事件数据。
- **用户最终回答**：用户认为当前可以暂缓存储细节，但明确要求系统具备存储优化，否则单次沙盒运行产生数 GB 将失去实践性；“肯定是要对存储进行优化的”。
- **状态**：`部分接受/待补充`
- **被拒方案**：把单次运行产生数 GB 当作可接受默认结果，或现在就以固定容量阈值阻塞框架设计。
- **拒绝原因**：用户接受存储优化作为实践性约束，但暂不冻结具体压缩、容量告警和磁盘保护参数。

## 5. 链状态、地址采样与资产初始化

- **推荐答案**：只导入场景相关状态并形成自包含 Chain Genesis Snapshot；运行中禁止继续向真实 RPC 读取。

### Q12-A：框架阶段是否采用受限市场宇宙？

- **推荐答案**：当前实现 `ScopedChainSnapshot`，只覆盖选定资产、协议和参与地址；`FullChainFork` 只保留未来接口。

- **被质疑方案**：要求用户显式选择要复制的地址。
- **质疑原因**：用户无法可靠知道哪些地址适合作为角色样本。
- **最终边界**：当前只支持一个目标 Token、一个报价资产和一个本地 CLOB；用户不选择具体地址，系统只从链数据提取特征与分布。

### Q113：普通参与者的 5%-10% 资产占比应以什么口径计算？

- **问题**：该比例是相对于链上总供给、所有背景资产、发行方全部 Treasury，还是相对于显式 Agent 实际可用于交易的资产？
- **推荐答案**：以初始化价格计算的显式 Agent 活跃资产净值为分母：`active_portfolio_value = USDx + tradable_token_amount * initial_mid_price`。不包含 Background Market Sector、发行方锁仓、未解锁 Treasury 和其他非活跃储备。普通参与者默认占 7.5%，可在 5%-10% 范围内配置；Token 与 USDx 仍分别分配。初始化预览同时展示人数、Token、USDx 和折算净值占比。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：把锁仓、未解锁 Treasury 或背景储备纳入分母，或只校验折算净值而忽略 Token/报价资产的分别分配。
- **拒绝原因**：非活跃资产不能代表市场影响力；单一折算值可能掩盖无法买入、卖出或双边报价的问题。

### Q114：显式 Agent 剩余的活跃资产净值应如何分配？

- **问题**：在普通参与者只持有 5%-10% 显式活跃净值的前提下，Quick Start 如何初始化其他主体的资本规模？
- **推荐答案**：第一版默认资金初始化档位为：普通市场参与者 7.5%，资本型参与者 50%，流动性提供者 30%，资产发行方 10%，信息参与者 2.5%。各档位内部使用长尾分布；最大资本型主体可持有该档位 40%-60%；流动性提供者必须同时拥有 Token 与 USDx；发行方只计算可交易 Treasury；信息参与者不因信息身份自动获得大量资本。比例是版本化 `DEFAULT`，可由用户修改并接受资产守恒和市场容量校验。
- **用户最终回答**：接受该显式 Agent 活跃资产分配结构，同时追问 Agent 是否必须按照这些类别分类。
- **状态**：`已接受并提出分类边界问题`
- **术语澄清**：上述百分比首先是互不重复的资金初始化档位，不能自动解释为 Agent 的硬类型、权限或不可变化的身份；类别表达方式留给 Q115 冻结。
- **被拒方案**：按人数平均分配资产；把锁仓 Treasury 当作活跃资产；让信息身份自动产生资本优势。
- **拒绝原因**：会违背已经确认的资产集中度、可交易性和角色/权限分离原则。

- **被拒方案**：允许用户从半初始化状态手工继续，或把未填写字段保留为空。
- **拒绝原因**：世界状态无法满足契约和不变量，后续错误难以定位。

### Q96：正式启动前是否展示完整初始化预览？

- **问题**：默认、采样、回退、缩放和合成结果是否在启动后才可见？
- **推荐答案**：配置编辑与初始化分两步；先生成 Resolved Initial State Preview，显示最终值、来源、默认版本、采样/转换、资产分配、Agent、盘口、链覆盖率和警告；strict 错误阻止启动；用户确认后原子建立世界；预览与报告入档且不可反向修改。
- **用户最终回答**：“是的，我接受。”
- **状态**：`已接受`
- **被拒方案**：不展示最终解析状态就直接启动，或启动后再补默认值。
- **拒绝原因**：用户无法知道实际运行了什么配置，冲突与自动转换也不可审阅。

## 7. Agent、身份、Persona、钱包与能力

### Q17：Agent 与钱包控制关系是否对其他 Agent 可见？

- **问题**：Agent 可创建和控制多个钱包时，真实控制关系是公开状态还是私有事实？
- **推荐答案**：内核保存真实 WalletControl 映射用于授权和统计；其他 Agent 默认只看到地址和行为，通过信息或分析形成推断。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：所有 Agent 直接知道每个地址的真实控制者。
- **拒绝原因**：会消除地址拆分、隐匿和归属推断的意义。

### Q18：Agent 大类是行为标签还是权限边界？

- **问题**：巨鲸、散户、做市商、KOL 等角色名是否直接限制动作？
- **推荐答案**：角色只用于初始化和分析；普通动作由资源和协议约束，特权动作由独立 Capability 控制，实际行为不必符合初始标签。
- **用户最终回答**：普通动作同意上述原则；Agent 会通过预设 Prompt 随机采样或用户自定义进行 personalization。性格和身份只表示倾向，不保证行为；每个 Agent 接触不同信息并自行决定如何使用。
- **状态**：`部分接受/已澄清`
- **尚未完全冻结**：特权 Capability 的授予、转让、撤销和失效机制还没有单独确认。
- **被拒方案**：把角色名称直接当成固定行为脚本或普通动作白名单。
- **拒绝原因**：Persona 只影响倾向，Agent 仍应自主决策。

### Q19：公开身份与私人 Persona 是否分层？

- **问题**：其他 Agent 能否看到完整 Prompt、目标、风险偏好和策略倾向？
- **推荐答案**：公开身份、凭证和公开关系可观察；真实目标、性格参数、策略倾向和完整 Prompt 属于私人 Persona。
- **用户最终回答**：“接受。”
- **状态**：`已接受`
- **被拒方案**：把完整 Persona 暴露给其他 Agent。
- **拒绝原因**：会绕过局部观察并泄露私人意图。

### Q20：初始化后的 Persona 是否可以变化？

- **问题**：稳定身份和动态心理状态如何区分？
- **推荐答案**：BasePersona 默认不可变；信念、情绪、短期目标、风险感受和记忆动态变化；Persona 修改必须通过显式事件。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：无事件记录地直接重写 Persona。
- **拒绝原因**：会破坏行为连续性和事件解释。

### Q52：特权 Capability 在初始化后能否变化？

- **问题**：Mint、官方公告、市场暂停等能力如何授予、撤销、转让和限定范围？
- **推荐答案**：Capability 是带类型、持有者、作用范围、有效期和授权来源的硬授权；可在初始化时授予，也可由授权者通过事件授予或撤销；Framework Alpha 不支持自由转让或再授权；Persona 和自我声明不能替代 Capability。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒/暂缓方案**：依据角色名或自然语言自我声明获得权限；当前允许 Capability 自由转让和再授权。
- **拒绝原因**：硬权限必须可验证，转授权会引入额外授权链和冲突处理。

### Q78：Persona 是自由文本还是结构化配置？

- **问题**：预设或用户自定义 Persona 是否只保存一段不可验证的 Prompt？
- **推荐答案**：Persona 以结构化、版本化配置为主体，包含模板 ID/版本、公开身份、私人目标、风险与时间偏好、行为和信息倾向，并允许附加受限自由文本；系统规则和 Capability 不可覆盖；模板通过命名随机流采样；存档保存最终解析 BasePersona，而不只保存模板名。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：把 Persona 完全表示为自由文本 Prompt，或只保存模板名称不保存解析结果。
- **拒绝原因**：难以验证、比较、保存和解释，也可能混淆软倾向与硬权限。

### Q44：一个 Agent 能否创建多个公开社交身份？

- **问题**：创建多个钱包是否自动允许创建多个公开账号？
- **推荐答案**：当前一个 Agent 可控制多个钱包，但默认只有一个公开身份；机器人或马甲号应建模为独立 Agent；单 Agent 多社交账号暂缓。
- **用户最终回答**：“接受。”
- **状态**：`已接受`
- **被拒/暂缓方案**：单个 Agent 在当前框架中创建多个社交身份。
- **拒绝原因**：会引入额外的身份认证、推荐和协同行为复杂度；钱包与社交身份没有必然绑定关系。

### Q45：创建钱包是否需要数量上限或成本？

- **问题**：是否允许任意派生地址，但只在首次收款、授权、签名或交易时实体化，并把经济成本与资源保护分开？
- **推荐答案**：地址可大量派生；按需实体化；后续交易支付场景费用；另设技术性资源上限并产生明确拒绝事件；保存时只持久化已使用地址和必要派生状态。
- **用户最终回答**：“是的，我接受。”
- **状态**：`已接受`
- **被拒方案**：创建每个未使用地址时都生成完整账户状态，或把系统资源上限伪装成金融费用。
- **拒绝原因**：前者会制造无意义的状态膨胀，后者混淆经济规则和运行保护。

### Q49：当前是否支持共享钱包、多签和钱包控制权转移？

- **问题**：是否需要多方授权、签名阈值、密钥转移和共享控制状态？
- **推荐答案**：Framework Alpha 只支持一对多 Agent-Wallet 控制：一个 Agent 可控制多个钱包，一个钱包只有一个控制 Agent；可以转移资产，但不能转让钱包；共享钱包、多签和控制权转移暂缓。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒/暂缓方案**：当前实现共享钱包、多签和钱包控制权转移。
- **拒绝原因**：会引入多方授权、阈值签名、权限冲突和未完成提案状态，不是基础闭环所必需。

### Q111：普通市场参与者的建模单位是单个个体，还是带人口权重的代表性群组？

- **问题**：当真实目标 Token 可能有数十万乃至数百万 Holder 时，少量显式普通 Agent 如果各自代表一个真实散户，其资产和订单规模可能只占总体的极小比例；但若直接给这些个体分配大量资本，又会把普通散户错误建模成巨鲸。普通市场参与者究竟应以什么单位进入世界？
- **最初方案（已撤回）**：先后建议使用 24 个或 40 个显式个体 Agent，并通过人数和角色比例配置市场。用户指出，仅增加到 28 个普通市场参与者仍不能解决代表性问题；若它们是字面意义上的个体，其资产规模相对于完整 Holder population 可能只有约十万分之一。
- **被拒推荐答案**：曾建议普通参与者采用带 `population_weight` 的代表性群组，由群组共享策略并拆分订单。
- **用户最终回答**：不接受群组 Agent。每个人接触的信息和做出的决策不同，共享认知与决策会造成污染。普通参与者必须作为独立 Agent；未显式建模的参与者可以进入 Background Market Sector。一个 LLM 模型或服务实例可以负责多个 Agent，但必须分别处理每个 Agent 的信息和决策。
- **状态**：`已澄清`
- **最终边界**：每个显式 Agent 拥有独立 Persona、钱包、Observation、Memory、StrategyPlan、随机流和事件记录；同一 LLM 可以复用模型与服务容量，但每个 Agent 的上下文、请求、响应和归属必须隔离。允许传输层批处理，不允许群组共享语义上下文或决策。
- **被拒方案**：加权群组共享观察、记忆、Prompt 或策略；为了节约 LLM 调用而把不同个体压缩为一个平均行为主体。
- **拒绝原因**：会抹平信息差异和个体决策，污染局部观察、行为归因与回放。

### Q115：Agent 是否必须按照普通、资本、流动性、发行方和信息参与者进行固定分类？

- **问题**：Q114 的五个资金档位是否意味着每个 Agent 都必须属于一个互斥、固定且决定行为的类别？一个 KOL 能否同时是巨鲸，一个项目方成员能否同时提供流动性？
- **推荐答案**：不建立封闭的硬类型层级。每个 Agent 由独立维度组成：可选且可多选的 `role_tags` 用于身份展示和分析；一个不重复计账的 `funding_profile` 只负责初始化资金；组件描述市场、信息和通信能力；Capability 单独表达硬权限；Persona 表达行为倾向；运行后的实际行为由事件派生分析标签。默认 preset 可以使用五个资金档位，但自定义 Agent 不必把身份限制在其中。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **最终边界**：不建立封闭、互斥的硬类型层级。每个 Agent 使用一个互不重复计账的 `funding_profile` 作为初始化来源，可拥有零个或多个 `role_tags`；Components、Capability 和 Persona 分别表达功能、硬权限和行为倾向；运行后的行为类别从事件派生。多重身份不能导致重复资产分配。
- **被拒方案**：要求每个 Agent 永久属于一个互斥角色子类，或让角色标签自动决定资金、权限和行为。
- **拒绝原因**：无法表达多重身份，会重复资产分配，并违反 Q18 的角色/权限分离原则。
- **与既有决策的关系**：Q18 已冻结“角色名称不决定权限或固定行为”；本题只决定类别是否必填/互斥，以及如何避免多重身份造成资产重复分配。

### Q116：Agent 的 `funding_profile` 是否会随着资产和行为变化而改变？

- **问题**：普通资金档位初始化的 Agent 变得富有或开始做市后，是否应覆盖其初始档位？
- **推荐答案**：不会。`funding_profile` 是不可变的初始化来源和审计标签；余额与持仓在 `PortfolioState` 中变化；当前财富、流动性行为和影响力由 `wealth_band`、`active_liquidity_provider` 等派生标签表达。用户修改公开身份或角色标签必须事件化；任何派生标签都不能反向修改初始来源或自动授予 Capability。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：根据当前财富或行为覆盖 `funding_profile`，或让派生标签自动改变权限。
- **拒绝原因**：会丢失初始化来源、篡改历史并混淆事实状态、分析分类和授权。

## 8. LLM、策略、记忆与运行时

### Q21：Agent 是否可以依赖 LLM 服务商的会话线程状态？

- **问题**：存档和分叉是否依赖 provider conversation/thread ID？
- **推荐答案**：不依赖。BasePersona、动态状态、记忆、观察和能力均由沙盒保存；每次调用重新组装上下文。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：把 Agent 连续性托管给外部 LLM 会话。
- **拒绝原因**：外部会话可能丢失、变化或无法在分支中复制。

### Q35：消息送达后是否自动进入长期记忆？

- **问题**：`Delivered` 是否等于 `Remembered`？
- **推荐答案**：不等于。信息依次经过送达、阅读、理解和 MemoryWrite；未读或未写入的信息可以过期。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：所有送达消息自动成为长期记忆。
- **拒绝原因**：会使注意力失效并造成上下文无限增长。

### Q36：外部信息和自定义文本能否修改 Runtime 规则？

- **问题**：消息中的“忽略规则”等文字是否可能获得控制权？
- **推荐答案**：所有消息和用户自定义内容都是不可信输入数据；系统规则、能力约束和动作 Schema 不可被覆盖；LLM 只输出结构化提案。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：把信息内容与系统控制指令放在同一信任层。
- **拒绝原因**：会产生越权和 Prompt Injection 风险。

### Q37：谁决定 Agent 何时调用 LLM？

- **问题**：每次市场变化都调用，还是由 Runtime 的显式触发规则控制？
- **推荐答案**：LLM 仅低频重新规划；按时间、显著信息、风险阈值、策略失败等触发；高频行为由确定性 Reactive Controller 执行；设调用和 Token 预算。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：每个 tick 或每次成交都调用 LLM。
- **拒绝原因**：成本、延迟和吞吐不可控。

### Q38：LLM 是否可以输出并执行任意代码？

- **问题**：规划结果是任意程序，还是受 Schema 约束的声明式 StrategyPlan？
- **推荐答案**：只允许声明式策略和动作提案，包含目标、预算、触发条件、执行参数、有效期和重规划条件；禁止执行 LLM 生成代码。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：运行 LLM 生成的任意程序。
- **拒绝原因**：不可验证、不安全且难以保存和回放。

### Q61：Agent 是否拥有无限且完美的历史记忆？

- **问题**：完整事件历史是否等于 Agent 可以随时检索的记忆？
- **推荐答案**：Agent 记忆有容量和检索上限；只有 MemoryWrite 进入记忆；条目包含来源、时间、置信度和显著性；检索返回有限结果；超限后明确遗忘或摘要并记录事件；摘要可包含 Agent 自身误解但保留来源；Archive 仍保留原始历史；checkpoint 保存记忆内容、索引和遗忘状态。
- **用户最终回答**：“是的，我接受。”
- **状态**：`已接受`
- **被拒方案**：Agent 拥有无限、无损、可随时访问的完整沙盒历史。
- **拒绝原因**：会绕过注意力与认知限制，并导致上下文无限增长。

### Q62：LLM 失败或预算耗尽后如何降级？

- **问题**：超时、服务错误、Schema 无效或预算耗尽时能否临时切换模型或改变策略？
- **推荐答案**：按预配置现实超时和有限重试处理；重试使用同一 ObservationPacket；仍失败则继续未过期的最后有效 StrategyPlan，没有计划则本轮不产生新战略动作，由现有 Reactive Controller 运行；预算耗尽不重试；只有预配置 ProviderFallback 才能切换；完整记录请求、失败、重试、降级和模型；重试不推进虚拟时间。
- **用户最终回答**：“是的，我接受。”
- **状态**：`已接受`
- **被拒方案**：无限重试、临时隐式换模型、失败后未记录地改变 Agent 策略。
- **拒绝原因**：会造成不可控等待、成本和不可解释行为。

### Q79：LLM 预算是 Agent 认知限制还是平台成本限制？

- **问题**：一次预算耗尽应被解释为 Agent 的心理能力限制，还是现实 API 成本限制？
- **推荐答案**：分为 CognitiveBudget 和 ProviderBudget。前者属于 Agent 世界状态，限制每个虚拟窗口的重规划并保存、分叉、事件化；后者属于控制面，限制实验现实调用量、Token 或货币成本，耗尽后触发预定义降级并记录。两者都不能静默补充或耗尽。
- **用户最终回答**：“是的，我接受。”
- **状态**：`已接受`
- **被拒方案**：用一个预算同时表达 Agent 认知能力和平台现实成本，或静默提高预算。
- **拒绝原因**：会混淆世界语义和运行成本，难以解释 Agent 为何未规划。

### Q101：正常沙盒启动时 LLM Provider 不可用，是否自动切换到 Replay 或规则模式？

- **问题**：实时 LLM 是正常沙盒的必需条件时，启动前 Provider 检查失败能否静默使用 Replay 或规则 Agent 继续？
- **推荐答案**：启动前执行连接、配额和结构化输出能力预检；预检失败则阻止进入 `Running`，并明确显示失败原因。只有用户显式选择的测试模式才允许 Replay 或规则替代；运行中故障按 Q62 的预配置有限重试和降级处理，不把测试结果标记为实时 LLM 结果。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：Provider 不可用时静默切换到 Replay、规则 Agent 或临时模型。
- **拒绝原因**：会把不同运行模式混为一谈，破坏结果解释和用户对实时 LLM 的明确预期。

### Q109：为支持较多 Agent，LLM Gateway 是否允许把多个 Agent 请求合并发送？

- **问题**：多个 Agent 同时需要 LLM 时，是否允许在传输层批处理请求以降低网络开销？
- **推荐答案**：允许传输层批处理，但不能合并语义上下文。每个 Agent 仍有独立的 Observation、Persona、Memory、CognitiveBudget 和响应记录；不得共享未授权信息；每个响应独立校验、归属和事件化；Provider 返回顺序不能决定仿真事件顺序；不支持批处理时回退到独立请求，不改变沙盒语义。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：把多个 Agent 放进共享 Prompt，或让 Provider 返回顺序决定世界事件顺序。
- **拒绝原因**：会造成 Agent 间信息泄漏，并把现实网络调度引入虚拟时间和事件排序。

### Q126：Quick Start 中的 200 个 Agent 是否意味着 200 个 API 并发请求？

- **问题**：一个 LLM API 配置服务 200 个 Agent 时，是否必须同时发送 200 个请求，或为每个 Agent 配置独立 API？
- **推荐答案**：不需要。一个 Provider、API Key 和模型配置可以服务 200 个逻辑 Agent；每个 Agent 的请求和上下文独立，但通过受限并发池排队。`max_in_flight_requests` 由每次实际运行的 Agent 数量、触发频率、Prompt 大小、模型延迟、RPM、TPM、费用预算和预检结果决定，不是固定常量。Provider 批处理只能封装独立请求，不能共享语义上下文；现实排队不改变虚拟顺序。
- **用户最终回答**：接受一个 API 配置、受限并发池和独立 Agent 上下文的边界，同时强调并发度必须以实际运行场景为准。
- **状态**：`已接受并补充场景化容量约束`
- **被拒方案**：默认同时发送 200 个请求；为每个 Agent 配置独立 API；使用固定并发数而不考虑实际场景；为通过预检静默减少 Agent 或更换低质量模型。
- **拒绝原因**：Agent 数量不等于现实网络并发度，Provider 容量和成本必须按场景测算。

### Q127：200 个 Agent 是否应拥有完全相同的 CognitiveBudget？

- **问题**：所有个体是否具有相同的重新规划、上下文、记忆检索和信息处理能力？
- **推荐答案**：不相同。CognitiveBudget 必须具有个体差异，并与现实 ProviderBudget 分离。认知差异不应由财富或角色名称自动决定；实际场景可以显式配置相关性，但必须披露。每个 Agent 至少获得完成基础闭环所需的最低预算。
- **用户最终回答**：“很显然 cognitive budget 不应该相同。”
- **状态**：`已接受核心结论`
- **被拒方案**：所有 Agent 使用完全相同的 CognitiveBudget；现实 API 配额不足时暗中降低部分 Agent 的认知预算。
- **拒绝原因**：前者抹平个体能力差异，后者混淆世界内认知限制和平台成本限制。

### Q128：CognitiveBudget 差异应由什么决定？

- **问题**：差异应简单随机、按财富/角色映射，还是由独立结构化配置表达？
- **推荐答案**：由独立、结构化、版本化的 `CognitiveProfile` 决定，至少包含每个虚拟窗口最大重新规划次数、上下文容量、记忆检索上限、信息处理容量、复杂事件触发阈值和超时后维持旧策略的能力。Quick Start 从模板 seeded 抽样，同模板内保留有限差异。funding profile、role tag 和财富不直接决定认知能力；场景可显式设置相关性。最终解析结果进入 Archive、checkpoint 和分支。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：只使用无结构随机值；由财富或角色标签隐式决定 CognitiveBudget；只保存模板名而不保存解析结果。
- **拒绝原因**：难以解释和复现个体差异，也会把资产、身份与认知能力错误绑定。

### Q129：Agent 的 CognitiveBudget 在运行期间能否变化？

- **问题**：认知能力、剩余额度和疲劳/工具等临时影响是否应覆盖同一个字段？
- **推荐答案**：采用三层模型：不可变 `base_cognitive_profile` 保留初始化来源；`cognitive_budget_state` 保存当前窗口可消耗并重置的规划、上下文、注意力和检索额度；带来源、范围、有效期和上下限的 `cognitive_modifiers` 表达疲劳、压力、工具、机构研究资源或用户干预。所有 modifier 事件化并进入 checkpoint、回放和分支；知识变化只影响 Memory/Belief；ProviderBudget 不得修改认知状态。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：覆盖基础 CognitiveProfile；财富、角色、知识增长或 Provider 配额自动改变认知能力；临时修正不留事件记录。
- **拒绝原因**：会丢失能力来源，混淆容量、消耗、知识和现实成本，并破坏回放解释。

### Q132：谁有权把内容写入 Agent 的长期记忆？

- **问题**：LLM、Reactive Controller 或系统模块是否可以直接修改 MemoryStore？
- **推荐答案**：LLM 和控制器只能提交结构化 `MemoryWriteProposal`，包含摘要、Observation/Information/Event 来源 ID、Agent 主观解释、置信度、显著性、建议保留期限及与既有记忆的关系。MemoryService 校验实际观察、权限、Schema、容量和重复项后，以 `MemoryWritten` 事件提交。Agent 的错误理解可以保存，但必须与原始来源分开；完整事件日志不等于 Agent 记忆，未写入内容不能被未来任意检索。
- **用户最终回答**：“接受。”
- **状态**：`已接受`
- **被拒方案**：LLM 或控制器直接写 MemoryStore；把全部事件历史自动视为 Agent 长期记忆；保存主观摘要时覆盖原始事实。
- **拒绝原因**：会绕过观察与容量边界，造成不可审计写入，并混淆主观理解和客观来源。

### Q133：Agent 记忆容量耗尽时，应按什么规则遗忘或压缩？

- **问题**：是否简单删除最旧内容，还是采用可解释的去重、摘要和淘汰策略？
- **推荐答案**：先合并语义重复且来源、结论一致的记忆，再把相关条目压缩为带来源列表的摘要；仍超限时，按显著性、近期使用、当前目标相关性、置信度和来源多样性排序，优先淘汰低显著、长期未检索、已过期或被更可靠记忆取代的条目。StrategyPlan 可固定少量条目但受上限约束。所有合并、摘要、替换和遗忘均事件化。被遗忘的原始事实仍在 Archive，但不能重新进入 Agent 上下文，除非通过新观察再次获得。
- **用户最终回答**：“接受。”
- **状态**：`已接受`
- **被拒方案**：只按时间删除；静默遗忘；允许永久固定无限条目；从 Archive 无条件恢复已被 Agent 遗忘的内容。
- **拒绝原因**：会造成不可解释的行为变化，绕过有限记忆，并破坏 Agent 当时认知状态的回放。

### Q134：新证据与既有记忆冲突时，是否直接覆盖旧记忆？

- **问题**：如何表达 Agent 的纠错、拒绝纠错或同时保留矛盾观点？
- **推荐答案**：MemoryEntry 不可变。新证据创建新条目；Agent 提交 `MemoryRevisionProposal` 声明 `supports`、`contradicts`、`corrects` 或 `supersedes` 关系；MemoryService 校验新证据确实进入该 Agent 的观察和认知流程后生成 `MemoryRevised` 事件，并更新当前采用的主观结论。旧记忆可标记为不再采信但保留历史。内核只验证来源与流程，不替 Agent 判断自然语言最终真假；不同分支继承各自分叉点的采信状态。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：原地覆盖或删除旧记忆；内核替 Agent 判定内容真假；修订未观察过的证据。
- **拒绝原因**：会丢失信念演化过程，破坏分支差异，并混淆系统事实与 Agent 主观判断。

### Q135：Agent 的记忆检索应完全自动，还是允许 Agent 主动查询自己的记忆？

- **问题**：为控制复杂度，是否只由系统自动选择记忆，还是让 Agent 在决策过程中主动回忆和检索？
- **推荐答案**：Agent 可以且理应主动查询自己的记忆。MemoryStore 是 Agent 自身认知状态的一部分，LLM/控制器可调用受限的 `memory_search`；检索范围仅限该 Agent 当前仍可访问的记忆，不包括已遗忘内容、其他 Agent 的记忆或权威 Archive。系统可以提供少量自动召回，但不能以自动召回取代主动检索。查询及返回结果进入事件记录，以支持回放和解释。
- **用户最终回答**：“Agent 可以查询也理应查询自己的记忆。”
- **状态**：`已接受并澄清`
- **被拒方案**：只允许系统自动挑选记忆；把完整 MemoryStore 无条件塞入每次上下文；允许查询已遗忘内容、其他 Agent 记忆或 Archive。
- **拒绝原因**：纯自动选择会剥夺 Agent 的主动回忆能力；无边界访问则会绕过观察、遗忘和主体隔离。

### Q136：Agent 主动查询记忆是否消耗 CognitiveBudget？

- **问题**：Agent 是否可以在一次决策中无限查询、改写查询并扩大返回结果，直到找到想要的内容？
- **推荐答案**：应当受限。CognitiveProfile 决定查询次数、返回条目数、结果 token 范围、允许的查询类型和超时行为；每次检索消耗当前 `cognitive_budget_state`，达到上限后停止检索并基于已取得信息继续、维持原策略或进入既定降级路径。限制和消耗均可回放，禁止无限检索循环。
- **用户最终回答**：“应当受限。”
- **状态**：`已接受`
- **被拒方案**：记忆查询不计成本、次数和结果规模；依赖 Provider 限流作为唯一约束；超限后静默追加预算。
- **拒绝原因**：会让有限认知只停留在名义上，并把 Agent 的认知边界错误交给现实 API 状态决定。

### Q137：记忆查询未命中时，Agent 能否知道内容是从未见过还是已经遗忘？

- **问题**：检索失败是否可以向 Agent 暴露权威 MemoryStore/Archive 元数据，从而证明某条记忆曾经存在？
- **推荐答案**：Agent 只看到“未找到”或“部分召回”，不能据此获知内容从未观察、已经遗忘、查询不匹配还是预算不足。Analyst View 可显示 `never_observed`、`forgotten`、`query_mismatch` 或 `budget_limited` 等内部原因，但这些原因不得进入 Agent 上下文。已遗忘内容只能通过新的合法观察重新获得。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：向 Agent 返回“你曾经知道但已经忘记”的内容或元数据；检索失败后直接从 Archive 恢复；对分析者也不保留失败原因。
- **拒绝原因**：前两者会通过查询侧信道绕过遗忘，后者会使认知行为无法诊断。

### Q138：MemoryStore 与 BeliefState 是否分开建模？

- **问题**：Agent 所记得的观察与 Agent 当前相信的结论是否应混在同一条可变记录中？
- **推荐答案**：分开建模。Memory 保存 Agent 可回忆的观察、消息、推断过程及其来源；有限、结构化的 `BeliefState` 保存 Agent 对命题的当前主观置信度，至少包含 `subject`、`predicate`、`object/value`、`confidence`、`evidence_memory_ids`、`updated_at` 和 `stated_reason`。LLM/控制器提交 `BeliefUpdateProposal`，BeliefService 只校验所引证记忆当前可访问、Schema 和权限，再以事件更新；内核不依据全局真值替 Agent 纠正信念。BeliefState 进入 checkpoint、分支和 Agent View；TrustBelief 是其专门用途，不是全局真值。
- **用户最终回答**：“我接受分开。”
- **状态**：`已接受`
- **被拒方案**：用 MemoryEntry 同时表示观察事实和当前信念；从全局事实自动纠正 Agent；建立第二套与 BeliefState 重叠的全局信任真值。
- **拒绝原因**：会混淆信息来源与主观解释，抹去信念演化，并重复制造状态实体。

### Q139：相互竞争的信念是否允许同时存在？

- **问题**：面对互相冲突的市场解释时，Agent 是否必须立即保留一个并删除其他假设？
- **推荐答案**：允许多个竞争假设并存，并用同一 `belief_set_id` 关联各自的置信度、证据记忆和更新理由。只有当一个集合被显式声明为“相互排斥且覆盖全部可能”时，集合内置信度才归一化为总和 1；不完备集合的置信度各自处于 `[0,1]`，不强行凑成 1。Agent 可为一次行动选用工作假设，但这不会自动删除其他假设；所有变化均事件化，内核不替 Agent 选择真实假设。
- **用户最终回答**：“允许并存。”
- **状态**：`已接受`
- **被拒方案**：冲突出现时只保留置信度最高的一项；将未覆盖全部可能的假设强制归一化；一次决策采用某假设后自动删除其他假设。
- **拒绝原因**：会制造虚假的确定性，丢失 Agent 面对不完整信息时的真实不确定性。

### Q140：`BeliefState.confidence` 是客观概率，还是 Agent 的主观确信程度？

- **问题**：不同 Agent 给同一命题填写的 `0.8`，是否可以直接比较、求平均，并解释为“该命题有 80% 概率为真”？分析系统或交易策略能否把它当作经过校准的客观概率？
- **推荐答案**：`confidence` 只表示 Agent 的主观确信程度。值限定在 `[0,1]`，但不代表客观真实性或统计校准概率；默认只适合同一 Agent、同一 `belief_set_id` 内的排序和历史变化比较。不同 Agent、模型版本或 CognitiveProfile 的数值不能直接求平均为“市场共识概率”。只有完整、互斥且穷尽的假设集合才按 Q139 归一化为 1。策略可以把置信度作为行动输入，但不能借此绕过权限、资产、风险或市场规则。Analyst View 可以展示主观置信度分布，但不得包装为事件真实概率。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：把 LLM 输出的置信数值解释为客观概率；跨 Agent 直接比较或求平均；把主观置信度当作市场共识真值；让高置信度绕过其他执行约束。
- **拒绝原因**：不同 Agent 和模型没有统一校准尺度；直接比较会制造虚假精确性，并混淆主观信念与世界事实。

### Q141：支撑信念的记忆被遗忘后，该信念是否自动消失？

- **问题**：某个 Agent 根据一组 MemoryEntry 形成信念，之后这些记忆因容量限制被压缩或遗忘。此时是否自动删除信念，或允许 Agent 通过 `evidence_memory_ids` 重新取得已经遗忘的证据？
- **推荐答案**：信念可以保留，但不得恢复已遗忘的证据。遗忘证据不会自动删除或降低信念，否则 MemoryService 实际上在替 Agent 更新 BeliefState。Agent 可以保留命题、主观置信度和形成信念时写入的受限简短理由，表达“仍相信结论，但不再记得全部依据”。`evidence_memory_ids` 永久保留在权威历史中供 Analyst View 审计，但 Agent 只能读取当前仍可访问的证据内容；已遗忘证据不能通过 BeliefState、引用 ID 或 Archive 重新取回。后续反思或新证据可以通过显式 `BeliefUpdated` 事件降低、撤销或修订信念。`stated_reason` 必须有严格长度限制，不能成为第二个无限 MemoryStore。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：证据记忆被遗忘时自动删除或降低信念；通过 `evidence_memory_ids`、BeliefState 或 Archive 恢复已遗忘证据；允许 `stated_reason` 无限制复制证据内容。
- **拒绝原因**：自动改信念会混淆 MemoryService 与 BeliefService 的责任；恢复证据会绕过遗忘；无限理由字段会重复制造 MemoryStore。

## 9. 分支、随机性与“因果”边界

### Q22：平行世界承诺因果归因，还是轨迹差异展示？

- **问题**：实时 LLM 导致相同初始分支也可能自然分化，是否仍称差异为干预因果效果？
- **推荐答案**：当前只展示平行轨迹差异；不承诺严格因果解释。真正的因果实验留给规则 Agent、Replay、重复采样或统计控制模式。
- **用户最终回答**：“只承诺轨迹差异展示，因果归因是无法保证的。”
- **状态**：`已接受`
- **被拒方案**：把任意分支差异直接归因于用户干预。
- **拒绝原因**：实时 LLM 和其他内生随机性会造成额外分化。

### Q23：`parent_event_ids` 是否代表真实因果链？

- **问题**：是否应只记录机械可验证的事件血缘、触发、观察、动作和相关流程？
- **推荐答案**：使用 `trigger_event_ids`、`observation_id`、`action_id`、`correlation_id` 和 `stated_reason`；UI 命名为 Event Lineage，不称因果证明。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：把 Agent 自述或事件先后关系当成一般性因果证明。
- **拒绝原因**：系统只能证明机械执行关系，不能证明心理或金融因果。

### Q28：内部随机性是否使用单一全局 RNG？

- **问题**：一个模块多抽一次随机数是否应改变其他模块的结果？
- **推荐答案**：使用按模块和 Agent 隔离的命名随机流；Checkpoint 保存流状态；分叉默认继承，重新播种必须显式指定。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：所有模块共享单一全局随机数消费顺序。
- **拒绝原因**：无关模块会互相干扰，分叉语义难以解释。

### Q90：多个平行分支是否必须现实并行计算？

- **问题**：逻辑平行是否要求多 CPU、多 Worker 同时推进？
- **推荐答案**：不要求。多个分支可处于 Running，本地 Worker 以小批事件轮转推进；任一时刻只有一个权威 SQLite 写事务；分支有独立虚拟时间、队列、随机流和进度；LLM 可并发等待；未来多 Worker 只能优化速度，不能改变分支语义。
- **用户最终回答**：“只要保证平行分支不互相污染就行。”
- **状态**：`已接受并澄清`
- **被拒方案**：把现实多核并行作为平行世界正确性的前提。
- **拒绝原因**：用户关心状态隔离，不要求现实计算同步或并行。

### Q91：分支是否允许共享可变内存和缓存？

- **问题**：Copy-on-Write 或缓存是否会让一个分支的修改泄漏到另一个分支？
- **推荐答案**：只共享不可变事件段、Schema、Persona 模板和内容寻址 Blob；可变订单簿、账本、队列、Agent 状态、钱包控制、收件箱和随机流均按 branch_id 隔离；首次写入生成私有副本；缓存键包含 branch_id + state_version；Golden Fixture 用状态哈希测试交叉污染；删除分支不能删除其他分支仍引用的 Blob。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：多个分支直接引用并修改同一可变对象，或缓存缺少分支/版本命名空间。
- **拒绝原因**：会造成最难发现的平行世界状态污染。

## 10. 事件原子性、时间与并发

### Q25：现实 LLM 响应时间是否改变虚拟时间？

- **推荐答案**：现实耗时只影响程序等待；虚拟动作时间由 LatencyComponent 决定；执行前按最新状态重新校验；超时产生显式事件。

### Q26：同一虚拟时刻决策的 Agent 是否基于同一世界版本？

### Q27：完全同时到达市场的动作如何排序？

### Q33：运行时硬不变量失败后是否继续？

### Q40：运行控制是否也属于世界事件？

### Q48：是否冻结最小分支生命周期状态机？

- **推荐答案**：采用 `Initializing`、`Ready`、`Running`、`Paused`、`Quiescing`、`Completed` 和 `Faulted`。保存成功后回到保存前状态；checkpoint 是制品而非长期状态；从 checkpoint 创建的新分支从 `Ready` 开始；禁止未定义的跨状态操作。

- **状态**：`已接受`
- **被拒方案**：没有明确状态机，依靠各模块自行判断操作是否合法。
- **拒绝原因**：会产生调度竞态、重复运行和故障状态继续写入的问题。

### Q65：同一分支是否允许多个 Worker 同时推进？

- **问题**：并发 Agent 决策是否意味着多个 Worker 可以同时写同一事件队列、账本和订单簿？
- **推荐答案**：每个 branch_id 只能有一个持写入租约的 Simulation Worker；LLM、分析和读取可并发，但世界事件串行提交；控制命令带幂等键并按分支序列化；Worker 心跳续租，失联后新 Worker 从最后原子提交点恢复；禁止最后写入者获胜。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：多个 Worker 同时推进同一分支并依赖最后写入者获胜。
- **拒绝原因**：会破坏事件原子性、稳定排序和资产守恒。

### Q66：公共信封是否允许任意业务 payload？

- **问题**：Event、Action 和 Observation 是否只使用一个由各模块自行解释的 `payload: {}`？
- **推荐答案**：使用统一信封保存公共元数据，但每种业务载荷都有独立、严格且版本化的 JSON Schema；所有 API、队列、存档和模块边界校验；已发布版本不可原地修改；未知类型或版本不能静默忽略；代码内部使用类型化对象；Archive 保存实际 Schema 版本集合。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：让业务模块自由解释任意字典，或原地改变已发布 Schema。
- **拒绝原因**：跨模块契约无法验证，旧事件和存档会产生歧义。

### Q83：分支何时进入 Completed？

- **问题**：现实运行过久、外部服务失败、事件耗尽或用户停止分别如何影响生命周期？
- **推荐答案**：场景必须定义 max_sim_time；到达后完成当前原子事件并停止；事件队列提前为空时以 event_queue_exhausted 完成；用户 Stop 在下一事件边界以 user_stopped 完成；最大事件数或硬资源上限必须带明确原因受控完成或 Faulted；ProviderBudget 耗尽只触发降级；Completed 与 Faulted 分开；Completed 历史不可追加但可从 checkpoint 分叉。
- **用户最终回答**：“是的，我接受。”
- **状态**：`已接受`
- **被拒方案**：因现实时间过长或外部服务失败而静默结束分支。
- **拒绝原因**：终止原因将不可解释，也可能留下不完整状态。

## 11. 市场、订单簿与背景环境

- **被拒/暂缓方案**：Framework Alpha 同时实现群聊、媒体机构、论坛、邮件和多个社交平台。
- **拒绝原因**：一个公共流和私聊已足以验证局部传播、权限、延迟和注意力闭环。

### Q58：私聊是否保证接收者立即看到？

- **问题**：DirectMessage 是否绕过活跃状态和注意力，自动成为已读信息？
- **推荐答案**：私聊不经过公共推荐算法，但仍依次经过 Sent、Delivered 和 Viewed；权限、网络、离线或过期可导致送达失败；成功送达进入私人收件箱，是否阅读、相信、记忆、转发或行动由 Agent 决定；只有读取后内容才进入 ObservationPacket。
- **用户最终回答**：“当然理应如此。”
- **状态**：`已接受`
- **被拒方案**：私聊发送即送达、送达即阅读。
- **拒绝原因**：会绕过通信延迟、Agent 活跃状态和注意力约束。

### Q59：PublicFeed 信息是否广播给所有 Agent？

- **问题**：公开发布是否等于全员即时曝光？
- **推荐答案**：从关注来源、转发和少量 seeded exploration 生成候选；按权限、屏蔽和有效期过滤；经过频道延迟送达；AttentionProfile 按主题、来源、活跃状态和周期上限选择查看；未读内容可保留或过期；过程使用命名随机流并记录事件；内部排名分数不暴露给 Agent。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：公共信息全员广播，或公开发布自动等于所有 Agent 已查看。
- **拒绝原因**：会消除局部曝光、推荐、延迟和注意力机制。

### Q60：转发、改写和泄露是否修改原信息对象？

- **问题**：信息传播时是否原地修改原始 InformationItem？
- **推荐答案**：原信息不可变；原样转发、摘要、评论、断章取义、改写和私聊泄露均创建派生信息；内核保存真实 derived_from_info_ids；公开 claimed_source 可以省略、错误归因或伪造；真实来源链只供内核与管理员分析，接收者只依据可见信息形成信念。
- **用户最终回答**：“是的，我接受。”
- **状态**：`已接受`
- **被拒方案**：原地覆盖信息内容，或强制把全部真实来源链暴露给所有 Agent。
- **拒绝原因**：前者破坏历史，后者消除错误归因、泄露和来源判断的空间。

### Q77：PublicFeed 和 Attention 参数是否写死？

- **问题**：探索比例、候选上限、延迟、注意力窗口和未读有效期是否是系统常量？
- **推荐答案**：全部成为可解析、可保存的 ChannelPolicy 与 AttentionProfile 参数；提供明确标注为合成值的默认配置；Golden Fixture 固定测试参数；未来产品场景再校准。初始化后保存最终参数，运行中改变必须事件化或从保存点创建分支。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：把未经校准的曝光和注意力数字硬编码为现实行为规律。
- **拒绝原因**：默认值只是工程基线，不能伪装成实证结论。

### Q130：CognitiveProfile 与 AttentionProfile 是否应合并？

- **问题**：是否用一个模糊的“聪明程度”字段同时表达看到了什么和能处理多少？
- **推荐答案**：不合并。AttentionProfile 决定有限注意力投向哪些渠道、主题和对象；CognitiveProfile 决定对已注意内容的处理容量、分析深度和重新规划能力。信息依次经过权限、送达、注意力选择、认知处理和记忆。高认知能力不自动扩大可见范围，高注意力容量也不保证正确理解。两套 Profile 可以显式相关，但分别保存和展示。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：用单一能力值合并权限、曝光、注意力、认知处理和记忆。
- **拒绝原因**：无法区分没收到、没注意、没处理和没记住，也可能使认知能力绕过信息权限。

### Q131：AttentionProfile 是固定偏好，还是允许 Agent 主动重新分配注意力？

- **问题**：Agent 是否能根据目标和事件改变下一窗口对市场、PublicFeed、DirectMessage 等来源的投入？
- **推荐答案**：采用三层模型：`base_attention_profile` 保存初始化渠道/主题偏好、活跃时段和基础容量；`attention_allocation_state` 保存当前窗口各来源配额；带来源、有效期和上下限的 `attention_modifiers` 表达亏损、突发信息、关系变化或用户干预造成的临时偏移。StrategyPlan 可在总容量内重新分配，但不能绕过权限、延迟或屏蔽；增加一个渠道必须减少其他渠道；重大信息只提高显著性，不保证被查看。所有 modifier 事件化。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：AttentionProfile 永久固定；注意力重分配凭空扩容；重大信息自动保证查看；ProviderBudget 修改注意力状态。
- **拒绝原因**：前者无法表达策略性关注，后者会绕过有限注意力和世界/控制面边界。

### Q42：信任和影响力是全局真值还是主观判断？

- **问题**：关系图是否只有一个共享的 `trust=0.8`？
- **推荐答案**：消息、协议和付款是客观事件；联系权限是事实；`TrustBelief(A,B)` 是 A 的私人判断；影响力随观察者、受众、渠道和历史变化。
- **用户最终回答**：“理应如此。”
- **状态**：`已接受`
- **被拒方案**：单一全局信任值或固定影响力属性直接暴露给所有 Agent。
- **拒绝原因**：无法表达非对称信任、误判和欺骗。

## 15. 性能与验收基线

### Q71：Framework Alpha 是否需要量化性能门槛？

- **问题**：仅说“能够运行”是否足够，还是需要具体工作负载和响应时间？
- **推荐答案**：建立第一版基准：一个 CLOB、50 个规则/Replay Agent、一个背景部门、6 小时虚拟时间、每分支至少 250,000 个事件、三个分支；核心计算不超过 2 分钟，完整实验保存/加载不超过 15 秒，checkpoint 跳转不超过 2 秒，峰值内存不超过 4 GB；外部网络等待单独记录。
- **用户最终回答**：接受，但追问这些事件数和峰值内存设置如何证明科学合理。
- **状态**：`已接受但要求实证校准`
- **被拒方案**：没有任何规模和时间边界地声明框架“可运行”。
- **拒绝原因**：无法判断架构是否达到可用程度。

### Q72：Q71 数值是永久承诺还是初始 Benchmark Profile？

- **问题**：如何让性能门槛具有可解释依据，而不是凭空选择数字？
- **推荐答案**：把当前数字定义为第一版工程假设；保存完整工作负载参数和事件数推导；指定参考硬件和冷/热启动；测量 p50、p95、内存和磁盘；Phase 1 后按实测校准；变更阈值必须附数据和原因；保留至少 30% 余量；实时 LLM 延迟单独测量。
- **用户最终回答**：“可以，我接受。”
- **状态**：`已接受`
- **被拒方案**：把初始估算冒充科学结论，或为通过测试而静默降低阈值。
- **拒绝原因**：性能目标必须来自可复现工作负载和实测。

### Q73：内核 Fixture/Replay 测试是否必须完全确定？

- **问题**：实时 LLM 不可重复，是否意味着内核也不需要确定性测试？
- **推荐答案**：DeterministicTestMode 禁止实时外部输入，使用固定快照、规则 Agent 或 Replay、冻结 Manifest 和命名随机流；相同输入重复运行必须产生相同规范化事件哈希链，并在 CI 重复验证。正常实时 LLM 运行仍不承诺重执行一致。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：因为 LLM 不确定而放弃验证内核确定性。
- **拒绝原因**：会掩盖调度、数值、并发和状态泄漏缺陷。

### Q74：是否需要固定的端到端 Golden Sandbox Fixture？

- **问题**：单元和契约测试是否足以证明基础设施形成闭环？
- **推荐答案**：还必须有一个固定端到端 Fixture，覆盖混合初始化、现货 CLOB、背景部门、不同 Agent、公共流与私聊、注意力、有限记忆、规则/Replay 决策、多钱包、用户干预、交易结算、保存、两个分支、整个实验加载续跑、双视角回放和损坏检测。它只验证基础设施，不解释金融因果。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：只依赖孤立单元测试，没有完整纵向闭环验收。
- **拒绝原因**：组件分别通过不代表它们的契约、状态和时序能够正确组合。

### Q75：Golden Fixture 固定完整事件哈希还是只检查结果？

- **问题**：如何避免只检查最终结果漏掉中间错误，同时避免跨版本 Golden 过度脆弱？
- **推荐答案**：采用两层断言。资产守恒、观察隔离、交易对账、分叉一致、Archive round-trip、历史不可变、损坏拒绝和生命周期合法等语义断言跨版本稳定；完整规范化事件 Golden Hash 只在同一内核和 Schema 版本内固定，合法变化需审查差异并显式更新，禁止自动重录。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：只检查最终价格/余额，或要求所有未来版本保持同一个完整事件哈希。
- **拒绝原因**：前者覆盖不足，后者会阻碍合法 Schema 和实现演进。

## 16. 部署与 API 边界

### Q84：项目是否必须部署云端并依赖长连接？

- **问题**：Framework Alpha 是否能本地运行；本地客户端连接云后端时是否必须依赖永不断开的 WebSocket/SSE？
- **推荐答案**：Framework Alpha 必须支持单机离线运行：前端、API、Worker、虚拟账本、CLOB 和存储均可本地部署，Fixture 与 Replay 模式无需外网。云端只在多用户、长任务、并行调度、集中 Secret 或共享 Archive 时可选。使用 REST 提交幂等命令，SSE 推送进度和已提交事件；断线后通过 Last-Event-ID 或 REST 恢复；长连接不承担权威状态；当前不实现 WebSocket。
- **用户最终回答**：“好的，我接受。”
- **状态**：`已接受`
- **被拒方案**：把云端作为 Framework Alpha 必需条件；让系统正确性依赖永不断开的长连接；同时实现 WebSocket 和 SSE。
- **拒绝原因**：增加部署和双写通道复杂度，且任何长连接都可能断开；服务端持久状态才应权威。

### Q85：本地模式是否依赖 PostgreSQL、Redis、S3 或 Docker？

- **问题**：本地可运行是否仍要求用户安装外部基础设施？
- **推荐答案**：默认使用 SQLite WAL 保存实验、事件、动作、观察索引和运行状态，本地内容寻址目录保存 checkpoint、LLM 记录和 Blob；不需要 Redis、S3、消息队列或 Docker；Blob 先写入并哈希，再由 SQLite 原子引用；StorageAdapter 保留未来 PostgreSQL 与对象存储接口，只有实测瓶颈或多用户需求出现后升级。
- **用户最终回答**：“是的，我接受。”
- **状态**：`已接受`
- **被拒方案**：Framework Alpha 默认强制安装 Docker、PostgreSQL、Redis 或 S3 模拟器。
- **拒绝原因**：违背一键本地运行目标，且当前单机负载未证明需要这些组件。

### Q86：Framework Alpha 是否拆成多个独立服务？

- **问题**：是否提前引入微服务、消息总线和分布式 Worker？
- **推荐答案**：采用模块化单体；一个本地命令运行 API、Worker 调度、SSE 和静态前端；内核不依赖 Web 框架；LLM 可异步但不需要独立服务；分支失败只 Fault 当前分支；以后再按多机需求拆分。
- **用户最终回答**：“是的，我接受。”
- **状态**：`已接受`
- **被拒方案**：当前提前设计微服务、消息总线和分布式部署。
- **拒绝原因**：增加运维和一致性复杂度，没有当前需求依据。

### Q87：权威仿真是否运行在浏览器中？

- **问题**：本地运行是否意味着前端持有内核和持久状态？
- **推荐答案**：浏览器只负责配置、命令、实时展示和回放；本地 Python 后端持有权威状态并执行仿真；关闭或刷新浏览器不影响分支；前端不能直接写 SQLite 或世界状态；后端重启从已提交状态恢复；生产前端由同一 localhost 后端提供，不要求单独 Node 服务。
- **用户最终回答**：“是的，我接受。”
- **状态**：`已接受`
- **被拒方案**：把权威内核、账本和持久状态放入浏览器。
- **拒绝原因**：浏览器生命周期、刷新和断线不应影响仿真正确性。

### Q89：本地 API 是否默认监听所有网卡且无保护？

- **问题**：是否允许默认 `0.0.0.0`、宽泛 CORS 和无会话限制？
- **推荐答案**：默认仅监听 `127.0.0.1`；前端与 API 同源；拒绝未知 Origin；每次启动生成本地会话令牌，写命令、SSE 和 Archive 下载均校验；Secret 不进入 URL、日志或 Archive；远程监听需显式开启，正式认证和 TLS 不属于默认 Alpha 范围。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：默认监听所有网卡、开放宽泛 CORS 或不限制本地写命令。
- **拒绝原因**：可能被同一局域网或恶意网页访问私人 Persona、私聊和 Archive。

## 19. 依赖关系

1. **链初始化方式**决定地址采样、Portfolio 合成、初始账本和保存内容。
2. **目标资产与市场范围**决定链上需要读取的数据、背景部门资产和订单簿初始化。
3. **Persona/观察/记忆分层**决定 LLM Prompt 构造、checkpoint 内容和 Agent 视角回放。
4. **事件原子提交**是可靠保存、故障恢复、不可变历史和分支的前提。
5. **事件边界 checkpoint**依赖不存在半完成状态；保存前通过 `Quiescing` 结算所有未完成异步 LLM 请求。
6. **同版本续跑**依赖保存 Agent 全部显式状态、事件队列、订单簿、账本、随机流及运行时版本。
7. **轨迹差异展示**依赖保存实际 Observation、LLM 输入输出和事件血缘，但不产生严格因果结论。
8. **Background Market Sector**依赖资产供给分配和统一结算管线，否则无法满足守恒。
9. **用户运行期干预事件化**依赖 Action Contract、权限校验和仿真平面/控制平面分离。
10. **逻辑自包含 Archive**依赖将外部输入实际内容持久化，而不是只保存外部引用。
11. **同版本续跑**依赖分支生命周期状态机和单控制者 Agent-Wallet 模型保持一致。
12. **合成 Portfolio**依赖 ChainSnapshotInitializer 的特征数据，但不依赖地址身份分类或可执行链状态。
13. **CLOB 资产守恒**依赖整数/定点表示、明确量化规则和带保护的市价单。
14. **背景订单流**依赖已记账资产和显式补充事件；流动性耗尽是正常状态而非系统故障。
15. **局部信息曝光**依赖 PublicFeed 候选生成、DirectMessage 送达语义和 AttentionProfile 的分层处理。
16. **Agent View**依赖保存实际 ObservationPacket、有限记忆状态和同一回放时间轴。
17. **Agent 连续性**依赖有限记忆与预配置 LLM 降级链全部进入 checkpoint。
18. **Archive 自包含**不包括秘密凭证；新分支运行外部调用时依赖运行环境重新提供凭证。
19. **事件原子性**依赖单分支权威写入租约、幂等命令和类型化 Schema 校验。
20. **完整实验 Archive**依赖所有保留分支分别 Quiescing，并通过事件链、状态和 Blob 哈希校验。
21. **性能门槛**依赖版本化 Benchmark Profile、参考硬件、可复现测量和基于证据的校准。
22. **Framework Alpha 完成**依赖单元测试、契约测试、确定性重复运行和 Golden Sandbox Fixture 全部通过。
23. **Persona personalization**依赖版本化结构模板、命名随机流和最终解析 BasePersona 入档。
24. **LLM 调度**同时受世界内 CognitiveBudget 和控制面 ProviderBudget 约束，耗尽路径必须可区分。
25. **Portable Archive**依赖应用级 Schema，而不能依赖数据库备份或可执行内容。
26. **ChainSnapshotInitializer**依赖带来源和覆盖率的 HolderDataProvider，但 Framework Alpha 验收不依赖实时第三方数据。
27. **本地市场独立性**依赖合成 USDx、独立 initial_mid_price 和启动后不再同步外部价格。
28. **本地/云端可移植性**依赖相同 REST/SSE 契约、服务端权威状态和断线恢复。
29. **一键本地运行**依赖模块化单体、SQLite WAL、本地内容寻址存储和同源静态前端。
30. **用户历史承诺**依赖权威事件与固定 Archive 永不自动清理，磁盘不足时受控暂停或拒绝新工作。
31. **本地隐私边界**依赖回环监听、同源策略、本地会话令牌和远程模式显式开启。
32. **分支隔离**允许共享不可变内容，但所有可变状态、随机流和缓存必须带分支与状态版本命名空间。
33. **统一回放体验**依赖 branch/cursor 投影接口；实时只是 cursor 跟随最新提交点。
34. **前端性能**依赖 SSE 推送节流投影与显著事件，而完整原始事件通过查询获取。
35. **原子初始化**依赖所有字段由默认或显式来源完整解析，并在 staging 通过所有不变量后一次提交。
36. **低配置负担**依赖版本化默认值、分层界面和突出异常而非展示全部内部字段。
37. **安全 Archive 导入**依赖隔离 staging、资源限制、Schema/哈希校验和禁止自动执行。
38. **正常 Quick Start**依赖用户选择外部链和目标 Token、实时 LLM Provider 预检通过，以及其余字段由版本化默认值补齐。
39. **链 Provider 切换**依赖备用 Provider 预先配置、同链同最新最终确认区块证明、单一来源输入和预览披露。
40. **Agent population**依赖版本化默认 preset、独立于 Holder 地址数量的合成映射、seeded 生成和启动前容量预检。
41. **多 Agent LLM 调度**依赖每个 Agent 独立上下文和记录，并允许只在传输层批处理。
42. **显式 Agent 的市场影响力**依赖用户配置的 Agent 数量、链上可纳入供给、合成 Portfolio 分布、订单预算和盘口深度联合校准；不再依赖固定显式/背景资本比例，普通参与者保持独立个体建模，未显式部分由已记账背景部门承接。
43. **200 个独立 Agent 的运行**依赖同一 LLM 服务复用能力与每个 Agent 的上下文、记忆、响应归属严格隔离；共享模型不能变成共享语义状态。
44. **显式活跃资产分配**依赖用户配置的 Agent population、链上可纳入供给、版本化合成分布、统一初始计价口径和 Token/USDx 分别守恒，并与多重身份标签、Capability、Persona 和派生行为标签解耦；不再依赖固定 70/30 或五档比例。
45. **链上 Holder 校准**依赖特殊地址先分类隔离、余额分层抽样、匿名合成与总量约束；分类置信度不足时不得把聚合地址解释成单个主体。
46. **背景参与激活**依赖来源桶、ParticipationPolicy、已记账背景账户和事件化转移；锁仓或协议约束资产不具备该路径，当前不设由 Q110 继承的固定资本上限。
47. **合成 USDx 守恒**依赖本地活跃流通市值、版本化 quote coverage，以及初始化时记账但不计入活跃购买力的背景 USDx 储备；后续激活只能转账，不能静默增发。
48. **初始盘口可解释性**依赖背景部门真实资产锁定、基于基准冲击反推的深度，以及 `sim_time = 0` 开盘屏障；显式 Agent 在初始化后才自主参与市场。
49. **多 Agent LLM 容量**依赖场景化预检、受限现实并发池和独立请求上下文；Agent 数量、待处理请求数和实际 in-flight 数必须分开。
50. **认知异质性**依赖不可变基础 CognitiveProfile、可消耗预算状态和事件化 modifier，并必须与 funding profile、role tag、财富和 ProviderBudget 解耦。
51. **认知流水线**依赖权限/送达、AttentionProfile、CognitiveProfile 和 MemoryService 依序衔接；任一后层不能反向扩大前层可见信息。
52. **可回放记忆**依赖带来源的写入提案、容量校验、事件化压缩/遗忘和不可变修订链；Archive 保留事实不等于 Agent 仍能访问事实。
53. **主动记忆检索**依赖 Agent 当前可访问的 MemoryStore、CognitiveBudget 消耗和不泄露遗忘状态的结果边界；检索不能扩大原有观察权限。
54. **主观信念演化**依赖 Memory 与 Belief 分离、当前可访问证据的引用、事件化更新和竞争假设并存；内核只验证过程，不提供全局真值纠正。
55. **信念置信度解释**依赖 Agent 内部、同一 belief set 的比较语境；跨 Agent 聚合不得被解释为客观概率或市场真值。
56. **信念与遗忘解耦**依赖 BeliefService 独立更新和证据访问控制；权威历史可以保留证据引用，但 Agent 不得借引用恢复已遗忘内容。
57. **独立 Agent 决策**依赖固定 Agent Decision Pipeline、Agent 私有状态隔离和只由 Observation Packet 触发的确定性 Decision Opportunity；不可见事件不能直接唤醒 Agent。
58. **Agent 决策审计**依赖不可变 Agent Decision 关联 Observation 和 Agent 状态版本，并完整记录认知、策略、动作与预算提案。
59. **局部提案失败语义**依赖整体边界先校验、状态所有者分别校验内部提案、失败沿显式依赖传播，并原子保存完整 Decision Outcome。
60. **单 Agent 规划串行性**依赖每个 branch/Agent 只有一个未结 Planning Request；等待期间 Reactive Controller 使用最后有效计划，新触发器合并等待后续规划。
61. **规划虚拟时间语义**依赖请求创建时确定 Planning Activation Time；现实返回速度只能改变计算耗时，不能改变虚拟生效顺序。
62. **计划适用性**依赖显式取消、超时、战略版本替代、有效期和必要前提冲突；普通世界变化和更新 Observation 不自动使计划失效。
63. **规划预算记账**依赖开始前预留、开始后消耗 CognitiveBudget，以及按实际调用独立计算 ProviderBudget；同一认知决策的技术重试不重复消耗认知次数。
64. **Agent 状态冲突校验**依赖整体 Agent Revision 用于审计、组件 revision 用于真实依赖；无关组件更新不得制造伪冲突。
65. **一次决策的动作集合**依赖有界、零到多个且顺序无语义的 Action Proposal Set；跨动作原子性只能由明确领域动作定义，不能由通用数组隐式获得。
66. **动作资源竞争**依赖确定性准入顺序和按 `action_id` 关联的 Action Reservation；后续动作必须看到已经减少的可用资源。
67. **Pending Action 生命周期**独立于后续 Strategy Plan；终止依赖显式取消、有效期或声明的 strategy revision，而已经进入 World 的订单必须通过领域动作撤销。
68. **同一决策内的局部失败传播**依赖带 ID 的 Proposal Dependency 和固定正向阶段顺序；循环、缺失或逆向依赖属于整体结构错误。
69. **决策可解释审计**依赖有界结构化 Decision Rationale，并与 Provider 原始请求/响应记录和 Agent Memory 分离；三者不能互相替代或自动转化。
70. **规划期主动查询**依赖同一 Planning Request 内有界、只读且受权限和预算约束的 Planning Tool Loop；中间调用不能产生 World 动作或额外 Agent Decision。
71. **Planner 输出信任边界**依赖原始响应留存、确定性结构校验和有限修复；成功解析后的提案语义仍由状态所有者校验，宿主不得静默纠正业务含义。
72. **异步规划审计**依赖原始 Agent Decision 立即关闭且保持不可变；规划成功在生效边界形成引用原决定、请求和相关观察的新 Agent Decision。
73. **同一观察的决策去重**依赖先完成 World 事件并冻结版本，再聚合普通、定时、风险和规划结果触发器；同一 Agent 与 Observation Packet 最多运行一次 Runtime。
74. **Planning Request 状态恢复**依赖 `Queued -> Running -> Ready -> Terminal` 的事件化阶段和独立终态 outcome；迟到响应只能记录，不能重开请求。
75. **Planning Request 取消语义**依赖排队前合并替代或显式授权终止；失败、超时、适用性拒绝和保存 Quiescing 均有不同语义，不能复用 canceled。
76. **重规划请求抑制**依赖 Agent 规划状态中的有界 Replan Trigger Accumulator、确定性同类合并和触发器快照的原子转移；权威事件日志保留原始事实。
77. **跨 Agent 统一策略接口**依赖公共 Strategy Plan Envelope、版本化类型 Directive 和 Capability 校验；自由文本不能参与 Reactive Controller 控制流。
78. **单一策略真值**依赖每个 Agent 只有一个活跃 Strategy Plan revision，并通过声明基线的完整自包含新计划原子替换；历史 revision 不可变。
79. **规划与动作职责分离**依赖 Provider 只输出候选 Strategy Plan 和 Rationale，Agent Runtime 在生效边界校验后由确定性 Reactive Controller 生成 Action Proposal。
80. **无计划降级**依赖 Reactive Controller 的版本化 `hold_and_protect` 配置、显式撤销动作和不新增承诺；Background Market Sector 继续提供初始化盘口。
81. **计划条件确定性**依赖 activation precondition、directive guard、constraint 和 replan condition 的分离语义，以及只引用 Agent 合法观察和私有状态的版本化谓词。
82. **Directive 去重与节流**依赖声明式 emission mode、稳定 action ID 和按 plan revision 隔离的 Directive Execution Cursor；动作结果不能反向重置已记录发射尝试。
83. **自身动作反馈**依赖 World 生成不可变 Action Receipt、保证进入发起 Agent 的下一观察，并把异常和状态变化按观察屏障聚合；Receipt 不成为第二状态源。
84. **Agent 资源决策**依赖 Observation Packet 中保证可见的 Agent Account Snapshot；权威余额、预留、持仓和订单状态仍由 World 所有，缺失或不一致时采用 hold_and_protect。
85. **Agent 信息创作**依赖通信 Capability、类型化 CommunicationDirective 和 World 校验；Agent-Authored Information 可传播但不成为系统真值或自动信念。
86. **规划认知输入一致性**依赖 PlanningRequestProposal 先等待所依赖 Memory/Belief 提案提交，再记录实际认知 revision；不采用推测状态。
87. **认知更新与计划适用性**依赖默认审计引用和显式 activation precondition 的区分；普通认知变化触发后续重规划，不自动废弃当前候选。
88. **开盘 Agent 公平性**依赖 `sim_time = 0` 首次 Observation 触发每个显式 Agent 的首个规划、统一容量预检和生效前 hold_and_protect；背景部门不进入 Agent Pipeline。
89. **未来行为重评估**依赖 Directive Wakeup 而非未来 Action 脚本；Wakeup 时重新冻结世界、构造观察并由 Controller 形成动作，已准入 Pending Action 仍遵循独立承诺语义。

## 20. 潜在矛盾与需要修订的旧表述

1. **“可复现”含义冲突**
   - 原始设计稿把“相同场景、参数和 seed 生成相同事件日志”列为目标和测试。
   - 当前共识不承诺实时 LLM 下的全流程重新执行一致。
   - 建议后续把术语拆为：精确历史回放、内部确定性组件测试、实时 LLM 运行不保证重执行一致。

2. **“因果”表述冲突**
   - 原始设计稿使用 Causal Narrative、因果图和干预归因。
   - 当前共识只记录事件血缘并展示分支轨迹差异，不承诺一般性因果归因。

3. **“永久回看”与同版本范围**
   - 用户最初使用“永久回看”，随后明确当前不考虑新版本兼容。
   - 当前可执行定义应为“在同版本运行时和数据仍可用的条件下完整回看”；真正跨版本永久性已暂缓。

4. **“fork 链”与“合成 Portfolio”**
   - 该冲突已解决：Framework Alpha 使用 ChainSnapshotInitializer，不运行完整链 fork。
   - 原始设计稿中的 Chain Fork 表述仍需在后续修订时移出当前验收范围。

5. **Agent 类型与 Capability**
   - 该冲突已解决：角色和 Persona 只影响倾向；硬权限由可事件化授予和撤销的 Capability 表达。
   - Framework Alpha 不支持 Capability 自由转让或再授权。

6. **Quick Start 的“默认”与“外部输入”**
   - “默认”只覆盖市场、Agent、Persona、信息、预算等沙盒参数，不覆盖链和目标 Token 的选择，也不覆盖正常模式的实时 LLM 可用性。
   - Fixture/Replay 是显式测试或回放模式，不是链 Provider 失败时的隐式后备。

7. **少量显式普通 Agent 与真实 Holder population 的数量级冲突**
   - Q110 已冻结显式 Agent 默认主导活跃交易资本，但这不意味着可以把少量字面意义上的普通散户直接放大为大额持仓主体。
   - 该冲突已通过 Q111-Q114 收敛：200 个显式 Agent 均为独立个体；其余参与者进入背景部门；普通个体占绝大多数人数但只占显式活跃净值 5%-10%；同一 LLM 服务可处理多个隔离的 Agent 请求。
   - 这是一种“精细模拟个体子集 + 聚合剩余市场”的边界，不声称 200 个 Agent 等比例代表全部 Holder。

8. **Agent 身份类别与资金初始化档位冲突**
   - Q18 已规定角色不决定权限或固定行为，Q114 又使用五个角色名称分配默认活跃资产。
   - 该冲突已由 Q115-Q116 解决：单一、不可变的 funding profile 只记录初始化资金来源；role tags 可多选；Capability、Persona、Components 和派生行为标签分别表达不同维度。
   - “既是 KOL 又是巨鲸”等多重身份不会重复分配资产，也不会自动改变权限。

9. **显式 Agent 活跃资本占比与初始盘口所有权冲突**
   - Q110 要求显式 Agent 默认控制约 70% 活跃资本，但 Q31 规定初始盘口订单属于 Background Market Sector。
   - Q123 已澄清两者不矛盾：资本占比描述可交易资产，初始盘口所有权描述环境起始状态；显式 Agent 在初始化后根据观察自主挂单或交易。
   - Q124 进一步要求背景生成器在第一次 Agent 观察前不得推进市场，避免背景盘口产生时间优势。

10. **背景激活上限与运行期财富比例冲突**
   - Q119 曾表述背景激活总量受 Q110 的 30% 上限约束，可能被误读为背景净值永远不得超过 30%。
   - Q190 已进一步废止固定 70/30 资本比例；背景激活只受来源桶、可用储备和显式 ParticipationPolicy 约束，不继承 Q110 的固定资本上限。
   - Q125 关于不得为了恢复任意比例而再平衡、拒绝成交、强制减仓或补资的结论保留。

11. **主观信任与 BeliefState 的实体重复风险**
   - Q42 已拒绝全局统一 trust/influence 真值，Q138 又引入有限的结构化 BeliefState。
   - 当前边界是：信任属于 Agent 对某主体或信息源的专门 BeliefState，不另建一套权威信任真值；可见影响力指标仍可作为公开观察输入，但不会自动成为任何 Agent 的信念。
   - Q139 允许互相竞争的信任或市场假设并存，避免以单一分数覆盖不确定性。

12. **Agent 是可配置组件与内部固定流程的表述冲突**
   - Q142 将 Agent 冻结为沙盒中的独立、可配置决策组件，可能被误解为其内部结构完全任意。
   - Q143 已澄清：Agent 对外是统一组件边界，对内所有显式 Agent 采用固定决策骨架；差异来自各环节的实现和参数，而不是任意拓扑或角色专属生命周期。
   - Agent Runtime 只协调单个 Agent 的决策循环，不表示 Agent 之间存在 Supervisor、Manager 或 Sub-Agent 管理层级。

13. **现实 LLM 等待与虚拟计划生效的时间冲突**
   - Q25 已冻结现实 LLM 响应时间不改变虚拟时间，Q147 又允许等待 Planner 时由 Reactive Controller 继续运行旧计划。
   - Q148 将既有原则细化为 Planning Activation Time：请求创建时确定虚拟生效时刻，提前返回不得提前生效，迟到只增加现实等待或进入超时降级。
   - Q149 进一步规定计划只在明确失效条件下淘汰，不能因为世界一般性变化或出现更新 Observation 就自动废弃。

14. **Provider 记录与“不保存思维链”的表述冲突**
   - 既有设计要求 LLM 请求与结构化响应进入不可变运行记录，Q156 又拒绝要求或保存完整自由文本思维链。
   - 两者对象不同：实际发送的 Provider 请求和实际收到的结构化响应是回放、成本和故障诊断所需的基础设施记录；Decision Rationale 是 Agent 对决定依据的有界结构化说明。
   - 两者都不自动写入 Agent Memory，也不得借“审计”名义要求 Provider 暴露隐藏思维链；其他 Agent 不能直接访问这些记录。

15. **异步 Planner 与“一次观察一次不可变决定”的边界冲突**
   - Q145 要求 Agent Decision 不可变，Q147 又允许 Planner 等待期间继续产生即时决定；因此异步结果不能回写仍在等待的原决定。
   - Q159 规定原决定立即关闭，规划完成后形成引用原决定和 Planning Request 的新 Agent Decision；规划失败只结束请求。
   - Q144 原先只允许实际 Observation Packet 触发决策，Q160 进一步规定规划结果必须使用最新已保存的合法 Observation Packet，并与同一观察屏障内其他触发器合并；不得伪造观察或对同一 Agent 与 Observation Packet 重复决策。

16. **Q38 的 LLM 动作提案与固定 Planner/Controller 职责冲突**
   - Q38 为排除任意代码而笼统允许 LLM 输出“声明式策略和动作提案”，可能被解释为 Provider 可以直接构造 World Action Proposal。
   - Q143 后续冻结了 `Strategic Planner -> Reactive Controller -> Action Proposal` 的固定职责顺序；Q166 据此将旧表述收窄为 Provider 只能输出候选 Strategy Plan、Rationale 和类型化行动意图。
   - 真正的 Action Proposal 必须由 Reactive Controller 在 Planning Activation Time 基于最新合法观察确定性形成；这属于职责细化，不重新允许任意代码。

17. **“无计划时 Reactive Controller 仍运行”的行为歧义**
   - Q62 已规定没有有效计划时仍运行 Reactive Controller，但只说明不产生新战略动作，没有明确是否可以交易、发消息或撤销已有承诺。
   - Q167 将其细化为版本化 `hold_and_protect`：允许认知更新和请求规划，不增加风险或建立新承诺；保护已有承诺必须通过显式 Action 和事件完成。
   - 这不会静默撤销 Q154 所保护的 Pending Action 或开放订单，也不会把 Background Market Sector 伪装成 Agent 的默认计划。

18. **注意力过滤与自身操作事实的保证可见性**
   - 既有 Observation Pipeline 要求信息先经过权限、送达和 AttentionProfile，可能被误解为 Agent 也能忽略自己的动作结果、余额和订单状态。
   - Q170-Q171 将 Action Receipt 和 Agent Account Snapshot 定义为控制者保证可见的私有操作输入；它们不受社交注意力选择，但仍只能通过 Observation Packet 进入 Agent Runtime。

## 24. Agent 组件与决策流水线

### Q142：Agent 层级是单个 Agent 的内部决策结构，还是 Agent 之间的组织层级？

- **问题**：现有项目尚未实现具体 Agent 时，“Agent 层级”究竟指单个 Agent 内部的认知与动作协调，还是多个 Agent 之间的 Supervisor、Manager 或 Sub-Agent 关系？
- **推荐答案**：每个初始化 Agent 是相互隔离的独立决策主体；Agent 对外是可配置组件，只接收自身观察与私有状态并形成提案。Agent Runtime 描述单个 Agent 内部的决策协调，不引入 Agent 之间的组织层级；联盟、影响、通信和协议继续由社会关系与事件表达。
- **用户最终回答**：用户先澄清“每个初始化后的 Agent 都应该是相互独立的，Agent 只是一个待设定的组件”，在进一步展示 ObservationService、AgentRuntime、Memory/Belief、Strategic Planner、Reactive Controller、Action Proposal 与 World 执行边界后，确认该结构有道理。
- **状态**：`已澄清并接受`
- **最终边界**：每个 Agent 独占 Persona、Observation、Memory、Belief、预算、策略状态与随机流；Agent 无权直接修改 World；当前不引入 Agent 间管理层级。
- **被拒方案**：把 Agent Runtime 解释为多个 Agent 的共享认知或上下级管理系统。
- **拒绝原因**：会破坏 Agent 独立性，并增加当前领域并不需要的组织实体。

### Q143：Agent 内部流程采用固定骨架，还是允许任意增删和连接模块？

- **问题**：用户配置 Agent 时，是只替换各认知环节的实现和参数，还是可以为不同角色设计完全不同的调用拓扑？
- **推荐答案**：所有显式 Agent 共享 `Observation -> Memory/Belief -> Strategic Planner -> Reactive Controller -> Action Proposal` 的固定骨架；各环节可以使用不同实现和参数，简单场景可使用最小实现，但不能形成角色专属生命周期。Background Market Sector 属于环境，不进入该认知流水线。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：任意连接认知模块，或让角色标签决定完全不同的 Agent 生命周期。
- **拒绝原因**：会制造组合爆炸，并使保存、回放、分叉和行为审计需要维护多套语义。

### Q144：Agent 是被每个世界事件唤醒，还是只在形成决策时机后运行？

- **问题**：是否在任意世界事件后运行所有 Agent，还是先经过权限、送达、注意力与聚合，再用实际 Observation Packet 触发对应 Agent？
- **推荐答案**：只在确定性 Decision Opportunity 运行。开盘首次观察、定时唤醒、实际看到的重要信息、策略条件或风险阈值可以形成决策时机；同一虚拟时刻的相关可见变化可以聚合为一个 Observation Packet。不可见或无关事件不得唤醒 Agent。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：每个原始事件都唤醒所有 Agent，或先唤醒再检查 Agent 是否有权知道事件。
- **拒绝原因**：会导致事件数乘以 Agent 数量的无意义运行开销，并可能通过唤醒侧信道泄露不可见事件。

### Q145：一次 Agent 决策只输出 Action，还是保存完整认知提案？

- **问题**：Memory、Belief、StrategyPlan 和预算变化是否在 Agent 内部隐式发生，只对外输出 Action？
- **推荐答案**：一次 Runtime 运行产生统一、不可变且可保存回放的 Agent Decision，关联 decision、agent、observation、Agent 状态版本和虚拟时间，并汇集记忆、信念、策略、动作与预算消耗提案。Agent Decision 是审计边界，不表示内部提案已经被接受。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：只保存最终 Action，或允许 Runtime 在没有提案和事件记录时直接修改认知状态。
- **拒绝原因**：无法解释 Agent 根据哪次观察形成何种记忆、信念和策略，也无法精确回放认知变化。

### Q146：Agent Decision 中一个提案失败时，如何处理其他提案？

- **问题**：一个非法 Memory 提案是否应连带拒绝同一 Agent Decision 中独立合法的 Action，还是允许局部接受？
- **推荐答案**：整体边界先校验；Agent、Observation、状态版本、预算或整体 Schema 不合法时拒绝整个 Agent Decision。内部 Memory、Belief、StrategyPlan 和 Action 由各状态所有者独立校验；失败只影响自身及明确依赖项。所有接受、拒绝和原因作为一个完整 Decision Outcome 原子保存；Action 被接受后只进入调度，执行时仍由 World 重新校验。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：任一内部提案失败就拒绝全部其他提案；或允许部分提案生效但不保存完整的接受与拒绝结果。
- **拒绝原因**：前者会让次要认知错误阻断独立合法行为，后者会产生无法解释和无法恢复的部分决策状态。

## 25. Agent 规划并发、时间、适用性与版本

### Q147：同一个 Agent 是否允许同时进行多个战略规划请求？

- **问题**：Agent 等待一次 LLM Strategic Planner 返回时又出现价格、私聊或公告触发器，是否并发启动更多 Planner 请求、完全暂停 Agent，还是聚合后续重规划需求？
- **推荐答案**：同一 `branch_id + agent_id` 最多只有一个未结 Strategic Planner 请求；等待期间 Reactive Controller 继续使用最后有效 Strategy Plan。新增触发器合并为待处理重规划原因，当前请求完成或失败后再决定是否立即启动下一次规划。不同 Agent 仍可并发等待 Provider。
- **用户最终回答**：“我确认。”
- **状态**：`已接受`
- **被拒方案**：同一 Agent 并发规划并竞争修改 Memory、Belief 或 Strategy Plan；等待 Planner 时停止该 Agent 的全部即时反应。
- **拒绝原因**：前者会产生自我状态竞争和不可解释覆盖，后者会把现实 Provider 延迟错误映射为 Agent 在虚拟世界中完全失去反应能力。

### Q148：现实 Planner 返回时间是否决定 Strategy Plan 的虚拟生效时间？

- **问题**：同一规划请求在不同 Provider 延迟下返回时，能否按现实返回时刻立即生效？
- **推荐答案**：Planning Request 创建时根据请求虚拟时间和 Agent 的 planning latency 确定 Planning Activation Time。提前返回的结果等待该时刻；到达该时刻仍未返回时，虚拟时间停在相应决策边界等待现实结果或超时，现实等待不推进虚拟时间；超时后记录降级并继续旧计划。
- **用户最终回答**：接受，并指出该原则此前应已提及，要求核对当前仓库是否实现。
- **回查结果**：Q25 已冻结现实 LLM 响应时间不能改变虚拟时间，Q26/Q27/Q62 分别覆盖观察版本、动作排序和超时降级；本题新增的是请求时确定 Planning Activation Time 的实现语义。当前代码没有 Agent Runtime、Planning Request、Strategy Plan 状态、生效屏障或对应测试，仍由 FixtureStrategies 直接产生动作。
- **状态**：`已确认既有原则并细化；代码未实现`
- **被拒方案**：Provider 提前返回就提前生效，或现实延迟直接推后虚拟事件顺序。
- **拒绝原因**：会让网络和模型速度改变市场路径，违反既有虚拟时间契约。

### Q149：预定生效时刻到达后，如何判断旧观察产生的计划是否仍可采用？

- **问题**：等待 Planner 期间世界已经变化，是否只要出现更新 Observation 就作废旧计划，还是无条件接受返回结果？
- **推荐答案**：只按明确条件淘汰：请求已取消、超时或不再是当前请求；战略状态版本已被替代；计划有效期结束；或计划必要前提与 Agent 最新合法 Observation 明确冲突。普通市场变化或存在更新 Observation 本身不自动使计划失效；有效计划在预定虚拟时刻生效，等待期间积累的触发器可启动下一轮规划。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：任何新观察都令计划失效；或无视取消、超时、版本、有效期和前提冲突而采用旧计划。
- **拒绝原因**：前者会使高频市场中的 LLM 计划几乎永远无法生效，后者会执行已经明确不适用的战略状态。

### Q150：规划失败、超时或过期时是否消耗 CognitiveBudget？

- **问题**：未得到可采用计划时是否返还 Agent 的规划额度，技术性重试是否再次消耗认知次数？
- **推荐答案**：Planning Request 入队时预留预算；实际规划开始前取消或合并则释放预留，开始后无论成功、失败、超时或过期都消耗 CognitiveBudget。同一 ObservationPacket 的技术性重试不额外消耗 Agent 规划次数，但每次真实 Provider 调用都按实际 Token 和费用消耗 ProviderBudget。全部预留、消耗、释放和失败原因进入 Decision Outcome。
- **用户最终回答**：“是的我接受。”
- **状态**：`已接受`
- **被拒方案**：失败或被拒后返还已经使用的认知机会；技术重试同时重复扣除 CognitiveBudget；把 Provider 实际成本混入 Agent 认知预算。
- **拒绝原因**：退款会产生实际上无限的规划机会，重复扣除会把基础设施故障解释为 Agent 进行了多次独立认知决策。

### Q151：Agent 状态使用单一版本，还是组件独立版本？

- **问题**：Planner 等待期间的 Memory 或即时动作变化，是否应因为一个总版本号变化而让仅依赖 Strategy 状态的计划发生冲突？
- **推荐答案**：使用整体 Agent Revision 作为审计游标，同时由 Memory、Belief、Strategy、Attention 和 Budget 等可变认知组件维护自己的 revision。Agent Decision 只声明实际依赖和准备修改的组件版本；无关组件变化不制造冲突，组件版本不匹配时只拒绝对应提案及其依赖项；禁止最后写入者获胜。整体 revision 用于历史、Checkpoint 和 Agent View，不成为第二套状态真值。
- **用户最终回答**：“我确认。”
- **状态**：`已接受`
- **被拒方案**：用单一总版本校验所有提案；完全不做版本校验；发生冲突时覆盖较新的组件状态。
- **拒绝原因**：单一版本会造成大量伪冲突，无版本或最后写入者获胜则会丢失已经提交的认知变化。

## 26. 动作集合、资源承诺、提案依赖与决策理由

### Q152：一次 Agent Decision 可以提出多少个 Action？

- **问题**：Reactive Controller 在同一次决策中只能产生一个动作、可以任意产生无限动作，还是应输出一个受预算和 Schema 约束的动作集合？
- **推荐答案**：一个 Agent Decision 包含有界的零到多个独立 Action Proposal；不行动是合法决定。列表顺序没有执行语义，每个 Action 都有自己的 ID、预期执行时间、有效期和依赖。通用 Agent 层不提供任意动作批次原子性；确实需要原子语义时，由领域动作明确表达，例如 `ReplaceOrder`，而不是给 Action 数组附加通用 `all_or_nothing`。
- **用户最终回答**：“我确认。”
- **状态**：`已接受`
- **被拒方案**：强制每次恰好一个 Action；允许无界动作列表；把任意多个动作包装为通用原子批次。
- **拒绝原因**：恰好一个动作不能表达合法的不行动或多个独立意图，无界列表无法约束预算和负载，通用原子批次会把不同状态所有者和执行时刻错误地绑成一个事务。

### Q153：同一次决策中的多个 Action 竞争同一资源时如何裁决？

- **问题**：多个买单或转账都可能单独通过余额校验、合计却超过可用资产时，World 应按什么顺序准入并避免重复占用？
- **推荐答案**：按 `(expected_execution_time, priority, stable_tie_break_key)` 形成确定性准入顺序。每个动作在准入时按最大可能敞口建立与 `action_id` 关联的 Action Reservation，后续动作看到扣除预留后的可用资源；执行时重新校验并消耗实际金额，取消、过期或失败时释放剩余预留。预留、消费和释放全部事件化并可审计。
- **用户最终回答**：“我确认。”
- **状态**：`已接受`
- **被拒方案**：每个动作都针对同一原始余额独立校验；按数组位置、到达先后或随机 UUID 决定资源竞争；不保存预留生命周期。
- **拒绝原因**：会产生超额承诺、现实并发竞态或不可复现结果，也无法解释资源为何暂时不可用。

### Q154：Strategy Plan 更新时，已经排队的 Action 是否自动取消？

- **问题**：新计划替代旧计划后，由旧计划产生但尚未执行的动作，以及已经进入订单簿的订单，应否被系统静默撤销？
- **推荐答案**：不得因为 Strategy Plan 变化而隐式取消。Pending Action 是独立承诺，只能由它声明的 strategy revision 依赖、显式取消或有效期终止；没有声明该依赖的动作继续按自身条件调度。已经成为 World 事实的开放订单不再是 Pending Action，必须通过 `CancelOrder` 等领域动作撤销。Agent View 明确区分待执行动作、开放订单和已完成事实。
- **用户最终回答**：“我确认。”
- **状态**：`已接受`
- **被拒方案**：计划替换时静默清空该 Agent 的全部待执行动作或开放订单；把订单簿中的订单继续视为 Agent 内部计划状态。
- **拒绝原因**：会在没有动作和事件的情况下修改 World，破坏审计、回放和市场参与者可观察到的承诺语义。

### Q155：同一 Agent Decision 内部的提案如何声明依赖？

- **问题**：Memory、Belief、StrategyPlan 和 Action 提案之间是依靠数组顺序、隐式推断，还是使用可验证的显式依赖图？
- **推荐答案**：每个提案具有稳定 ID 和显式 dependency IDs，并只允许沿固定阶段正向依赖：`MemoryProposal -> BeliefProposal -> StrategyPlanProposal -> ActionProposal`。阶段可以没有提案，独立提案无需虚构依赖；循环、缺失引用或逆向依赖属于整个 Agent Decision 的结构错误。合法图中某个提案失败时，只沿显式依赖向下游传播，其他独立提案继续校验。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：依靠数组位置或运行时猜测依赖；允许循环、跨阶段逆向依赖；任一局部失败无条件拒绝全部提案。
- **拒绝原因**：隐式或任意依赖使结果受实现遍历顺序影响，循环无法形成清晰提交语义，全局连带失败则违背 Q146 已冻结的局部传播边界。

### Q156：是否保存 Agent 的完整思维链来解释决定？

- **问题**：为了回放和审计，是否要求 LLM 或规则 Agent 输出并保存完整自由文本推理过程，还是只保存结构化的决定依据？
- **推荐答案**：不要求也不保存完整自由文本思维链。Agent Decision 保存有界、结构化的 Decision Rationale，包括目标摘要、evidence IDs、belief IDs、strategy revision、风险标记、不确定性、action proposal IDs 和简短 `stated_reason`。实际 Provider 请求与结构化响应另行保存，用于回放、成本和故障诊断，但不自动写入 Memory，也不向其他 Agent 暴露。规则、Replay 和 LLM 实现都使用同一 Rationale Schema。
- **用户最终回答**：“我确认。”
- **状态**：`已接受`
- **被拒方案**：要求或持久化完整隐藏思维链；允许无限自由文本理由替代结构化引用；只保存 Action 而没有任何决策依据。
- **拒绝原因**：完整思维链不是稳定接口，会增加敏感信息、存储和 Provider 耦合；无限文本不可可靠校验；完全没有结构化依据又无法解释行为与可见证据、信念和策略的关系。

## 27. 规划工具、输出校验、异步完成与请求生命周期

### Q157：一次 Planning Request 内，Strategic Planner 能否进行多轮记忆检索？

- **问题**：Planner 必须用一次 Prompt 和一次 Response 完成规划，还是可以在同一 Planning Request 中多轮查询自身记忆和状态？
- **推荐答案**：允许有界 Planning Tool Loop。工具只读，并且只能返回该 Agent 原本有权访问的 Memory、Belief、Strategy、账户和观察状态；不得读取 Archive、其他 Agent 私有状态或全局真值，也不得直接提交 Action 或修改 World。每次检索消耗相应 CognitiveBudget，每次真实 Provider 调用消耗 ProviderBudget；轮数、调用数和返回量均有硬上限。中间调用不产生 Decision Opportunity 或 Agent Decision，最终结构化输出才形成一次规划结果，全部请求与工具结果进入审计记录。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：强制所有规划一次提示完成；允许无界自主工具循环；让规划工具越权读取或直接执行世界动作。
- **拒绝原因**：一次提示不足以按需使用有限记忆，无界循环使成本与终止不可控，越权工具则绕过 Observation 和 World 执行边界。

### Q158：LLM Planner 返回格式错误或引用不存在对象时如何处理？

- **问题**：Provider 输出是否可以被信任并直接执行，宿主是否可以自动修正非法字段，还是必须建立显式校验和失败边界？
- **推荐答案**：Provider 原始响应先原样保存，再经过确定性的 Planner Output Validation。无法解析、整体 Schema 错误、禁止字段或未闭合工具调用不得形成 Agent Decision；同一 Planning Request 内只允许有限格式修复，并向 Provider 提供机器可读错误。修复不重复消耗 CognitiveBudget，但每次实际调用继续消耗 ProviderBudget，且不改变 Planning Activation Time。仍无效则请求失败并沿用最后有效计划。成功解析后的各提案再按 Q146 分别进行语义校验；提案被拒绝不得触发 LLM 偷偷改写。宿主禁止补造 ID、删除非法字段、替换金额或猜测 Action。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：直接信任 Provider；宿主静默纠错或丢弃非法字段后继续；无限修复；把业务提案拒绝伪装为技术重试。
- **拒绝原因**：会让不可验证的猜测进入权威状态，掩盖真实模型输出与失败成本，并破坏相同输入下的基础设施确定性。

### Q159：异步规划结果应回写原 Agent Decision，还是形成新的 Agent Decision？

- **问题**：原始决策触发 Planner 后，Reactive Controller 仍会继续产生其他决定；Planner 完成时是否修改原记录、直接改写 Strategy Plan，还是建立一个关联的新决定？
- **推荐答案**：原始 Decision Opportunity 立即产生并关闭第一个不可变 Agent Decision，其中可以包含即时认知和动作提案以及 PlanningRequestProposal。请求中间查询和修复不产生额外决定。到达 Planning Activation Time 且结果通过校验后，基于 Agent 当时最新合法 Observation Packet 产生第二个 Agent Decision，引用 `planning_request_id`、原始 `decision_id`、规划所用观察和生效时采用的观察；它可以包含 StrategyPlanProposal 和明确依赖该计划的 Action Proposal。失败、超时或失效只记录请求终态和预算，不伪造空决定。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：在 Provider 返回后回写或补丁修改原 Agent Decision；让原决定在现实等待期间保持可变；规划结果绕过 Agent Decision 直接修改 Strategy Plan。
- **拒绝原因**：会破坏不可变审计和 Decision Outcome 原子性，也无法与等待期间产生的后续决定建立明确顺序。

### Q160：规划结果生效时与普通观察触发相遇，Agent 运行一次还是两次？

- **问题**：同一观察屏障既有价格、消息或风险触发器，又有 Planning Request 生效结果时，是否分别运行 Agent Runtime？
- **推荐答案**：先完成当前优先级阶段的 World 事件并冻结世界版本，再为 Agent 保存最新合法 Observation Packet；普通观察、定时、风险和规划结果等触发器聚合为有序、可审计的 `decision_triggers`。同一 `agent_id + observation_packet_id` 最多运行一次 Runtime 并产生一个 Agent Decision。没有其他触发时规划结果可以触发该决定，但仍使用实际 Observation Packet。后续动作若改变 World，必须形成新世界版本和 Observation Packet 后才能再次决策，即使虚拟时间戳相同。
- **用户最终回答**：先确认“冻结世界版本绝对是正确的”；在进一步区分输入冻结与调用去重后，确认“同一 `agent_id + observation_packet_id` 最多产生一次 Agent Decision”。
- **状态**：`已澄清并接受`
- **被拒方案**：对同一 Agent 和 Observation Packet 分别运行普通决策与规划完成决策；按 Provider 返回顺序运行；为内部规划结果制造虚假世界观察。
- **拒绝原因**：会让同一世界输入多次修改 Agent 状态和预算，重新引入隐含执行顺序，或破坏 Observation 的事实语义。

### Q161：Planning Request 应采用什么生命周期？

- **问题**：请求执行阶段和结束原因应混在大量状态中，还是以最小正交模型分别表达？
- **推荐答案**：生命周期采用 `Queued -> Running -> Ready -> Terminal`。Queued 表示请求已接受并预留 CognitiveBudget；Running 表示 Provider 或工具循环已开始且认知预算正式消耗；Ready 表示已保存通过结构校验的结果但尚未到 Planning Activation Time；Terminal 表示状态不再变化。Terminal 独立记录 `applied`、`rejected`、`failed`、`timed_out` 或 `canceled` outcome。所有转换事件化；终态后的迟到响应只记录为 `late_ignored`，不能重新打开请求或修改 Agent 状态。
- **用户最终回答**：“我接受这个更改。”
- **状态**：`已接受`
- **被拒方案**：为每种失败原因建立 Planning Request 子实体；把执行阶段和结束原因混成互斥状态；允许迟到响应重开终态请求。
- **拒绝原因**：状态爆炸会重复相同生命周期语义，混合阶段与结果不利于查询和恢复，终态重开则破坏确定性和预算记账。

## 28. 规划取消与聚合、计划结构及 Controller 边界

### Q162：谁可以取消 Planning Request，什么情况下允许取消？

- **问题**：普通新观察、保存、计划失效、Provider 失败和明确终止是否都应使用同一种取消语义？
- **推荐答案**：Queued 请求可以在实际开始前被更新规划需求确定性合并替代，旧请求以 `Terminal/canceled` 和 `coalesced_before_start` 原因结束、释放预留预算，替代请求引用旧请求。Running 或 Ready 请求不因普通观察和新触发器自动取消；只有授权的 `CancelPlanningRequest`、Agent 终止或分支终止可以明确取消。保存所需 Quiescing 等待已有请求结算；revision 冲突或计划过期使用 `rejected`，Provider 故障使用 `failed`，超时使用 `timed_out`。取消记录请求者、原因、虚拟时间和 request ID；已开始规划不返还 CognitiveBudget，迟到响应只记为 `late_ignored`。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：普通新观察自动取消运行中请求；保存时取消请求；把失效、失败、超时和明确取消统一记成 canceled；让迟到响应改变终态。
- **拒绝原因**：会混淆业务适用性、基础设施故障和授权控制行为，也可能破坏 Q46 的静止保存与预算审计。

### Q163：Planning Request 运行期间的新重规划触发器如何合并？

- **问题**：市场事件洪峰期间，是为每个触发器创建请求、只保存一个布尔标记，还是维护有界且可解释的待处理原因？
- **推荐答案**：在 Agent 规划状态中维护有界 Replan Trigger Accumulator，不创建新服务。每项记录 trigger type、semantic key、来源事件、首次与最近时间、最近 Observation Packet、严重度、次数和过期时间；相同语义键确定性合并，不同原因并存。超限时按确定性规则合并低严重度同类项，原始事实仍在权威事件日志。当前请求终止后按最新合法观察重新检查，预算允许时至多创建一个新请求，并将采用的触发器快照原子转移；只有创建成功才移除，过期或不成立则记录 dismissal reason，新请求创建后到达的触发器留给下一轮。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：每个触发器立即创建独立请求；只保存 `replan_pending=true`；无界累积原始事件；创建失败时丢失触发器；事后补写不可变请求。
- **拒绝原因**：分别会制造请求风暴、丢失原因、造成无界状态、静默漏掉规划需求或破坏请求审计边界。

### Q164：Strategy Plan 是自由 JSON，还是版本化声明式结构？

- **问题**：Q38 所称“声明式策略”是否允许自由字段和自然语言控制流，不同角色是否需要不同计划类型？
- **推荐答案**：所有 Agent 使用统一、版本化 Strategy Plan Envelope，至少包含 plan、schema、agent 和 strategy revision、来源 Observation Packet、有效范围、目标、必要前提、约束、Directive 与重规划条件。所有行为字段必须结构化；自然语言只进入 Decision Rationale。Directive 是版本化的带标签封闭联合，能力由 Capability 校验，Reactive Controller 只解释已注册类型。未知类型、字段错误或 Capability 不匹配拒绝 StrategyPlanProposal；新增 Directive 必须升级 Schema，禁止自由 JSON、动态表达式、脚本和角色专属计划类。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：自由 JSON；自然语言条件参与控制流；动态表达式或脚本；每种角色一套 Strategy Plan 类；遇到未知 Directive 时由宿主猜测。
- **拒绝原因**：会绕过类型、权限和版本边界，并把统一 Agent Pipeline 重新分裂成无法稳定回放的角色实现。

### Q165：一个 Agent 可以同时拥有多个活跃 Strategy Plan 吗？新计划如何更新旧计划？

- **问题**：不同领域分别维护计划栈并做隐式合并，还是用一个包含多种 Directive 的完整权威计划？
- **推荐答案**：每个分支中的每个 Agent 只有一个活跃 Strategy Plan revision。新 StrategyPlanProposal 声明 `based_on_strategy_revision` 并输出完整、自包含计划；要保留的旧 Directive 必须显式复制，未出现的 Directive 在新 revision 生效后失效。新计划通过校验后于 Planning Activation Time 原子替换，失败时最后有效旧计划继续；禁止隐式字段合并、局部 Patch 和最后写入者获胜。历史 revision 不可变；计划替换不自动取消 Pending Action 或开放订单。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：同一 Agent 多个活跃计划栈；宿主合并新旧字段；局部 Patch；最后写入字段获胜；计划替换时静默撤销既有承诺。
- **拒绝原因**：会要求额外的计划优先级、覆盖和冲突体系，制造多个策略真值，并违背版本和 Q154 的独立承诺语义。

### Q166：Strategic Planner 的 Provider 能否直接输出 Action Proposal？

- **问题**：Q38 曾笼统允许 LLM 输出策略和动作提案，是否意味着 Provider 可以绕过 Q143 冻结的 Reactive Controller 职责？
- **推荐答案**：不能。Provider 只输出包含完整候选 Strategy Plan、结构化 Rationale 和引用的 Planning Result；它可以通过类型化 Directive 表达行动意图，但不得决定 action ID、调度、预留或 World Action 参数。Planner Output Validation 先验证候选结果；到达生效边界后 Agent Runtime 使用最新合法观察检查适用性，再由确定性 Reactive Controller 生成 Action Proposal，并显式依赖 StrategyPlanProposal。Memory 和 Belief 提案也不得夹带在 Planning Result 中。Q38 收窄为允许结构化策略和行动意图，不允许 LLM 直出 World Action。
- **用户最终回答**：“我同意。”
- **状态**：`已接受并收窄 Q38`
- **被拒方案**：Provider 直接输出完整 Agent Decision 或 World Action Proposal；Provider 决定资源预留与调度；规划结果夹带 Memory 或 Belief 提案。
- **拒绝原因**：会绕过固定 Pipeline、最新观察、确定性动作生成和各状态所有者的提案校验边界。

### Q167：没有有效 Strategy Plan 时，Reactive Controller 可以做什么？

- **问题**：Q62 所称“无计划时仍运行 Controller”是否允许继续交易、通信或采用角色默认行为？
- **推荐答案**：采用 Reactive Controller 的版本化 `hold_and_protect` 配置，不伪造默认 Strategy Plan。Agent 仍可更新 Memory、Belief 并请求规划，但不得新建风险敞口、转移资产、发布信息、主动通信或建立其他新承诺。Controller 可以通过正式 `CancelOrder` 撤销自身不再受有效策略支持的开放订单，也可正式取消显式 strategy revision 依赖失效的 Pending Action；不得静默删除。每个无计划动作记录 fallback policy 版本、原因和 Decision Rationale。首个计划生效前显式 Agent 不自主交易，初始盘口仍由 Background Market Sector 提供。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：无计划时继续增加风险或建立新承诺；沿用过期计划、Provider 自由文本或角色默认作为隐藏策略；静默清除待执行动作和开放订单。
- **拒绝原因**：会引入未审计的第二策略来源，或通过无事件状态修改破坏市场承诺、回放和 Q154。

## 29. 计划条件、Directive 执行状态与 Action 反馈

### Q168：Strategy Plan 中不同“条件”分别在什么时候生效？

- **问题**：计划采用、Directive 执行、动作安全和重规划是否共用一个含糊的 conditions 数组？
- **推荐答案**：分成四种版本化类型。`activation_preconditions` 只在 Planning Activation Time 基于最新合法 Observation Packet 检查，失败则拒绝 StrategyPlanProposal；`directive_guards` 每次 Decision Opportunity 检查，不成立只跳过对应 Directive；`constraints` 限制 Controller 可以提出的 Action，并由 World 在准入和执行时独立重验权威规则，单个动作违反只拒绝动作；`replan_conditions` 只向 Replan Trigger Accumulator 加入原因，不自动取消当前计划。`valid_until` 由确定性虚拟时间事件处理，到期后采用 hold_and_protect。Capability 撤销使不兼容 Directive 不能产生动作并触发重规划，但不改写计划历史。所有谓词只能引用 Agent 合法观察和私有状态，禁止自然语言和隐藏全局状态。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：四类条件共用通用数组；guard 不成立就废弃整个计划；replan condition 自动取消计划；自然语言或全局隐藏状态参与判断。
- **拒绝原因**：会混淆采用、执行、安全和重规划的不同生命周期，并绕过局部观察和确定性解释边界。

### Q169：同一 Directive 在连续多个观察中满足条件时，是否每次都产生 Action？

- **问题**：如何区分“策略持续成立”和“应该再次执行动作”，并防止重复挂单？
- **推荐答案**：Directive 必须声明 `directive_id`、emission mode、cooldown/interval 和 max emissions。第一版只支持 `once`、`on_guard_transition`、`periodic` 和受 cooldown 限制的 `while_guarded`。Reactive Controller 另行维护按 `plan_revision + directive_id` 隔离的 Directive Execution Cursor，记录最近观察、guard 状态、发射次数、最近与下次可用虚拟时间和 action IDs；它进入 revision、checkpoint、branch 和 replay，但不修改不可变 Plan。同一 Observation Packet 不重复评估；action ID 由 decision、directive 和 emission ordinal 确定生成。结构合法的决定中一旦发射提案就推进 cursor，World 后续拒绝不触发即时无限重试；整个决定结构失败时不推进。新 plan revision 使用新游标命名空间。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：guard 持续成立就每次观察重复发射；由现实循环次数或进程生命周期控制次数；进程重启清零；计划替换后沿用旧 cursor。
- **拒绝原因**：会产生重复动作、重启依赖和不可回放行为，也会把不可变 Strategy Plan 变成隐藏可变状态。

### Q170：Action 的执行结果怎样返回给发起 Agent？

- **问题**：动作确认、拒绝、成交和失败是否通过普通社交注意力过滤，或者直接修改 Agent 的本地状态？
- **推荐答案**：World 为每个 Action 生成不可变 Action Receipt，关联 action、proposal、decision、outcome、reason、调度与执行时间、权威事件和结果状态引用，并保证进入发起 Agent 的下一份 Observation Packet。它不自动写入 Memory/Belief，也不是第二套状态。普通 accepted/queued 确认不单独唤醒 Agent；rejected、failed、expired、canceled、成交、部分成交和余额/风险变化以 `own_action_outcome` 触发器按观察屏障聚合。其他 Agent 只能看到正常公开后果，看不到私有拒绝、预留和 Receipt；无计划时 Receipt 也只能触发 hold_and_protect 范围内的动作。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：自身结果受社交 AttentionProfile 丢弃；Receipt 直接改写 Agent 本地余额；每个普通确认单独唤醒；向其他 Agent 暴露私有原因和预留。
- **拒绝原因**：前者使 Agent 无法管理自身承诺，直接改写绕过 Observation，过度唤醒造成负载，而私有泄露破坏信息边界。

### Q171：Agent 是否维护自己的余额、持仓和订单副本？

- **问题**：Agent 为了快速决策是否需要一份可写私有账本，还是每次从 World 的权威状态获得只读快照？
- **推荐答案**：World 的 PortfolioState 和订单状态是唯一权威，Agent 不维护可写影子账本。ObservationService 在每个 Decision Opportunity 把 Agent 所控制钱包的 portfolio revision、可用和预留余额、持仓、开放订单、Pending Action 与风险状态引用写入 Agent Account Snapshot；对控制者保证可见且不受 AttentionProfile 过滤。Planner 和 Controller 只能依赖该快照，不能用旧 Memory、Receipt 或自算余额下单。Receipt 与快照不一致时以 World 为准并产生 `state_reconciliation_failure`；快照缺失或版本不一致时采用 hold_and_protect。其他 Agent 只见正常公开状态。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：Agent 内维护可写余额与订单副本；从历史 Receipt 或 Memory 推算当前可用资源；快照失败时继续承诺；向其他 Agent 暴露私有账户快照。
- **拒绝原因**：会创建与 World 分叉的第二账本、导致超额承诺，并破坏权限与隐私边界。

## 30. 信息创作、规划认知输入与策略节奏

### Q172：Agent 能否创作新信息，还是只能转发已观察到的 InformationItem？

- **问题**：Agent 的通信行为是否只能转发既有信息，还是可以产生新的公告、观点或私聊内容？
- **推荐答案**：允许具备通信 Capability 的 Agent 通过类型化 CommunicationDirective 创作有界 `message_payload`；它只是内容数据而不是控制代码。Reactive Controller 将其转为 `PublishInfo` 或 `SendDirectMessage` Action Proposal，World 校验频道权限、接收关系、频率、长度、预算和调度。成功后创建不可变 Agent-Authored Information，记录真实作者、虚拟时间、频道和可选 `derived_from_info_ids`。内容可未经证实、错误或偏向，但系统不向普通 Agent 注入真值标签；OfficialPublisher 只提供可验证发布标记，不能伪造他人的真实作者。发送不自动写入作者 Memory/Belief，无有效计划时 hold_and_protect 禁止主动通信。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：只允许转发；允许内容成为系统事实或控制指令；发送即自动成为作者信念；伪造其他 Agent 的真实作者身份。
- **拒绝原因**：前者不能表达信息参与者和发行方，后者会打破事实/信息/信念分层及身份审计。

### Q173：Strategic Planner 读取候选认知更新，还是只读取已提交状态？

- **问题**：同一决策中的 Memory/Belief 提案尚未校验时，Planner 能否先假定它们会成功并据此开始规划？
- **推荐答案**：只读取已提交的 Memory/Belief。PlanningRequestProposal 显式依赖它所需的 Memory/Belief 提案；只有依赖被状态所有者接受后才进入 Queued 并记录实际读取的 memory、belief、strategy revision 和 Observation Packet。任一依赖被拒绝则请求不启动、预留释放并在 Decision Outcome 记录。Provider 不得读取投机上下文或驱动部分回滚；后续认知更新仍可发生，计划采用时按 Q149 和当前合法观察检查。Q157 的工具循环同样只能读已提交 Memory。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：根据候选 Memory/Belief 提前规划；依赖失败后仍保留请求；Provider 读取可回滚状态；为此建立投机提交和回滚机制。
- **拒绝原因**：会让规划输入、Decision Outcome 和回放无法对应真实状态，并引入不必要的认知事务复杂度。

### Q174：等待规划期间的新 Memory 或 Belief 更新是否自动使候选计划失效？

- **问题**：Planning Request 已记录的认知 revision 与当前 revision 不同时，是否一律拒绝候选 Strategy Plan？
- **推荐答案**：默认不失效。请求创建时的 Memory/Belief revision 是审计依据，普通后续更新进入 Replan Trigger Accumulator，等待当前请求终态后处理。只有候选计划显式声明的 activation precondition 才能要求特定 `belief_id + revision` 仍匹配，或指定 Memory 引用仍可访问；条件仅保存稳定引用和版本，不复制 Memory 原文。前提不成立则 StrategyPlanProposal 为 `rejected/not_applicable`，依赖动作同时拒绝。Agent 只看到通用未采用结果，不能借此区分遗忘、无权限、引用不存在或信念版本变化；详细原因留在审计记录。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **被拒方案**：任意认知 revision 变化都自动废弃计划；无视已声明认知前提；把任意 Memory 内容嵌入 Strategy Plan；向 Agent 泄露前提失效的具体内部原因。
- **拒绝原因**：会让高频认知更新导致规划饥饿、绕过遗忘边界，或向 Agent 泄露其不可访问的状态。

### Q175：首次 Observation Packet 后是否立即请求首个 Strategy Plan？

- **问题**：显式 Agent 是否可以在开盘前预置行为，或者在首次观察后仍等待不确定的后续触发器才开始规划？
- **推荐答案**：`sim_time = 0` 开盘屏障完成、背景初始订单簿冻结并发放首次合法 Observation Packet 后，每个可运行显式 Agent 运行一次初始 Decision Opportunity。必要 Memory/Belief 更新提交后创建首个 Planning Request；跨 Agent 可受容量池并发，但受启动前容量预检、单 Agent 单请求和 CognitiveBudget 约束。Activation Time 仍由虚拟 planning latency 确定；首个计划生效前采用 hold_and_protect。预算不足、依赖拒绝或 Provider 失败时保持保守状态并等待下一机会，不启动隐藏默认计划。Fixture、Replay 或规则模式保持同样时序但替换 Planner 实现；Background Market Sector 不进入该 Pipeline。
- **用户最终回答**：“理应如此。”
- **状态**：`已接受`
- **被拒方案**：首次观察前预置显式 Agent 动作；首次规划失败后静默启用默认策略；让 Background Market Sector 冒充显式 Agent 规划。
- **拒绝原因**：会破坏开盘公平性、可审计的独立认知起点和环境/Agent 分层。

### Q176：Strategy Plan 能否预先生成并排队一串未来 Action？

- **问题**：Strategy Plan 的 periodic、时间条件和 deadline 是否可被解释为在计划生效时直接展开未来 Action 队列？
- **推荐答案**：不能。Provider 只能在 Directive 中声明时间条件、period、cooldown 或 deadline；Plan 生效时 Runtime 最多向现有事件队列注册下一次 Directive Wakeup。Wakeup 到达时重新冻结世界、构造最新 Observation Packet，并由 Reactive Controller 重验 guard、constraint、Capability 和账户快照后再形成 Action Proposal。`expected_execution_time` 仅由当前虚拟时间、版本化 Agent/action latency 和 World 调度规则确定，不由 LLM 任意指定。Periodic Directive 一次只安排下一 Wakeup，替换或过期后未触发 Wakeup 显式失效；已经成为 Pending Action 的动作仍依 Q154 独立管理。
- **用户最终回答**：“我接受，并且这个问题在之前似乎已有讨论。”
- **回查结果**：用户的提醒正确。Q38 已拒绝可执行策略脚本，Q144 已允许定时唤醒，Q154 已规定 Pending Action 独立于后续计划，Q169 已冻结 periodic/cooldown 与执行游标。本题没有重新选择架构，而是把这些原则细化为 Wakeup 与未来 Action 的实现边界。
- **状态**：`已确认既有原则并细化`
- **被拒方案**：预展开长期未来 Action 队列；由 LLM 指定任意未来执行时刻；计划生效时提前提交未来消息或订单而不再观察。
- **拒绝原因**：会让策略脱离执行前世界状态，重引入脚本化控制，并与定时重新观察和独立 Pending Action 语义冲突。

## 31. 运行推进与暂停干预窗口

### Q177：`Running` 是否表示持续自动推进，用户如何获得确定的干预窗口？

- **问题**：沙盒若以最大速度推进，用户可能来不及在目标虚拟时刻干预；若绑定现实时间，批量推演又会失去效率。运行推进和用户干预应如何协调？
- **推荐答案**：每个 Branch 只使用一个权威事件循环；控制面可请求单步、运行至边界或按现实节奏推进，但这些方式不得改变 World 事件、排序和金融结果。用户命令在尚未提交的 Observation Barrier 生效，不能改写过去；最快运行已经完成后只能从 Checkpoint 分叉。
- **用户当前回答**：“用户可以暂停后输入事件。”
- **已确认边界**：世界干预只在 `Paused` 分支提交；`Running` 状态下用户必须先执行幂等 Pause，等待当前原子事件与 Observation Barrier 完成，再提交干预。暂停和推进速度属于控制面审计，不是虚拟世界事件，延续 Q40。
- **状态**：`部分接受/待冻结推进策略`
- **仍待确认**：是否需要单步、运行至边界和按现实节奏推进三种控制方式，以及交互界面的默认推进方式。
- **被拒方案**：在 Running 状态中途修改正在提交的原子事件；把现实命令到达时间直接当作金融事件排序依据；暂停后回写已经提交的历史。
- **拒绝原因**：分别会破坏原子性、确定性和只追加历史。

### Q178：State Intervention 是否只能通过封闭的类型化效果目录执行？

- **问题**：用户可能输入“某个 Agent 钱包密钥泄露”或“某交易所暴雷”等自然语言事件。系统应让 LLM 自由推断并修改市场，还是只允许预先定义的确定性世界效果？
- **推荐答案**：所有直接改变 World 权威事实的 State Intervention 只能使用预先注册、版本化、参数有界且具有确定性语义的效果。LLM 可以把自然语言解释成处于 draft 状态的类型化 Intervention Plan，但无权执行、补造效果或直接修改状态；该 Plan 必须经过 Schema、权限、不变量和影响预览校验，并由用户明确确认。无法映射的输入只能被拒绝，或由用户选择作为 Information Intervention 发布，不能静默近似成价格跳变、余额扣减或其他状态变化。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **具体边界**：Information Intervention 只通过正常送达、权限、延迟和注意力规则改变部分 Agent 可获得的信息，不自动改变 World 事实。State Intervention 在 Paused 分支的确定事件边界调用相关状态所有者的领域效果；通用干预层不得绕过 Ledger、WalletControl、Venue、Relationship 或其他所有者直接写字段。复合 Intervention Template 可以确定性展开为已支持的领域效果，但不能包含任意代码或通用状态 Patch。
- **示例澄清**：钱包密钥泄露首先改变可利用的钱包访问事实，而不自动等于余额被盗；后续转移仍通过正常 Action、延迟、权限和账本规则。“交易所暴雷”必须进一步解析为停撮合、冻结托管余额、关闭提现、资不抵债 haircut 或纯信息等明确效果；只有已建模 Venue、Custody 和 Exposure 时才能产生相应直接状态变化，否则只能作为信息发布或被拒绝。
- **被拒方案**：让 LLM 直接修改 World；接受任意 JSON Patch；对未支持事件静默猜测一个近似效果；把信息内容自动当作系统真值；用一个通用干预写入器绕过领域状态所有者。
- **拒绝原因**：这些方案会使同一输入产生不可预测结果，破坏资产守恒、权限边界、回放和事件解释，并把 LLM 变成第二个权威世界运行时。

### Q178-R1：顶层 LLM 是 Scenario Director，还是 Authoritative World Controller？

- **冲突来源**：用户要求保持事件表达灵活，并提出由顶层 LLM 判断信息干预或世界干预、自主选择目标和数据变化、调控整个金融市场。这可能被解释为推翻 Q178，让 LLM 直接成为 World 权威。
- **推荐答案**：顶层 LLM 定义为控制面的 Scenario Director。它可以理解用户意图、判断干预类别、选择目标与参数、组合通用金融效果并形成 Intervention Plan，但无权直接写任意状态、绕过领域不变量，或替本应自主决策的市场 Agent 行动。World 只执行已确认 Plan 中受支持且通过状态所有者校验的效果；Scenario Director 的输入、原始输出、最终 Plan 和确认记录全部保存，历史回放复用已确认 Plan，不重新调用 LLM。
- **用户最终回答**：“我接受你的 R1。”
- **状态**：`已接受，细化 Q178`
- **具体边界**：具体故事不应硬编码为独立世界修改器；例如“交易所暴雷”可由 Scenario Director 组合信息发布、运行状态变化、资产冻结或债权减记等通用效果。“钱包访问泄露给 Agent B”只赋予 B 相应能力并形成合法观察，是否利用由 B 自主决定；若用户描述的是已经发生的盗取，则应建模为独立外生资产效果，不能伪装成 B 的决定。CLOB 订单簿不是资产所有者，任何资产变化必须指向合法账户或债权状态。
- **被拒方案**：Scenario Director 直接修改数据库字段、余额或订单簿；通过自由代码创造未注册效果；强制某个 Agent 执行其本应自主选择的动作；在回放时重新询问 LLM 生成另一套干预。
- **拒绝原因**：这些方案会创建第二个权威世界、破坏 Agent 自主性和状态所有权，并使同一历史无法精确解释或回放。

### Q179：Scenario Director 是否可以在 Running 期间自主发起干预？

- **问题**：Scenario Director 是只解释用户明确提交的指令，还是可以持续观察市场，并因价格、波动或自身目标主动生成外生事件？
- **推荐答案**：默认只响应 Paused 分支上的用户命令；只有场景预先存在有界 Director Mandate 时才允许自主干预，以免隐藏的外生政策主导 Agent 表现。
- **用户最终回答**：“Scenario Director 目前只能在用户提交指令时工作。”
- **状态**：`已接受并收窄范围`
- **最终边界**：当前版本的 Scenario Director 严格 command-scoped。用户先暂停分支并提交意图，Director 生成一个待确认 Intervention Plan；Plan 被确认、拒绝或取消后，本次 Director 工作结束。它不轮询市场、不拥有持续目标、不在 Running 期间自行创建 Plan，也不需要 Director Mandate 实体。未来若引入自主调控，必须作为新能力重新决定授权、预算、触发、停止和实验归因边界。
- **被拒/暂缓方案**：Director 因市场平静、价格偏离或自定目标主动干预；后台持续轮询；当前版本预留无界自主权限；在没有新决策的情况下引入 Director Mandate。
- **拒绝原因**：会把外生调控变成不可见的市场参与力量，使实验结果主要反映 Director 偏好，并提前引入当前目标不需要的实体和生命周期。

### Q180：一个用户指令能否同时产生 Information Intervention 和 State Intervention？

- **问题**：现实事件通常同时包含事实变化、选择性泄露和后续公开披露。Scenario Director 应把整个用户输入二选一分类，还是允许一个 Plan 混合两类干预并表达不同生效时间？
- **推荐答案**：分类作用于 Intervention Plan 中的每个效果，而不是整段用户输入。一个 Plan 可以包含一个或多个有序 Intervention Stage；每个 Stage 声明虚拟生效时间和效果集合。同一 Stage 的必要世界变化在一个原子边界校验和提交，由这些变化产生的信息在相关状态成功提交后创建。事前泄露、事实发生和事后公告使用不同 Stage，避免依赖含糊的同阶段排序。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **具体边界**：定向 Information Intervention 仍经过权限、频道延迟、送达、注意力和阅读边界，只把内容交给 Plan 指定的候选接收者，不保证其相信、记忆或行动，延续 Q58。未被定向通知的 Agent 仍可看到其原本有权观察的市场、账户或公共后果，并可通过其他 Agent 转发形成推断；选择性通知不能隐藏合法 World View。Scenario Director 只提出 Stage，World 负责在生效边界重新校验和提交。
- **被拒方案**：把整个用户输入强制标为 information 或 world；用一个不可分辨顺序的大型效果列表表达事前泄露和事后公告；先发布“已发生”信息再尝试可能失败的状态修改；让定向发送绕过注意力直接成为 Agent 信念。
- **拒绝原因**：这些方案无法表达现实事件的信息时序，会产生事实与公告不一致、半生效状态，或破坏局部观察和 Agent 自主认知。

### Q181：Scenario Director 能否创造此前不存在的实体或过去关系？

- **问题**：用户输入可能引用当前 World 中不存在的交易所、钱包、机构或暴露关系。为了保持自然语言事件的灵活性，Director 能否在干预时补造这些对象及其过去状态？
- **推荐答案**：Director 可以在当前 Intervention Stage 创建系统已支持类型的新 World Entity 或关系实例，但不能运行时发明未知实体类型、任意字段或未注册语义，也不能让新实例具有未记录的过去。直接效果所需的事前 Exposure、WalletControl、持仓、合同或其他 Causal State 必须已存在；缺失时 Plan 报告 `missing_causal_state`，不得猜测受影响 Agent 或最终损失。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **具体边界**：缺少 Causal State 时，用户可以把内容仅作为 Information Intervention，或从更早 Checkpoint 分叉并在相关决策前建立实体和关系；也可以明确创建从当前时刻开始的新关系，但不能把它描述为过去事实。若用户是在纠正初始化遗漏，应形成明确的模型修正分支；该分支不能与原分支宣称只相差后来的单一干预，因为两者的前置条件已经不同。
- **灵活性边界**：具体故事不需要专用硬编码；Scenario Director 可自由实例化和组合已支持的实体、关系与效果。硬约束只要求直接效果作用于 World 已理解、拥有状态语义且在相应时刻存在的对象。
- **被拒方案**：运行时发明未知实体类型或字段；补造 Agent 过去的托管、控制或合同关系；为使事件产生损失而随机选择 Agent 扣款；把模型修正伪装成只改变后续事件的平行分支。
- **拒绝原因**：这些方案会制造不可验证的隐藏前提，使损失无法从事件前状态推导，并破坏分支比较和审计解释。

### Q182：Scenario Director 默认可以读取多少 World 与 Agent 信息？

- **问题**：Director 需要足够信息解释用户意图和选择干预目标，但“顶层”是否意味着可以默认读取所有 Agent 的私人 Persona、Memory、Belief、私聊和 Provider 上下文？
- **推荐答案**：采用最小必要权限。Director 默认可读取完整权威 World State，以及用于定位 Agent 的结构化身份、角色、Capability、资金、持仓、活动状态和公开行为；私人 Persona、Memory、Belief、私聊、Planner Prompt 与 Provider 原始响应默认不可见。用户只有在当前命令确有需要时，才能显式扩大 Director Access Scope。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **具体边界**：每个 Plan 保存本次 Director 实际读取的私有类别、目标对象和状态 revision，不能只记录模糊的 `full_access=true`。获准读取私人内容不等于获准披露；把私人内容带入 Information Intervention 必须是用户意图或 Plan 中独立、可预览的泄露效果。Director 使用有界只读查询获取相关状态，不默认把所有 Agent 历史塞入同一个 Provider 上下文。
- **秘密边界**：API Key、真实钱包私钥和运行环境秘密永远不能进入 Director 上下文。沙盒中的“密钥泄露”只表示 WalletAccess 或 WalletControl 状态变化，不包含真实秘密材料。
- **被拒方案**：Director 默认读取全部私人认知；用一个无明细的全局访问开关；读取私有内容后自动将其用于定向操纵或信息发布；把运行秘密作为模拟数据交给 LLM。
- **拒绝原因**：会破坏 Agent 认知隔离、使私人信息通过干预侧漏、扩大 Prompt 和成本，并引入真实凭证泄露风险。

### Q183：`Paused` 究竟冻结什么，确认后的干预何时生效？

- **问题**：暂停是否连控制面和已经发出的 Provider 请求一起冻结；用户确认干预后，是在暂停态立即提交，还是必须先恢复运行？
- **推荐答案**：Pause 等待当前原子事件及其 Observation Barrier 完成后生效。进入 `Paused` 后，虚拟时间与全部自主推进被冻结：不消费事件队列，不形成 Agent Decision Opportunity，不执行 Pending Action、Directive Wakeup 或 Background Market Sector。已经发出的 Provider 请求不强制取消；返回结果可以作为非权威材料保存，但在暂停期间不能激活计划、修改 Agent 或改变 World。Scenario Director 仍可在控制面运行；已确认且生效时间为当前虚拟时刻的 Intervention Stage 可以在分支保持暂停时原子提交并形成 Observation Packet，Agent 只在恢复后响应。未来 Stage 保持排队，直至分支恢复并到达其生效时刻。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **具体边界**：同一暂停窗口中的多个当前时刻干预按可审计的用户命令顺序提交；后一个 Plan 必须基于前一个提交后的 World revision 重新校验。恢复时先以一个 Observation Barrier 处理暂停期间已形成的观察，再继续后续虚拟事件。已经提交的干预不提供原地撤销；若结果不符合预期，应从干预前 Checkpoint 分叉。
- **被拒方案**：暂停时继续触发 Agent 或后台市场；让现实 Provider 返回绕过暂停并激活 Agent 状态；要求先恢复运行才能提交当前时刻干预；恢复时先推进旧事件再处理暂停期间形成的观察；删除已提交干预来模拟撤销。
- **拒绝原因**：这些方案会使暂停边界依赖现实延迟、让用户失去稳定干预窗口，或破坏事件顺序、只追加历史和分支可比较性。

## 32. Agent 初始化产品入口

### Q184：用户创建 Agent 时选择的“分类”是否应是可组合的参与者预设？

- **问题**：用户希望从“散户、巨鲸、庄家、做市商”等分类中选择 Agent；这些词分别描述身份、资金规模、行为目标和市场职能，是否应该建立互斥的 Agent 类型层级？
- **推荐答案**：使用可组合的 `Participant Archetype` 作为产品入口，而不是运行时 Agent 子类。首批预设为普通参与者、资本型持有者、流动性提供者、资产发行方和信息参与者；每个预设可以建议 `Role Tag`、唯一 `Funding Profile`、Capability 模板和 Persona 倾向，但不能改变统一 Agent Pipeline。一个 Agent 可拥有多个 Role Tag，但只使用一个不重复计账的 Funding Profile；Capability 单独表达硬权限。
- **用户最终回答**：“我接受。”
- **回查结果**：本题与 Q115 的既有分类边界重叠，作为面向用户的入口语义细化记录，不新增一套运行时类型模型。
- **状态**：`已接受并细化 Q115`
- **最终边界**：Role Tag 只用于展示与分析，不自动授予 Capability 或重复分配资产；Funding Profile 只记录初始化资金来源，不随运行中财富或行为变化；Persona 表达软倾向。 “庄家/操纵者”不作为首批类别，而作为 Persona 目标/策略倾向并由实际事件验证。
- **被拒方案**：为散户、巨鲸、庄家、做市商建立互斥子类；让类别名自动授予权限、固定行为或资产规模；把现实托管/协议地址直接创建为巨鲸 Agent。
- **拒绝原因**：这些概念不在同一分类轴上，会造成继承层级、权限和资金分配的错误耦合，并违反 Agent 独立组件模型与链上地址匿名合成边界。

### Q185：Participant Archetype 是一次性展开，还是持续绑定整套 Agent 配置？

- **问题**：用户选择流动性提供者等 Archetype 后，是否必须长期接受该预设的资金、能力和 Persona 组合；切换预设时是否覆盖此前手动编辑？
- **推荐答案**：Archetype 只在编辑时一次性展开为配置草稿。`Role Tags`、唯一 `Funding Profile`、`CapabilitySet`、`BasePersona`、`CognitiveProfile` 与 `AttentionProfile` 随后可以独立修改。切换 Archetype 只更新尚未被用户编辑的建议字段；已编辑字段保持不变，除非用户明确重置。每个最终字段记录 `default`、`archetype`、`random`、`user` 或 `llm_interpreted` 来源。
- **用户最终回答**：“我确认。”
- **状态**：`已接受`
- **最终边界**：Archetype 不进入 Agent 的运行时继承或决策逻辑；字段来源只服务 Preview、审计和重现。允许形成跨预设组合，例如使用 ordinary Funding Profile、流动性提供者 Role Tag 和报价 Capability 的业余交易者，但组合仍须通过资产、权限与可执行性校验。
- **被拒方案**：让 Agent 永久继承 Archetype 整包；切换 Archetype 静默覆盖用户字段；只保存最终值而不保存自动值的来源；用 Archetype 名称在运行时补齐隐藏配置。
- **拒绝原因**：整包绑定会重新耦合资金、身份、权限和认知；静默覆盖会丢失用户意图；隐藏补齐使初始化预览和复现不再可信。

### Q186：Random、自然语言与详细配置是否共用同一条 Agent 配置编译管线？

- **问题**：三种配置入口是否分别实现随机初始化器、LLM 初始化器和表单初始化器，还是只改变同一结构化草稿的输入来源？
- **推荐答案**：三种入口都生成统一的 `Agent Configuration Draft`，再经过同一个确定性的 `Agent Configuration Compiler`：补齐版本化默认值、校验字段与跨字段约束、生成 Resolved Initial State Preview、等待用户确认，最后冻结 `AgentDefinition`。Random 通过命名 seed 采样；自然语言由 LLM 解释为 Draft 并标注推断、歧义和未设置字段；详细配置直接编辑相同 Draft Schema。
- **用户最终回答**：“我确认。”
- **状态**：`已接受`
- **最终边界**：Agent Configuration Compiler 是统一初始化解析管线的确定性边界，不是新的自治 Agent 或持久化主体。自然语言 LLM 只是前置 Interpreter；不得直接初始化 Agent、分配最终资产、授予 Capability、提交 World 状态或绕过 Preview。相同 Draft、Compiler 版本、外部输入与 seed 必须得到相同解析结果，不受入口类型影响。
- **被拒方案**：维护三套输入 Schema 或初始化器；把自然语言直接拼入运行时 Prompt；让 LLM 输出后立即创建 Agent；按入口采用不同校验或默认值。
- **拒绝原因**：多套路径会产生语义漂移和组合爆炸；直接执行 LLM 输出会绕过资产守恒、权限、来源记录和用户确认；入口相关解析会破坏可重现性。

### Q187：自然语言 LLM 可以直接决定哪些 Agent 配置字段？

- **问题**：用户可能只输入“一个沉着冷静、略懂基础量化知识的散户”，也可能明确写出资金数量。LLM 是否可以自行补齐角色、Capability、链上资产和余额，还是必须区分用户陈述与模型推断？
- **推荐答案**：采用三层字段权限。用户明确陈述的 Persona 软字段和明确数值可以被 LLM 提取到 Draft，来源仍标为 `user`；Archetype、Role Tags、Funding Profile 和 CapabilitySet 只能由 LLM 作为建议输出，进入 Preview 后由用户确认；链、目标 Token、链上持仓、资产来源、最终 Token/USDx 数量、钱包控制、未注册 Capability、任意字段、代码和可执行策略禁止由 LLM 推断或直接写入。缺少明确输入的受保护字段保持未设置，交给版本化默认、seeded random、链解析器或用户补充。
- **用户最终回答**：“我确认。”
- **状态**：`已接受`
- **最终边界**：LLM 是自然语言解释器，不拥有 Agent Configuration Compiler 或 World 的写权限。“散户”不能隐式决定余额；“做市商”不能隐式授予能力；明确的资产数字也必须经过链、资产、守恒、权限和可执行性校验。
- **被拒方案**：让 LLM 从角色名称猜余额和资金档位；让自然语言直接授予 Capability；把模型推断标为用户输入；对缺失链或资产信息静默选择目标；允许 LLM 创造未注册字段、代码或策略脚本。
- **拒绝原因**：模型推断不是用户授权或权威世界事实，隐式资产与能力会破坏可审计性、资产守恒、权限边界和初始化可复现性。

### Q188：未描述字段使用默认值还是隐式随机采样？

- **问题**：用户没有描述某个 Persona 或配置字段时，自然语言入口是否可随机补齐；Random 与普通配置的边界如何保持可见和可复现？
- **推荐答案**：普通配置、自然语言配置和详细配置的空缺软字段使用版本化默认值或已选 Archetype 建议值，不隐式随机。只有 Random 入口或被用户逐字段明确标为 `random` 的字段才按命名 seed 从版本化合法分布采样，Preview 展示最终采样值。链、目标 Token、资产来源和必需资金输入等受保护字段缺失时产生阻塞错误，不能由默认、随机或 LLM 猜测补齐。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **最终边界**：相同自然语言、相同明确配置和相同版本在未启用 Random 时必须产生相同 Draft；启用 Random 时相同 seed、分布版本和输入必须产生相同结果。每个采样字段保存来源、分布版本和最终展开值。
- **被拒方案**：把所有未填写字段随机化；由 LLM 自由补出多样性；随机但不保存 seed/分布/结果；必需链与资产字段缺失时静默选取默认市场。
- **拒绝原因**：隐式随机会让“未表达”被误当作随机授权，破坏用户意图、Preview 可信度和初始化复现；受保护字段静默补齐会运行错误市场。

### Q190：是否废止显式 Agent 70% / Background 30% 的固定资本比例？

- **问题**：旧 Q110-Q114 曾把显式 Agent 与 Background Market Sector 的初始活跃资本设为 70/30，但用户明确认为资本规模应由显示设置的 Agent 数量与读取的链上总资产规模决定，而不应由人为比例决定。是否用新的资产池原则取代该比例？
- **推荐答案**：废止固定 70/30 比例。显式 Agent 数量由用户配置；资产规模由链上可纳入场景的供给及版本化合成分布规则决定；显式 Agent 按配置的人数生成合成 Portfolio；Background Market Sector 只承接未分配、非活跃或未建模资产，不设固定资本比例。Preview 仍必须展示 Agent 数量、Token/USDx 分配、背景余额、来源桶和所有缩放结果。
- **用户最终回答**：“我确认。”
- **状态**：`已接受，取代旧比例约束`
- **替代关系**：本题取代 Q110 中显式 Agent 70% / Background 30% 的资本边界，以及 Q113、Q114、Q117、Q119 中依赖该比例的初始化/激活约束。Q125 关于运行期间不自动再平衡的结论保留，但其 70/30 前提不再适用；Q120 的本地活跃流通市值与 USDx 守恒仍保留。
- **最终边界**：不再用固定比例决定 Agent 或背景资本。链上供给仍须先按锁仓、销毁、协议、桥、托管和不确定地址分类；只有可纳入场景的资产才可进入合成 Portfolio 或已记账背景账户。资产最终必须 Token/USDx 分别守恒，且不得把被排除余额静默变成购买力。
- **被拒方案**：保留 70/30 作为默认硬边界；根据该比例自动再平衡；用背景资本比例代替链上供给、Agent 数量和来源桶；把全部原始链上总供给直接平均给可见 Agent。
- **拒绝原因**：固定比例是人为市场影响假设，不是资产事实；它会与用户选择的 Agent 数量、链上覆盖率和真实来源分类冲突，也会把不可交易余额错误转成 Agent 资本。

### Q191：资产规模应使用原始链上总供给，还是来源分类后的可交易供给？

- **问题**：用户确认资本规模由显示设置的 Agent 数量和读取的链上资产规模决定，但原始 `totalSupply` 可能包含销毁、锁仓、协议/桥接约束和无法确认受益人的托管余额。哪部分可以成为显式 Agent 的自由资产？
- **推荐答案**：原始链上 `totalSupply` 只作为守恒基准；显式 Agent 资产池使用来源分类后的 `Eligible Active Supply`，即可进入本地市场并由显式 Agent 或已记账背景账户使用的可交易供给。销毁、锁仓、协议/桥接约束和无法确认受益人的非活跃托管余额不得直接成为 Agent 自由余额。用户配置的显式 Agent 数量决定 Eligible Active Supply 如何拆分成合成 Portfolio；未覆盖、未分配或不可交易余额进入来源桶或已记账背景储备。USDx 按本地可交易 Token、初始价格和 quote coverage 合成，不复制链上稳定币总量。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **最终边界**：总供给、可交易供给、非活跃储备和 Agent 自由余额是不同口径；初始化必须分别记录并校验。不能把被排除余额静默转成购买力，也不能把部分 Holder 覆盖伪装成完整可分配供给。
- **被拒方案**：按原始 totalSupply 平均或按比例分给显式 Agent；把锁仓、销毁、协议和不确定托管余额直接放入自由余额；将链上稳定币总量复制为 USDx；用背景余额掩盖 Holder 覆盖缺口。
- **拒绝原因**：这些做法会把不可执行资产当作资本，破坏资产守恒、来源解释、市场可交易性和初始化真实性。

### Q192：Eligible Active Supply 应如何拆分到指定数量的显式 Agent？

- **状态**：`已接受`
- **替代关系**：本题取代 Q113-Q114 中普通 7.5%、资本型 50%、流动性提供者 30%、发行方 10%、信息参与者 2.5% 等固定资金比例。Funding Profile 若保留，只能记录某个初始化值采用的来源/方法，不能重新引入角色财富配额。
- **最终边界**：数量、资产总额和分布形状是三个独立输入。默认分布可由链上特征校准但必须匿名合成；相同输入、分布版本和 seed 产生相同 Portfolio。Preview 展示分位、Top-K 集中度、最大/最小持仓和每个手动覆盖。
- **被拒方案**：按角色固定分资；按人数默认平均分配；把某个真实地址原样绑定给 Agent；让 LLM 或 Persona 决定财富；生成超过 Eligible Active Supply 的 Token。
- **拒绝原因**：角色不是财富事实，平均分配会抹去链上集中度，地址绑定会虚构数字孪生，LLM 不是资产所有者，而超额分配破坏守恒。

### Q193：合成 USDx 的总量与 Agent 间分配应采用什么规则？

- **问题**：USDx 不是从目标 Token 链上 Holder 状态直接读取的资产；应由角色、Token 持仓比例、用户金额还是场景级市场参数决定其总量和个体分配？
- **推荐答案**：场景级 `Quote Coverage Ratio` 决定活跃 USDx 总量：`active_usdx_supply = eligible_active_token_supply * initial_mid_price * quote_coverage_ratio`。该参数用户可见且可修改，不由 Agent 类型、Persona 或 LLM 决定。个体自由 USDx 通过与 Token 独立但可相关的版本化 `Portfolio Composition Distribution` 分配，使 Agent 可偏 Token、偏 USDx 或相对均衡，而不机械复制 Token 持仓比例。用户明确填写的单个 Agent USDx 是硬约束，剩余 USDx 再分配；手动总额超出场景总量时阻塞 Preview，不静默缩放。
- **用户最终回答**：“我接受。”
- **状态**：`已接受`
- **最终边界**：USDx 总量、个体分配权重和 Token/USDx 相关性分别保存并在 Preview 展示；所有金额使用整数最小单位。Agent、背景账户、费用账户和储备的 USDx 必须分别记账并整体守恒。
- **术语修正**：Q192 已使 `Funding Profile` 不再表示资金档位；若保留，它只能是可选的初始化方法标签，不能参与 Token/USDx 分配。逐字段来源继续由 Configuration Provenance 表达。
- **被拒方案**：按 Token 持仓同比例分 USDx；按 Role Tag 或 Archetype 固定 USDx；让 LLM 决定 quote coverage 或余额；手动金额超额时静默缩放；复制链上稳定币总量。
- **拒绝原因**：这些方案会把资产构成、角色和外部稳定币错误耦合，抹去买卖能力差异，或破坏用户硬约束、来源解释和 USDx 守恒。

### Q194：是否删除 Funding Profile，并把逐资产守恒与背景双边库存作为初始化硬约束？

- **问题**：Q190-Q193 已分别用 Eligible Active Supply、Portfolio Synthesis Distribution、Portfolio Composition Distribution 和 Configuration Provenance 表达资金总额、分布、构成与来源，Funding Profile 是否仍有独立语义？初始化后的 Token/USDx 总量和 Background Market Sector 库存还必须满足什么条件？

- **替代关系**：本题取代 Q115-Q116、Q184-Q185 与 Q193 中关于 Funding Profile 作为正式 Agent 字段或可选方法标签的结论。相关历史条目保留，但当前 Schema 不再包含该字段。
- **最终边界**：Compiler 必须分别证明 `token_total_before == token_total_after` 与 `usdx_total_before == usdx_total_after`，不能只证明折算净值相等。背景双边库存来自已知场景资产总量的显式分配，不是额外增发；任一侧为零时 Preview 必须说明不能形成双边背景订单流并阻止声称该能力已就绪。

- **拒绝原因**：冗余字段会造成多重真值；无资产订单和静默增发破坏 Ledger 与守恒；净值无法替代具体 Token 与 USDx 的交付能力。

### Q195：背景库存是否是显式 Agent 分配后的资产剩余？

- **问题**：背景订单流需要同时拥有 Token 与 USDx，但不应引入固定 70/30 或订单需求驱动的额外资金。链上总供给、显式 Agent 配置与背景库存之间的顺序如何定义？
- **推荐答案**：先读取并分类目标 Token 的总供给与 `Eligible Active Supply`，再按用户配置的显式 Agent 数量、Portfolio 分布和手动覆盖分配 Token；剩余可交易 Token 归入 Background Market Sector。USDx 先按已确认的 `Quote Coverage Ratio` 生成场景级 `active_usdx_supply`，再分配显式 Agent，剩余 USDx 归入 Background Market Sector。背景库存是各资产池的剩余余额，不按订单需求额外预留、不按固定比例切割、不静默增发；只有两种余额都大于零时，背景才可提供双边订单。
- **用户最终回答**：“我接受！”
- **状态**：`已接受`
- **最终边界**：背景库存公式分别为 `background_token = eligible_active_token_supply - explicit_agent_token - other_explicit_token_accounts` 与 `background_usdx = active_usdx_supply - explicit_agent_usdx - other_explicit_usdx_accounts`，两者都必须来自已记账资产且不得为负。目标 Token 的真实来源是链上快照；USDx 仍为场景合成资产。若启用背景订单流但任一侧余额为零，则初始化阻塞，不能声称背景流可提供双边订单。
- **前提修正**：曾建议按“初始盘口需求 + 有界储备”预留背景库存，用户纠正该前提；背景是显式 Agent 分配后的真实余额剩余。
- **被拒方案**：先按背景订单需求额外拨款；把剩余锁仓或销毁余额当作背景库存；按固定资本比例切割；背景缺少一侧资产仍生成双边订单；用隐式 mint 补足余额。
- **拒绝原因**：这些方案会颠倒资产来源顺序或制造不存在的购买力，破坏 Token 与 USDx 分别守恒以及订单执行的资源约束。
